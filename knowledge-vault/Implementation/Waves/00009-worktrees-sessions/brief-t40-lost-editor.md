### What happened

The orchestrator's Claude Code session had been started by aineo from one Neovim. It ran on as a background session after that Neovim quit, and the user started new ones. Its report server was told the first editor's address once, at Claude Code's start, in `AINEO_EDITOR_ADDRESS` (`lua/aineo/mcp/init.lua:33`, `mcp_servers()`). Every report since then failed with `aineo could not reach the editor at <runtime dir>/nvim.<pid>.0: ENOENT` (`lua/aineo/mcp/editor.lua:169`), while the user's live editors heard nothing. The user: "ok, this definetly needs to be fixed."

The planning read the incident's processes (`evidence/w9-t40-probes.txt`, P4): the conversation moved to Claude Code's background host is **a new Claude Code process on a new session id**, `--session-id <new> --fork-session --resume <old transcript>`, under `claude --bg-pty-host`, its `--mcp-config` carried over word for word with the dead editor's address. Its MCP server is a child of that Claude Code process, and its environment holds `CLAUDE_CODE_SESSION_ID` = the new id, and `NVIM` and `AINEO_CHILD` — Claude Code passes its environment on to its MCP server.

### The behaviour (D42)

What D42 does not fix is the planning's reading, each named as an assumption the orchestrator reports to the user (A10–A21, `plan.md`). Build them as written.

**1. Where a report goes.** The report server (`lua/aineo/mcp/`) hands each valid report on in this order:
1. **The editor that started Claude Code, as today** (`AINEO_EDITOR_ADDRESS`, `editor.deliver_report()`). Whatever that editor answers stands: delivered, not confirmed in time (`unconfirmed`), refused, or closed before it answered — each as today. **Only an editor that cannot be reached** — the connection is not made: ENOENT after it quit, ECONNREFUSED after it was killed (P3), any other connect failure — makes the server look further (A11). A report already sent is never sent again elsewhere, so no report shows twice.
2. **The report's session** (A10): the session the server's own Claude Code process is on, as T35's hooks last told it (*3*, below), read at this report; when no hook of that process has told one, the server's own `CLAUDE_CODE_SESSION_ID`, which is the process's first session (M5, P4). Either must pass the session-id check aineo already has (`aineo.claude`'s `is_session_id()` on T35's branch; the check is `SESSION_ID_PATTERN` and lower case) — or, since `aineo.mcp` may not require `aineo.claude`, a check of the same pattern in the MCP home, said so in your report. With no session known, the answer is today's failure, saying also that no session was known to keep the report for.
3. **A running aineo Neovim that shows that session** (D42; A12–A14): from the list of running aineo Neovims (*2*, below), every entry that follows the report's session, in this order: the one with the newest claim (`:Aineo claim`, *5*), then by last use, the most recently used first. Each is tried until one takes the report:
   - an entry whose address cannot be reached is skipped, and its entry removed (P3: a failure costs well under a millisecond);
   - the editor is asked to take the report **only if it still follows that session** — a new export of the report home, run there as `receive_report()` is (`lua/aineo/report/init.lua:390` on T36's branch) — so a list entry that went stale between its last write and this report is refused by the editor itself, and the next entry is tried; a Neovim at that address that is not aineo, or an older aineo, refuses too (its error), and the next is tried;
   - **delivered** ends the search; **unconfirmed** ends it too — the editor holds the request and runs it once its user is done, as today (`tests/test_mcp_blocked_editor.lua:97`); **closed before it answered** ends it as a failure, as today (`:128`). Only a refusal or an unreachable address passes to the next.
4. **Kept on disk, under that session** (D42; D39): when no running Neovim took it, the report is appended as a record to that session's records file — T36's `records.session_records_file(state_directory, session_id)` (`lua/aineo/report/records.lua:47` on T36's branch) — through a new export of the report home's entry point, never `records.lua` reached past it. The record's time is the server's own clock, as `YYYY-MM-DDTHH:MM:SS`. The next aineo that follows the session shows it (`follow_report_session()`, `:416` on T36's branch, reads that file). It is never kept in the working directory's file nor another session's.

The search is bounded: an unreachable address fails at once (P3), a refusal is an answer, and only an editor that takes the request and holds it waits — the existing `CONFIRMATION_TIMEOUT_MS`, 5 s (`lua/aineo/mcp/editor.lua:16`) — and it ends the search.

**What Claude is told** (D42: "Claude is told which happened"; A16): the tool's result says which of three happened, each a text of its own: delivered to the Agent Report as today (`Delivered to the Agent Report.`, `lua/aineo/mcp/protocol.lua:65`); delivered to the Agent Report of another Neovim that shows this session, the one Claude Code started in being gone; or kept in this session's Agent Report on disk, no Neovim showing the session now, to show when aineo next shows it. None of the three is a tool error (`isError` false). A report that could not be kept at all is a tool error naming why, as today. The `unconfirmed` text stands as it is.

**2. The running aineo Neovims** (A12–A14). A list under the editor's state directory (`kept_places().state_directory`), in a folder of its own under `aineo/`, one owner-only file per editor, each replaced whole (a temporary file and a rename, as `session_ids.keep_session_id()` writes) so a reader never reads half of one. **Not `stdpath('run')`:** on macOS it is a directory of each Neovim's own, removed when it quits (P1). An entry holds the editor's address (`v:servername`), its working directory, the session it follows, when it was last used, and when it claimed that session, if it did. An editor:
- **writes its entry** whenever it is told a session to follow — at every start of Claude Code and every switch, where T39's wiring tells the report home the session — and an editor that follows no session has no entry;
- **marks itself used** at `FocusGained`, at each start and switch, and at a claim (A14);
- **removes its entry** as it quits (`VimLeavePre`);
- reads nothing of the list itself: only the report server reads it. An entry whose address cannot be reached is removed by the server that finds it so (*1.3*).
The list holds the user's own addresses only; nothing is executed from it, and the editor at an address decides for itself whether it takes a report (*1.3*).

**3. The session a Claude Code process is on, for its report server** (A10, A18, A19). T35's hook relay (`lua/aineo/claude/hook_relay.lua` on T35's branch) keeps, at every `SessionStart` and `SessionEnd`, a small record per Claude Code process — the session that process is on now, and whether that session's `SessionEnd` has come — under the state directory, keyed by the Claude Code process's pid:
- **The pid comes from `"$PPID"` written on the hook's command line**, never from the relay's own parent: P2 measured that a shell running a hook expands `$PPID` to the process that ran it, under `/bin/sh`, `/bin/zsh`, `/bin/bash` and Node's `spawn(…, { shell: true })` alike, while the relay's own parent is that process only when the shell runs the command in its own place, and the shell itself otherwise. Today's command is a list of words each quoted for a POSIX shell (`arguments.lua:22`, `shell_word()`, on T35's branch); `"$PPID"` is the one word left for the shell to expand. The report server finds its own Claude Code process as its parent (`vim.uv.os_getppid()`): M5 and P4 measured the server a child of Claude Code's process.
- **The hook writes the record itself, before it starts its deliverer**, so the records follow the order Claude Code runs its hooks in: T35's deliverer is detached (`hook_relay.lua:70`, `start_deliverer()`), and two of them may run at once. One small file replaced by a rename; the hook still returns at once (A3 as revised for T35, A18). Say in your report what you measured the hook to take.
- **Each start's token is unique on the host** (A19): T35's token is the launch count in one editor (`lua/aineo/claude/init.lua:256–257` on T35's branch, `tostring(launches)`), so two editors' first starts share `1`. Make it as unique as a new session id (`session_ids.new_session_id()` makes one), and keep it in the record: a record whose token is not the hook's is an earlier process's whose pid was reused, and is replaced, never paired with.
- The report server reads the record of its own parent pid at each report that needs it (*1.2*). Records of Claude Code processes that no longer run do not pile up: say in your report how they are removed (a pid that no longer runs, `vim.uv.kill(pid, 0)`, is one way).

**4. The hook relay follows the same rule** (D42, answer 2; A17). When T35's deliverer cannot reach its editor — the `pcall(deliver, …)` that today ends quietly (`hook_relay.lua:114`) — and the event is a switch by the record of *3* (a `SessionStart` of another id after the `SessionEnd` of the session the record holds, in the same process, as A1 defines a switch), the deliverer keeps the new id for the working directory aineo started Claude Code in, as the session the next start there resumes (D38; `session_ids.keep_session_id()`), and exits quietly as today. The record of *3* has already moved to the new session, so the next report of that Claude Code goes to the new session. **It tells no other Neovim** (A17): a Neovim that shows the session left runs its own Claude Code in its terminal, which did not switch, and its panes follow that one (D37, T39). A `SessionStart` with no `SessionEnd` before it in the same process — the first of a process, such as the background host's — keeps nothing for the directory (A1). The hook's command line gains what this needs: the state directory and the working directory, written by aineo as the address is, and `"$PPID"`.

**5. `:Aineo claim`** (D42, answer 4; A15). A subcommand of `:Aineo` and a `<Plug>(aineo-claim)` mapping, **with no prefix key** (A15):
- it claims, for this Neovim, the session it follows now (T35's `session_id()`): its entry records the claim and its time, and it is marked used; a report of that session whose own editor is gone comes here before any other Neovim showing the session, until another Neovim claims it;
- in a Neovim that follows no session yet — Claude Code never started there — it claims nothing and tells the user once, with a warning;
- a claim decides among the Neovims that show the session when the editor that started the report's Claude Code cannot be reached; it never takes a report from a starting editor that answers (A15);
- a claim ends when this Neovim follows another session (its entry then names that one, unclaimed) or quits (its entry goes); the most recently used of the others then gets the session's reports (A15);
- picking another session to claim is not this packet's: it waits for the session picker the user names `\cs`.
The completion offers `claim`; `:Aineo claim` takes no further word.

The help** (`doc/aineo.txt`, inside the places under *Boundary*): where a report goes when the editor that started Claude Code is gone, and the three things Claude is told; that a report whose session no Neovim shows is kept for that session and shows when aineo next follows it; `:Aineo claim` and `<Plug>(aineo-claim)`; the list of running Neovims under `stdpath('state')`; that a switch made by a Claude Code whose editor is gone is kept as the session the next start resumes; and, in a LIMITS subsection, what is not measured (below) — above all that a conversation moved to Claude Code's background runs on a new session id no Neovim follows (P4), so its reports are kept on disk under that session until a Neovim follows it, and `:Aineo claim` cannot pick it.
