### What happened

### The behaviour (D42)

What D42 does not fix is the planning's reading, each named as an assumption the orchestrator reports to the user (A10–A27, `plan.md`). Build them as written.

**1. Where a report goes.** The report server (`lua/aineo/mcp/`) hands each valid report on in this order, sending the editor the report's session (*1.2*) with it whenever it knows one:
1. **The editor that started Claude Code, as today** (`AINEO_EDITOR_ADDRESS`, `editor.deliver_report()`) — with one difference (A23): an editor that follows a session other than the report's, which happens while `:Aineo claim <id>` has made it follow a session its own terminal does not run (*5*), keeps the report on disk under the report's session (*1.4*) and answers so, without showing it. Whatever that editor answers stands: delivered, not confirmed in time (`unconfirmed`), refused, or closed before it answered — each as today. **Only an editor that cannot be reached** — the connection is not made: ENOENT after it quit, ECONNREFUSED after it was killed (P3), any other connect failure — makes the server look further (A11). A report already sent is never sent again elsewhere, so no report shows twice.
2. **The report's session** (A10): the session the server's own Claude Code process is on, as its record (*3*, below) holds it at this report — T35's hooks keep it; when no hook of that process has written one, the server's own `CLAUDE_CODE_SESSION_ID`, which is the process's first session (M5, P4), and which the server writes as that process's record at its start (A27). Either must pass the session-id check aineo already has (`aineo.claude`'s `is_session_id()` on T35's branch; the check is `SESSION_ID_PATTERN` and lower case) — or, since `aineo.mcp` may not require `aineo.claude`, a check of the same pattern in the MCP home, said so in your report. With no session known, the answer is today's failure, saying also that no session was known to keep the report for.
3. **A running aineo Neovim that shows that session** (D42; A12–A14): from the list of running aineo Neovims (*2*, below), every entry that follows the report's session, in this order: the one with the newest claim (`:Aineo claim`, *5*), then by last use, the most recently used first. Each is tried until one takes the report:
   - an entry whose address cannot be reached is skipped, and its entry removed (P3: a failure costs well under a millisecond);
   - the editor is asked to take the report **only if it still follows that session** — a new export of the report home, run there as `receive_report()` is (`lua/aineo/report/init.lua:390` on T36's branch) — so a list entry that went stale between its last write and this report is refused by the editor itself, and the next entry is tried; a Neovim at that address that is not aineo, or an older aineo, refuses too (its error), and the next is tried;
   - **delivered** ends the search; **unconfirmed** ends it too — the editor holds the request and runs it once its user is done, as today (`tests/test_mcp_blocked_editor.lua:97`); **closed before it answered** ends it as a failure, as today (`:128`). Only a refusal or an unreachable address passes to the next.
4. **Kept on disk, under that session** (D42; D39): when no running Neovim took it, the report is appended as a record to that session's records file — T36's `records.session_records_file(state_directory, session_id)` (`lua/aineo/report/records.lua:47` on T36's branch) — through a new export of the report home's entry point, never `records.lua` reached past it. The record's time is the server's own clock, as `YYYY-MM-DDTHH:MM:SS`. The next aineo that follows the session shows it (`follow_report_session()`, `:416` on T36's branch, reads that file). It is never kept in the working directory's file nor another session's.

The search is bounded: an unreachable address fails at once (P3), a refusal is an answer, and only an editor that takes the request and holds it waits — the existing `CONFIRMATION_TIMEOUT_MS`, 5 s (`lua/aineo/mcp/editor.lua:16`) — and it ends the search.

**What Claude is told** (D42: "Claude is told which happened"; A16): the tool's result says which of three happened, each a text of its own: delivered to the Agent Report as today (`Delivered to the Agent Report.`, `lua/aineo/mcp/protocol.lua:65`); delivered to the Agent Report of another Neovim that shows this session, the one Claude Code started in being gone; or kept in this session's Agent Report on disk, no Neovim showing the session now, to show when aineo next shows it. None of the three is a tool error (`isError` false). A report that could not be kept at all is a tool error naming why, as today. The `unconfirmed` text stands as it is.

**2. The running aineo Neovims** (A12–A14). A list under the editor's state directory (`kept_places().state_directory`), in a folder of its own under `aineo/`, one owner-only file per editor, each replaced whole (a temporary file and a rename, as `session_ids.keep_session_id()` writes) so a reader never reads half of one. **Not `stdpath('run')`:** on macOS it is a directory of each Neovim's own, removed when it quits (P1). An entry holds the editor's address (`v:servername`), its working directory, the session it follows, whether that is its own terminal's session or one `:Aineo claim <id>` made it follow, when it was last used, and when it claimed that session, if it did. An editor:
- **writes its entry** whenever it is told a session to follow — at every start of Claude Code and every switch, where T39's wiring tells the report home the session — and an editor that follows no session has no entry;
- **marks itself used** at `FocusGained`, at each start and switch, and at a claim (A14);
- **removes its entry** as it quits (`VimLeavePre`);
- reads nothing of the list itself: only the report server reads it. An entry whose address cannot be reached is removed by the server that finds it so (*1.3*).
The list holds the user's own addresses only; nothing is executed from it, and the editor at an address decides for itself whether it takes a report (*1.3*).

**3. The session a Claude Code process is on, for its report server** (A10, A18, A19). T35's hook relay (`lua/aineo/claude/hook_relay.lua` on T35's branch) keeps, at every `SessionStart` and `SessionEnd`, a small record per Claude Code process — the session that process is on now, and whether that session's `SessionEnd` has come — under the state directory, keyed by the Claude Code process's pid:
- **The pid comes from `"$PPID"` written on the hook's command line**, never from the relay's own parent: P2 measured that a shell running a hook expands `$PPID` to the process that ran it, under `/bin/sh`, `/bin/zsh`, `/bin/bash` and Node's `spawn(…, { shell: true })` alike, while the relay's own parent is that process only when the shell runs the command in its own place, and the shell itself otherwise. Today's command is a list of words each quoted for a POSIX shell (`arguments.lua:22`, `shell_word()`, on T35's branch); `"$PPID"` is the one word left for the shell to expand. The report server finds its own Claude Code process as its parent (`vim.uv.os_getppid()`): M5 and P4 measured the server a child of Claude Code's process.
- **The hook writes the record itself, before it starts its deliverer**, so the records follow the order Claude Code runs its hooks in: under D43 the deliverer is detached (`hook_relay.lua:70`, `start_deliverer()`), and two of them may run at once. One small file replaced by a rename; the hook still returns at once (D43, A18). Say in your report what you measured the hook to take.
- **The hook's command is the one D44's merged `--settings` carries**: T35's fix round merges aineo's two hooks into the user's own `--settings`; the words this packet adds to the hook's command (*4*) go into those same hooks, wherever the fix round builds them (the dispatch amendment names the function). When aineo starts Claude Code without its hooks (D44, the user's `--settings` unreadable), no hook writes a record, and the server's own (A27) stands.
- **Each start's token is unique on the host** (A19): T35's token is the launch count in one editor (`lua/aineo/claude/init.lua:256–257` on T35's branch, `tostring(launches)`), so two editors' first starts share `1`. Make it as unique as a new session id (`session_ids.new_session_id()` makes one), and keep it in the record: a record whose token is not the hook's is an earlier process's whose pid was reused, and is replaced, never paired with.
- The report server reads the record of its own parent pid at each report that needs it (*1.2*). **At its start, when its process has no record, the server writes one** (A27): its parent's pid, its own `CLAUDE_CODE_SESSION_ID`, and its own working directory, which is its Claude Code's (P6). So a Claude Code that runs without aineo's hooks — started without them under D44 because the user's `--settings` could not be read, or moved to Claude Code's background host if that host drops `--settings` (P4, not measured) — still has a record, of its first session.

- **The sessions that have a running Claude Code** (for `:Aineo claim <id>`'s completion, *5*) are the sessions of the records whose pid runs: `vim.uv.kill(pid, 0)` returns 0 (P5); ESRCH is an ended process and EPERM another user's that took the pid, and either record is removed. A pid one of the user's own processes took since passes the check as Claude Code's would (P5): such a stale record is offered until a hook or a server replaces it (A26). Listing 50 records costs about a millisecond (P5). A session whose Claude Code runs with neither aineo's hooks nor aineo's report server — a Claude Code aineo did not start, or the incident's, whose server runs the relay of before this packet — is in no record and is not offered.
- Records of Claude Code processes that no longer run do not pile up: say in your report how they are removed.

## The tests

Each behaviour gets one test, seen failing first:
- a report whose starting editor answers goes there and nowhere else, even when another Neovim that shows the same session is in the list and was used more recently;
- with the starting editor gone (quit, and killed), a report goes to the Neovim in the list that follows the report's session, and the answer says so in its own words, not an error;
- with no Neovim following the report's session — none in the list, or only ones following other sessions, the working directory alike — the report is kept in that session's records file, not the directory's nor another session's; a Neovim that then follows the session shows it; the answer says it was kept, not an error;
- the report's session is the one its Claude Code process's hooks last told: after a `/clear` in the fake, a report whose editor is gone goes to the new session, not the first (A10);
- with no record of the process's hooks, the server's own `CLAUDE_CODE_SESSION_ID` is the report's session (A10); with neither, today's failure, saying no session was known;
- two Neovims following the session: the more recently used gets it (a `FocusGained` in the other moves it there);
- `:Aineo claim` in the less recently used: it gets the session's reports from then on, until the other claims it; after the claiming Neovim quits, the other gets them;
- `:Aineo claim` in a Neovim that follows no session warns once and records nothing;
- a claim lapses when its Neovim follows another session: a report of the claimed session goes to the other Neovim that shows it;
- a list entry whose Neovim has switched to another session since it was written: the editor refuses, and the next entry, or the disk, takes the report;
- a list entry whose address cannot be reached is skipped and removed, and the next entry takes the report;
- a Neovim in the list at a hit-enter prompt: the report is `unconfirmed`, as today, not passed on to another Neovim nor kept on disk, and shows there once the user is done;
- an editor's entry is written at a start, follows a switch, and is gone once that editor quits;
- the hook's command line carries `"$PPID"` unquoted for the shell, every other word quoted as before; the record lands under the fake's pid when the fake runs the hook through `sh -c` with the command alone, and through a shell that does not run the command in its own place (P2);
- the start tokens of two editors' first starts differ;
- with its editor gone, a switch through the fake (`/clear`, `/resume`, `/branch`) is kept for the working directory: the next start there resumes the new session; a `SessionStart` with no `SessionEnd` before it in that process keeps nothing; with the editor present, T35's behaviour is unchanged;
- with its editor gone, a switch through the fake moves a Neovim that follows the session left by `:Aineo claim <id>` to the new session, and its next report shows there; a Neovim that shows the session left as its own terminal's stays where it is (A17);
- the completion offers `claim`, and after it the running sessions of this working directory: a session whose Claude Code ended, or that runs in another directory, is not offered; `:Aineo claim` takes at most one word;
- a Claude Code started without aineo's hooks (the fake given no `--settings` hooks to run): its report server writes its record at its start, with the fake's `CLAUDE_CODE_SESSION_ID`, and the completion offers that session; with the hooks, the server leaves the startup hook's record as it is (A27);
- `:Aineo claim <id>` of a session whose editor is gone (the fake's starting editor quit): this Neovim's Report shows that session's kept records, its changes pane and Input that session's, and the next report of that Claude Code shows here, the answer naming another Neovim;
- while a claim of another session holds, a report of this Neovim's own Claude Code is kept under its own session and not shown, the answer saying kept (A23); a `/clear` in its own Claude Code keeps the new session for the directory and leaves the panes on the claimed session (A25); `:Aineo claim <own id>` brings them back;
- `:Aineo claim <id>` with an id that fails the session-id check errs once, naming it, and changes nothing; one that passes it but runs nowhere is followed (A26).
