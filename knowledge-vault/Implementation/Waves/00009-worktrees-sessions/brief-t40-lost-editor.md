### What happened

The orchestrator's Claude Code session had been started by aineo from one Neovim. It ran on as a background session after that Neovim quit, and the user started new ones. Its report server was told the first editor's address once, at Claude Code's start, in `AINEO_EDITOR_ADDRESS` (`lua/aineo/mcp/init.lua:33`, `mcp_servers()`). Every report since then failed with `aineo could not reach the editor at <runtime dir>/nvim.<pid>.0: ENOENT` (`lua/aineo/mcp/editor.lua:169`), while the user's live editors heard nothing. The user: "ok, this definetly needs to be fixed."

The planning read the incident's processes (`evidence/w9-t40-probes.txt`, P4): the conversation moved to Claude Code's background host is **a new Claude Code process on a new session id**, `--session-id <new> --fork-session --resume <old transcript>`, under `claude --bg-pty-host`, its `--mcp-config` carried over word for word with the dead editor's address. Its MCP server is a child of that Claude Code process, and its environment holds `CLAUDE_CODE_SESSION_ID` = the new id, and `NVIM` and `AINEO_CHILD` — Claude Code passes its environment on to its MCP server.

### The behaviour (D42)

What D42 does not fix is the planning's reading, each named as an assumption the orchestrator reports to the user (A10–A29, `plan.md`). Build them as written.

**1. Where a report goes.** The report server (`lua/aineo/mcp/`) works out the report's session (*1.2*) before each report, since the claim check needs it, and hands each valid report on in this order, sending the editor the report's session with it whenever it knows one:
1. **A Neovim that has claimed the report's session, then the editor that started Claude Code** (D42, answer 6; A11, A15).
   - **The claimant first, even while the starting editor answers.** Before each report, the server looks in the list of running aineo Neovims (*2*) for the entries that follow the report's session with a claim, and takes the one with the newest claim. When there is one and its address is not the starting editor's, the server asks it to take the report the way *1.3* asks, only if it still follows that session. Delivered, `unconfirmed`, or a connection closed before it answered each end the search, the last as a failure, as today: a report sent to the claimant is never sent again. A claimant that cannot be reached, whose entry is then removed, or that refuses, having followed another session since its entry was written, passes the report on to the starting editor. The check reads files only. P7 measured it on Neovim 0.12.5: 0.07–0.28 ms with one to ten Neovims listed, 1.2 ms with fifty (`evidence/w9-t40-probes.txt`), the user's "about 1 ms". With no session known, there is no check, and the starting editor gets the report as today. When the claimant is the starting editor itself (a `:Aineo claim` with no argument in the Neovim whose terminal runs the session), that editor is tried once, as the starting editor.
   - **Then the editor that started Claude Code, as today** (`AINEO_EDITOR_ADDRESS`, `editor.deliver_report()`) — with one difference (A23): an editor that follows a session other than the report's, which happens while `:Aineo claim <id>` has made it follow a session its own terminal does not run (*5*), keeps the report on disk under the report's session (*1.4*) and answers so, without showing it. Whatever that editor answers stands: delivered, not confirmed in time (`unconfirmed`), refused, or closed before it answered — each as today. **Only an editor that cannot be reached** — the connection is not made: ENOENT after it quit, ECONNREFUSED after it was killed (P3), any other connect failure — makes the server look further (A11). A report already sent is never sent again elsewhere, so no report shows twice.
2. **The report's session** (A10): the session the server's own Claude Code process is on, as its record (*3*, below) holds it at this report — T35's hooks keep it; when no hook of that process has written one, the server's own `CLAUDE_CODE_SESSION_ID`, which is the process's first session (M5, P4), and which the server writes as that process's record at its start (A27). Either must pass the session-id check aineo already has (`aineo.claude`'s `is_session_id()` on T35's branch; the check is `SESSION_ID_PATTERN` and lower case) — or, since `aineo.mcp` may not require `aineo.claude`, a check of the same pattern in the MCP home, said so in your report. With no session known, the answer is today's failure, saying also that no session was known to keep the report for.
3. **A running aineo Neovim that shows that session** (D42; A12–A14): from the list of running aineo Neovims (*2*, below), every entry that follows the report's session but the claimant *1.1* tried already, the most recently used first. Each is tried until one takes the report:
   - an entry whose address cannot be reached is skipped, and its entry removed (P3: a failure costs well under a millisecond);
   - the editor is asked to take the report **only if it still follows that session** — a new export of the report home, run there as `receive_report()` is (`lua/aineo/report/init.lua:390` on T36's branch) — so a list entry that went stale between its last write and this report is refused by the editor itself, and the next entry is tried; a Neovim at that address that is not aineo, or an older aineo, refuses too (its error), and the next is tried;
   - **delivered** ends the search; **unconfirmed** ends it too — the editor holds the request and runs it once its user is done, as today (`tests/test_mcp_blocked_editor.lua:97`); **closed before it answered** ends it as a failure, as today (`:128`). Only a refusal or an unreachable address passes to the next.
4. **Kept on disk, under that session** (D42; D39): when no running Neovim took it, the report is appended as a record to that session's records file — T36's `records.session_records_file(state_directory, session_id)` (`lua/aineo/report/records.lua:47` on T36's branch) — through a new export of the report home's entry point, never `records.lua` reached past it. The record's time is the server's own clock, as `YYYY-MM-DDTHH:MM:SS`. The next aineo that follows the session shows it (`follow_report_session()`, `:416` on T36's branch, reads that file). It is never kept in the working directory's file nor another session's.

The search is bounded: the claim check reads files (P7), an unreachable address fails at once (P3), a refusal is an answer, and only an editor that takes the request and holds it waits — the existing `CONFIRMATION_TIMEOUT_MS`, 5 s (`lua/aineo/mcp/editor.lua:16`) — and it ends the search.

**What Claude is told** (D42: "Claude is told which happened"; A16, reworked for answer 6): the tool's result says which of four happened, each a text of its own: delivered to the Agent Report as today (`Delivered to the Agent Report.`, `lua/aineo/mcp/protocol.lua:65`); delivered to the Agent Report of another Neovim that claimed this session; delivered to the Agent Report of another Neovim that shows this session, the one Claude Code started in being gone; or kept in this session's Agent Report on disk, no Neovim showing the session now, to show when aineo next shows it. None of the four is a tool error (`isError` false). A report that could not be kept at all is a tool error naming why, as today. The `unconfirmed` text stands as it is.

**2. The running aineo Neovims** (A12–A14). A list under the editor's state directory (`kept_places().state_directory`), in a folder of its own under `aineo/`, one owner-only file per editor, each replaced whole (a temporary file and a rename, as `session_ids.keep_session_id()` writes) so a reader never reads half of one. **Not `stdpath('run')`:** on macOS it is a directory of each Neovim's own, removed when it quits (P1). An entry holds the editor's address (`v:servername`), its working directory, the session it follows, whether that is its own terminal's session or one `:Aineo claim <id>` made it follow, when it was last used, and when it claimed that session, if it did. An editor:
- **writes its entry** whenever it is told a session to follow — at every start of Claude Code and every switch, where T39's wiring tells the report home the session — and an editor that follows no session has no entry;
- **marks itself used** at `FocusGained`, at each start and switch, and at a claim (A14);
- **removes its entry** as it quits (`VimLeavePre`);
- reads nothing of the list itself: only the report server reads it. An entry whose address cannot be reached is removed by the server that finds it so (*1.3*).
The list holds the user's own addresses only; nothing is executed from it, and the editor at an address decides for itself whether it takes a report (*1.3*).

**3. The session a Claude Code process is on, for its report server** (A10, A18, A19). T35's hook relay (`lua/aineo/claude/hook_relay.lua` on T35's branch) keeps, at every `SessionStart` and `SessionEnd`, a small record per Claude Code process — the session that process is on now, and whether that session's `SessionEnd` has come — under the state directory, keyed by the Claude Code process's pid:
- **The pid comes from `"$PPID"` written on the hook's command line**, never from the relay's own parent: P2 measured that a shell running a hook expands `$PPID` to the process that ran it, under `/bin/sh`, `/bin/zsh`, `/bin/bash` and Node's `spawn(…, { shell: true })` alike, while the relay's own parent is that process only when the shell runs the command in its own place, and the shell itself otherwise. Today's command is a list of words each quoted for a POSIX shell (`arguments.lua:22`, `shell_word()`, on T35's branch); `"$PPID"` is the one word left for the shell to expand. The report server finds its own Claude Code process as its parent (`vim.uv.os_getppid()`): M5 and P4 measured the server a child of Claude Code's process.
- **The hook writes the record itself, before it starts its deliverer**, so the records follow the order Claude Code runs its hooks in: under D43 the deliverer is detached (`hook_relay.lua:70`, `start_deliverer()`), and two of them may run at once. One small file replaced by a rename; the hook still returns at once (D43, A18). Say in your report what you measured the hook to take.
- **The hook's command is the one D44's merged `--settings` carries**: T35's fix round merges aineo's two hooks into the user's own `--settings`; the words this packet adds to the hook's command (*4*) go into those same hooks, wherever the fix round builds them (the dispatch amendment names the function). When aineo starts Claude Code without its hooks (D44, the user's `--settings` unreadable), no hook writes a record, and the server's own (A27) stands.
- **Each start's token is unique on the host** (A19): T35's token is the launch count in one editor (`lua/aineo/claude/init.lua:256–257` on T35's branch, `tostring(launches)`), so two editors' first starts share `1`. Make it as unique as a new session id (`session_ids.new_session_id()` makes one), and keep it in the record: a record whose token is not the hook's is an earlier process's whose pid was reused, and is replaced, never paired with.
- The report server reads the record of its own parent pid at each report that needs it (*1.2*). **At its start, when its process has no record, the server writes one** (A27): its parent's pid, its own `CLAUDE_CODE_SESSION_ID`, and its own working directory, which is its Claude Code's (P6). A hook's record is never written over by the server: the startup hook runs before the server starts (M5), and a later hook replaces the server's. So a Claude Code that runs without aineo's hooks — started without them under D44 because the user's `--settings` could not be read, or moved to Claude Code's background host if that host drops `--settings` (P4, not measured) — still has a record, of its first session.
- Every record also holds the working directory of its Claude Code: the one aineo wrote on the hook's command line, or the server's own.
- **The sessions that have a running Claude Code** (for `:Aineo claim <id>`'s completion, *5*) are the sessions of the records whose pid runs: `vim.uv.kill(pid, 0)` returns 0 (P5); ESRCH is an ended process and EPERM another user's that took the pid, and either record is removed. A pid one of the user's own processes took since passes the check as Claude Code's would (P5): such a stale record is offered until a hook or a server replaces it (A26). Listing 50 records costs about a millisecond (P5). A session whose Claude Code runs with neither aineo's hooks nor aineo's report server — a Claude Code aineo did not start, or the incident's, whose server runs the relay of before this packet — is in no record and is not offered.
- Records of Claude Code processes that no longer run do not pile up: say in your report how they are removed.

**4. The hook relay follows the same rule** (D42, answer 2; A17). When T35's deliverer cannot reach its editor — the `pcall(deliver, …)` that today ends quietly (`hook_relay.lua:114`) — and the event is a switch by the record of *3* (a `SessionStart` of another id after the `SessionEnd` of the session the record holds, in the same process, as A1 defines a switch), the deliverer keeps the new id for the working directory aineo started Claude Code in, as the session the next start there resumes (D38; `session_ids.keep_session_id()`), and exits quietly as today. The record of *3* has already moved to the new session, so the next report of that Claude Code goes to the new session. **It tells only a Neovim that follows the session left by a claim of a session its own terminal does not run** (A17, amended for answer 5): such a Neovim, found in the list of *2* (whose entry says so), is told the switch and follows the new session as a claim of it — the same follow `:Aineo claim <id>` makes (*5*) — so it keeps receiving that Claude Code's reports. The editor-side call is an export the composition root wires (T35's receiver drops another start's token, so it cannot serve). A Neovim that shows the session left as its own terminal's is not told: its Claude Code did not switch, and its panes follow that one (D37, T39). A `SessionStart` with no `SessionEnd` before it in the same process — the first of a process, such as the background host's — keeps nothing for the directory (A1). The hook's command line gains what this needs: the state directory and the working directory, written by aineo as the address is, and `"$PPID"`.

**5. `:Aineo claim` and `:Aineo claim <id>`** (D42, answers 4 to 7; A15, A23, A25–A29). A subcommand of `:Aineo`, taking one optional word, and a `<Plug>(aineo-claim)` mapping for the form with no word, **with no prefix key** (A15).
- **With no word** (A29), what it does depends on what this Neovim follows now:
  - **It follows its own Claude terminal's session** (T35's `session_id()`): it claims that session for this Neovim. Its entry records the claim and its time, and it is marked used. Each report of that session then comes here first, even while the editor that started its Claude Code answers (*1.1*), until another Neovim claims it.
  - **It follows a session claimed by `:Aineo claim <id>`** that its own terminal does not run: it returns this Neovim to its own terminal's session and claims that. The Report, the changes pane and Input's draft are told that session, the same way a switch tells them (T39's wiring): the claimed session's draft is kept as that session's, and this Neovim's own session's draft comes back into Input (D40). Its entry then names its own session, claimed, and the claim of the other session ends.
  - In a Neovim whose terminal runs no session, because Claude Code never started there (T35's `session_id()` gives none), it tells the user once, with a warning, and changes nothing. That happens whether or not it follows a session claimed by an id. Such a Neovim leaves a claimed session with another `:Aineo claim <id>`.
- **With a session's id**, it makes this Neovim follow that session — its Report, its changes pane and Input's draft, each told the session as a switch tells them (T39's wiring), so the shown windows show it at once and a hidden pane when next shown — and claims it, as above. **Its own Claude terminal keeps running its own session**; nothing is sent to Claude Code. An id that fails the session-id check is refused with one error, naming it, and changes nothing. An id that passes it is taken whether or not a Claude Code runs it now (A26): the Neovim then shows that session's kept Report and draft.
- **The completion** after `claim` offers the sessions that have a running Claude Code (*3*) whose working directory is this Neovim's (A26), the Neovim's own terminal's among them; `:Aineo claim` takes at most one word.
- **While this Neovim follows a session its own terminal does not run** (A23, A25, A28):
  - a report of its own Claude Code still comes to it as the starting editor, unless another Neovim has claimed its session (*1.1*), and is kept on disk under its own session, not shown (A23);
  - a switch inside its own Claude Code is kept for the directory, as T35 keeps one (D38), but does not move the panes, which stay on the claimed session (A25);
  - `\s` sends nothing (A28, below);
  - `:Aineo claim` with no word, or with its own session's id, brings the panes back to its own terminal's session (A29).
- **`\s` while this Neovim follows a session its own terminal does not run** (D42, answer 7; A28, which replaces A24). Send and Visual Send both send nothing: Normal-mode `\s`, `:Aineo send` and `<Plug>(aineo-send)`, and `\s` in Visual mode. Input is not changed. The user is told once, with one warning that starts `aineo: nothing sent —` as Send's own refusals do (`lua/aineo/send/init.lua`, `REFUSALS`, 28). The warning says that Input holds the claimed session's draft, names that session, and says that `:Aineo claim` with no argument returns this Neovim to its own session. The Visual form ends Visual mode with the selection kept for `gv`, as Visual Send's own refusals do (`refuse_selection()`, 288). The claim is checked before Send's own checks, so this warning is the only one the user sees. When this Neovim follows its own terminal's session, claimed or not, Send is as today.
  - **Where the refusal lives.** It is made by the composition root, in `plugin/aineo.lua`'s two send actions: `ACTIONS.send` (369–371 at `85a57f9`) and `VISUAL_ACTIONS.send` (462–466). Every path to Send goes through these two: `:Aineo send` runs `ACTIONS[...]` (708), and `\s` maps to `<Plug>(aineo-send)` in both modes (`PREFIX_KEYS.send = 's'`, 477; `map_prefix()`, 524). **`lua/aineo/send/` is not touched.** Under modularity's direction table, `aineo.send` may require only `aineo.config`, `aineo.claude` and `aineo.layout`, and none of them knows which session the panes follow. The composition root does, since it holds the claim.
- **A claim takes the session's reports from every other Neovim, the starting editor included** (*1.1*; A15, reworked for answer 6). It does so while the claimant answers and follows the session. So a Neovim that claims a session another live Neovim's Claude Code runs gets that session's new reports. The other Neovim's Report shows none of them until it next reads the session's records, at its next follow of the session. Both Neovims keep the reports in the session's one records file (D39), each through its own report home.
- A claim ends when this Neovim follows another session (its entry then names that one, unclaimed), returns to its own by `:Aineo claim` with no word (A29), or quits (its entry goes). It also ends when another Neovim claims the session (the newest claim wins). When a claim ends, the session's reports go to the starting editor again; when that editor cannot be reached, the most recently used Neovim that shows the session gets them, else the disk (A15).
