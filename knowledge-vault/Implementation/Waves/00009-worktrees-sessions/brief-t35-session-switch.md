### The behaviour (D36, D37, D38)

What Claude Code does was measured on 2026-10-07 with Claude Code 2.1.292 (`evidence/w9-real-claude-sessions.txt`, M1–M8). Where this section goes past the user's answers it says so: assumptions A1–A3 are the orchestrator's, reported to the user (`plan.md` › *Assumptions to report to the user*).

- **The hooks (D36; A1).** Every start of Claude Code that `start_session()` makes also passes `--settings` with an inline JSON object whose `hooks` key holds two entries, `SessionStart` and `SessionEnd`: each a `type: "command"` hook with no matcher, so that it runs for every source and every reason, a short `timeout` in seconds, and as its command the relay below. aineo adds no other settings key: no `disableAllHooks`, no `statusLine`, nothing a user's settings would lose. M2 measured that a `--settings` hook is added to the hooks already configured, not put in their place, so no plugin-directory fallback is built.
- **What Claude Code sends (M1).** `SessionStart`'s `source` is `startup`, `clear`, `resume`, `fork` (for `/branch`) or `compact`. Every switch — `/clear`, an in-session `/resume`, `/branch` — is `SessionEnd` with the old id (`reason` `clear`, or `resume` for both `/resume` and `/branch`), then `SessionStart` with the new id, about 0.1 s later. `/compact` sends `SessionStart` (`compact`) with the same id and no `SessionEnd`. Exit sends `SessionEnd` (`prompt_input_exit`). In every hook `CLAUDE_CODE_SESSION_ID` equals stdin's `session_id` (M3).
- **The relay (A3).** A Lua file in the claude home, run as aineo's MCP server is run — `<v:progpath> --headless --clean --cmd 'set noloadplugins' -l <relay> <editor address> <start token>` (`lua/aineo/mcp/init.lua` › `mcp_servers()` for the shape and the reason for `noloadplugins`) — that reads the hook's JSON from stdin and sends the editor **one RPC notification**, never a request, naming the event (`SessionStart` or `SessionEnd`), the `session_id`, the `source` or `reason`, and the start token it was given, then exits. **It returns at once:** M8 measured that `/resume` waits for the `SessionStart` hook (a hook sleeping 2 s held the resumed screen 2.3 s), so the relay does nothing Claude Code waits on beyond writing the notification, and every bit of work happens in the editor, scheduled after it. The editor's address is written on its command line by aineo, not read from `$NVIM`, though M3 measured that the hook inherits `$NVIM` and `AINEO_CHILD`. A JSON it cannot read, or one without a string `session_id`, sends nothing. **An editor it cannot reach** — gone, as at an exit-time `SessionEnd` — makes it exit 0 and write nothing: the brief review measured a bare relay exiting 1 there with `E5113: … connection failed: connection refused` and a stack trace on stderr (`brief-review.md`, T35-10, S7). It never writes to stdout. (The planning read on Claude Code's hooks page, https://code.claude.com/docs/en/hooks, that a `SessionStart` hook's stdout is added to Claude's context; `evidence/w9-probes.txt`'s D-docs does not quote that sentence, so read the page before you cite it. Writing nothing to stdout holds either way.)
- **The hook's command is one shell string.** A command hook has a `command` string alone, which Claude Code runs through a shell — not the MCP server's `command` and `args` array (`lua/aineo/mcp/init.lua:28–35`), so that shape cannot be copied. Every word of it — the program, each flag, the relay's path, the address, the token — is quoted for a POSIX shell: `'…'`, a `'` inside written `'\''`. Measured by the brief review (`brief-review.md`, T35-2): with a program path and a relay path each holding a space and a `'`, words joined by spaces gave `hook_code = 127` and `/bin/sh: …: No such file or directory`, and nothing was notified; each word quoted, the editor got `{ "SessionStart", "…", "startup" }`.
- **The start token.** Each start gives its relay a token of its own on the command line — the terminal's job id will do — and the receiver drops a notification whose token is not the running start's. That is how a late hook of an exited Claude Code is told from the running one's: the notification otherwise names no process.
- **The receiver (D37; A1, as reworded on 2026-10-07).** The claude home exposes one function the relay's notification calls. It takes the event, the id, the source or reason and the token, checks the id (below), and works from a scheduled callback, never inside the RPC handler:
  - a `SessionStart` whose id is the one the session follows does nothing more (`compact`, or the start's own `startup` or `resume`);
  - **a switch is a `SessionStart` with another id that follows the followed id's own `SessionEnd`**, in the running start: it makes that id the session's, keeps it for the session's working directory as `keep_session_id()` keeps a new one today (D38), and calls the `on_session_switched(id, source, left)` callback the composition root gives in `aineo.claude.Settings` (a new optional field beside `on_terminal_replaced`), `left` being the session left; the `SessionEnd`'s reason is told too (A1). M1 measured that pair before every real switch — `/clear`, `/resume`, `/branch`;
  - **a `SessionStart` with a new id and no such `SessionEnd` before it is not a switch**: nothing is followed, kept or called back. The one exception is the start aineo itself makes (below). Whether a `/fork` background copy, a conversation moved to the background or a subagent sends such a `SessionStart` was not measured (*Not measured*);
  - a `SessionEnd` of the followed id marks that session ending and calls nothing back: a `SessionEnd` alone, as at exit, changes nothing shown, since the process's end is followed as today;
  - it does nothing once Neovim is quitting (`v:exiting`), nor for a notification whose start token is not the running start's (an exited Claude Code's late hook).
- **A start that replaces the session followed is a switch (D38).** When a start of Claude Code follows another id than the one followed before it — **T19's fallback included**, where a resume found no conversation and `start_new_session_in_place()` starts a new id (`lua/aineo/claude/init.lua:319–333`, called from 345–355), which today hands `settings.on_terminal_replaced` the terminal and nothing else — the claude home keeps the new id and calls `on_session_switched(<new id>, 'startup', <old id>)`, `resume` in place of `startup` when that start resumed an id. D38 names the case: "a `/clear` session in which nothing was sent falls back to a new session, as T19 does". Without it, the fallback's new id is followed silently, its own `SessionStart(startup)` matches it and calls nothing back, and T39's homes keep every report, base, mark and draft under the dead session (`brief-review.md`, T35-1). The first start in an editor, with no session followed before it, calls nothing back.
- **Which session aineo says it is on (A2).** `aineo.claude` gains a way to ask for the id the session follows now (for T39): from each start, the id aineo started Claude Code on (`--session-id` or `--resume`), without waiting for a hook to name it, since in a folder not yet trusted no hook runs at all (M7); then each switch's, the fallback's new id included. Nil before any start.
- **The id's check (M4).** Claude Code's ids are lower-case version-4 UUIDs, which today's kept-id check (`SESSION_ID_PATTERN`) accepts. Keep the check as it is; a `session_id` it refuses is neither followed nor kept.
- **Where hooks do not run** — before the trust dialog is answered (M7: no hook, no MCP server, no title until then; what follows a "Yes" was not seen), under a managed `allowManagedHooksOnly`, under a `disableAllHooks` in any of the user's settings (D-docs: "the `disableAllHooks` setting can't disable managed hooks from outside managed settings", which reads as turning every other hook off, aineo's `--settings` hooks presumably included; not measured) — aineo hears of no switch and behaves as D23 does today, on the session it started. The help says so, in the LIMITS subsection.
- **The MCP server is never asked (A4).** M5 measured one MCP server for Claude Code's whole life, whose `CLAUDE_CODE_SESSION_ID` goes stale after a switch. Nothing here reads a session id from it or its environment.
- **The fake `claude`** learns to run the `SessionStart` and `SessionEnd` hooks of the `--settings` it is given, with the JSON M1 recorded on their stdin, when a test tells it to, each through a shell as Claude Code runs a command hook (`sh -c <command>`, the JSON on stdin) and each **with `env = { NVIM = os.getenv('NVIM') }`**, the `NVIM` the fake inherited, as Claude Code passes its environment through (M3). Without it, `vim.system()` sets `NVIM` to the fake's own server (`$VIMRUNTIME/lua/vim/_core/system.lua`, `base_env()`), so a hook would see the fake's address, not the editor's, and T35's mutant 5 would die for a reason that has nothing to do with the relay (`brief-review.md`, T35-3, S1b and S1c). What it sends: `SessionStart` at its start (`startup` for `--session-id`, `resume` for `--resume`); on keys standing for `/clear`, an in-session `/resume <id>` and `/branch`, `SessionEnd` of the old id — `reason` `clear` for `/clear`, `resume` for both `/resume` and `/branch` — then `SessionStart` of the new (`clear`, `resume`, `fork`); on a key standing for `/compact`, `SessionStart` (`compact`) alone; and `SessionEnd` (`prompt_input_exit`) when it exits by keys only — nothing on a hangup or at its lifetime's end, since only the exit by keys was measured to send it. What it runs is recorded, as everything it does is.

## The tests

Each behaviour gets one test, seen failing first:
- `start_session()` passes `--settings` with a `SessionStart` and a `SessionEnd` command hook, before `--allowedTools`, on a new session and on a resumed one; nothing else in the JSON;

- the relay, given a hook's JSON on stdin and an editor's address, notifies that editor of the event, the id, the source or reason and the token, and writes nothing on stdout; given JSON it cannot read, it notifies nothing and exits;

- the session followed is the started id from the start, with no hook run at all (A2);
- a `SessionStart` with the followed id calls nothing back; one with a new id after the followed id's `SessionEnd` calls `on_session_switched` once, naming the session left, and keeps the id for the directory, so the next start resumes it;
- a `SessionStart` with a new id and no `SessionEnd` of the followed id before it — as a `fork` source might send — calls nothing back and keeps nothing (A1);
- a `SessionEnd` alone calls nothing back (A1);
- T19's fallback: the fake with `AINEO_FAKE_CLAUDE_CONVERSATIONS` finding no conversation for the resumed id, then the fallback's new id followed, kept for the directory, and told once through `on_session_switched(<new id>, 'startup', <old id>)` (T35-1, D38);
