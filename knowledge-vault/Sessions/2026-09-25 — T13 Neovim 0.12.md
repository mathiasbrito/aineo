## What was done

- **`plugin/aineo.lua`** (NC2, MR64): `error_line()` strips `ERROR_FRAMING` from the error's first line, and repeats that until nothing more comes off. The list is:
  - `^Lua: `, the words 0.12 wraps an error raised in Lua in;
  - `^Error executing lua: `, 0.11's words for the same;
  - the position `<file>.lua:<n>: `, whose path holds no white space (`'^%S-%.lua:%d+: '`, the correction);
  - 0.12's two positions for its own Lua, `vim/<module>:<n>: ` and `[string "vim/<module>"]:<n>: `;
  - `^Vim:`.

  On 0.12.5 a user whose TermOpen autocommand fails is told `aineo: nvim_exec2()[1]..TermOpen Autocommands for "*": Vim(append):Lua callback: [string "<nvim>"]:3: the user autocommand fails`. The inner `Lua callback:` differs from 0.11's `Error executing lua callback:`; it is not at the line's start, so it stays, and the test states each version's text.
- **`lua/aineo/mcp/editor.lua`** (NC3, C5): `first_line()` became `editor_reason()`. It strips, until nothing more comes off:
  - `^Lua: ` and `^Error executing lua: `;
  - the same three positions.

  So Claude's tool error reads `the editor did not take the report: aineo.report has no environment: call set_report_environment() first` on both versions.
- **`lua/aineo/health.lua`** (NC4, C7): `error_line()` strips two position forms.
  - `<file>.lua:<n>: `.
  - `vim/<module>:<n>: `, which 0.12 gives those of its own modules it names without `.lua` (`vim/_core/system`).
  - It does not strip the `[string "vim/<module>"]:<n>: ` form: nothing inside the check raises from such a module.
  - The "could not run" warning reads `ENOENT: no such file or directory` on both versions. The configuration error shares the function, and its pins stay green.
- **`tests/test_claude.lua`** (NC5, C3): the exit-line case reads `[Process exited 3]` where each version puts it:
  - on 0.11, the buffer's text, through `claude.wait_for_screen`;
  - from 0.12 on, the virtual text of the extmark in the `nvim.terminal.exitmsg` namespace. The default `TermClose` autocommand of group `nvim.terminal` sets it. The check is inline in the test file; `tests/helpers/claude_session.lua` is unchanged.

  The `start_session()` error pin states each version's request framing. `lua/aineo/claude/` is unchanged.
- **`tests/helpers/report_tui.lua`** (NC6):
  - The helper waits, at most 5 s each, for the editor to listen and to finish starting before its first request that loads aineo, and raises an error naming the wait when either does not happen (the correction replaced the fix round's RPC wait: see *Correction*).
  - It answers each Device Status Report query the TUI writes (`CSI 5 n` → `CSI 0 n`), as a terminal would. 0.12's startup therefore no longer waits 100 ms and leaves E1568 in `:messages`.
  - `tests/test_mcp_blocked_editor.lua` gains two cases: the editor loads aineo's report home as it starts (`package.loaded['aineo.report']`), and it starts with no message.
- **`tests/test_entry.lua`, `tests/test_mcp_delivery.lua`**: each states the text on both versions. The delivery text has no framing on either.
- **`doc/aineo.txt`**, inside `*aineo-install*` only: aineo's behaviour was measured on Neovim 0.11.6 and 0.12.5.

- **Neovim frames an error again after a position.** When a Lua function calls an API function that runs Lua (`nvim_buf_call`), the error reads `<caller>.lua:<n>: Lua: …` on 0.12.5 and `<caller>.lua:<n>: Error executing lua: …` on 0.11.6. `lua/aineo/report/buffer.lua:15` does this when it frees the name `aineo://report` held by a buffer the user edited.   - the user, as `aineo: Lua: [string "vim/_core/editor"]:353: nvim_exec2()…`;

  - The first request is still served during startup, so both changes are needed.

## Decisions & reasoning

- **The helper answers the DSR query rather than setting `NVIM_TEST`.** `NVIM_TEST` would hide E1568 and keep the wait it reports. It is also a switch no user's editor has, and this test file is about what a user's editor shows.
- **Both versions' framings are stripped, in `plugin/aineo.lua` and in the relay.**
  - The relay runs on the editor's `v:progpath`, so relay and editor are normally one version. Stripping both avoids a version check in production code.
  - In the relay, the stand-in editor pins each framing on both versions (P1).
  - In the plugin, each framing is pinned only on the version that writes it.
- **The strip repeats until nothing comes off** (the orchestrator's decision 1, adopting the attack's measured fix). A single pass, framing first, leaves any framing that follows a position.
- **A file's position is never looked for past a space** (the correction, adopting the re-measure's measured fix). With the loop, the lazy `'^.-%.lua:%d+: '` ran through the last `.lua:<n>: ` of the line, crossing Neovim's `…Autocommands for …: Vim(append):Lua callback:` and the user's own words.
- **The version branches live in the test files' constants and helpers**, never inside a case: `vim.fn.has('nvim-0.12')` picks the whole expected text. No pattern was widened to accept both.
- **A query split across two reads is not joined.** The first answerer joined one. Its mutant (M13) survived because no run split a query, so the join was removed in `4d35fd8`.
- **Health's pre-existing crash is left** (the orchestrator's decision 2): see *Open threads*.

## Readings for the MVP review

- **NC3 changes v0.1.0's text on 0.11 too** — the orchestrator's reading, for the user to confirm. On 0.11, a report the editor does not take was a tool error reading `the editor did not take the report: Error executing lua: aineo.report has no environment: …`. It now reads `the editor did not take the report: aineo.report has no environment: …`, and 0.12's reads the same.
- **The relay strips a reason's own leading framing** — the attack's trade-off, which the orchestrator accepted. A reason the report home raises that itself begins with `Lua: `, `Error executing lua: ` or a position loses those words: `error('Lua: the report home says so', 0)` reaches Claude as `the editor did not take the report: the report home says so`. Nothing in aineo or in Neovim raises such text. The words are kept anywhere after the start: P2 pins `the reason quotes Lua: and Error executing lua: in its own words`.
- **The plugin strips an error's own leading framing too** — the same trade-off, on the user's side (the re-measure's finding 3). An error whose first line begins with `Lua: ` or `Error executing lua: `, or with a file's position followed by them, loses those words, and `error_line()`'s docstring says so.
  - Pure-string probe of the committed `error_line()`, in the correction: `/home/u/.config/nvim/lua/user/hooks.lua:3: Lua: the user text` → `aineo: the user text`; the same with `Error executing lua: `.
  - At `050bd97`, a TermOpen autocommand in a Lua file raising `error('Lua: the user text')` reached the user as `aineo: the user text` on both versions (the re-measure's input). With the correction it keeps its words: Neovim's framing before the position holds spaces, which the file position no longer crosses.
  - The first round's A5, "the plugin keeps such words", holds wherever the words do not begin the line.

- **Health crashes on userdata `setup()` options — pre-existing, a candidate fix** (the orchestrator's decision 2; the attack's H1).

- **The lazy `'^.-%.lua:%d+: '` cut real words, and the correction bounded it in the plugin and the relay.** It strips up to the first `.lua:<n>: ` anywhere in the first line; the fix round's loop made it strip through the last. The re-measure measured the inputs, on `050bd97`, on both versions: any failing TermOpen, BufFilePre or BufFilePost autocommand defined in a Lua file, through `:Aineo open`, the autostart and the relay.

  The correction's `'^%S-%.lua:%d+: '` never looks for a file's position past a space, and the three pins hold the context and the user's words. **Its trade-off:** a position whose shown path holds a space is no longer stripped — `/Users/John Smith/.config/nvim/lua/claude/init.lua:144: claude.cmd: x` stays whole (pure-string probe of the committed strips).
