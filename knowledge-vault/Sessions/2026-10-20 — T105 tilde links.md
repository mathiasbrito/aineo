## What was done

- **The fix.** `M.with_home_expanded(path)` in `entry/links.lua` replaces a leading `~` that is the whole path or is followed by `/` with `vim.uv.os_homedir()`, after the `file://` conversion and before the absolute-path test; with no home folder the path is left as it is. Only those leading bytes change: `$` and `*` in the rest of the path are not expanded. The warning keeps the text as it was written (`aineo: ~/nope names no file`).
- **Which panes it reaches.** Claude's terminal (double-click, Normal and Terminal mode, and `gx`) goes through `open_link()`. The Report's own double-click goes through `open_drawn_path()` of `report/home.lua`, whose `file_named_by()` read a `~` as written; A522 (the ruling on the spec conflict the first push reported) makes it follow the same rule.
- **One helper.** `links.with_home_expanded()` is the only copy. The report home may require `aineo.config` only (the direction table), so it is not required there: the composition root (`entry/tab.lua`) hands it to the report home as the environment's new optional field `with_home_expanded` (validated as a function; a path is read as written when it is not given). `file_named_by()` applies it, so the underline (`names_file`), the refusal and the opening agree. A new home for the helper would need a direction-table edge for `aineo.report`, which a packet may not add.
- **Help.** `aineo-links` says a path starting with `~/` is looked up in the home folder, and a `~` elsewhere, or `~name/`, is left as written.

## Decisions

- A521 and A522, as written. No D row: it fixes D88's behaviour.
- A bare `~` is handled but cannot come from a pane: the Report's path detection (`looks_like_path()`) needs a `/` or an inner `.`, so `~` alone is never a candidate. It is pinned by a direct call of `open_link('~', …)`, as other entry suites call the composition root's body.
