## What was reproduced first

1. **Which placement lacked the keys row (A645 (2)).** Driven through the real keys (`\w`, `V\w`) in a child Neovim, with screenshots: the head row showed for a Normal insertion and a Visual replacement in the middle of a file, and at its last line. It was missing wherever the preview hung it above the buffer's first line, where Neovim shows virtual lines only in a window scrolled up to them: every proposal for a file of one line (the diff view is drawn when an edit spans the whole buffer) — which is D128's own example, a new file holding only the request — the diff view of an edit starting on line 1, and a stale proposal on line 1 whose marks were cleared. The fix's preview shared the flaw.
2. **Why adding code at the last line was refused (A646 (2)).** Measured on `dev` with well-formed answers: an insertion below the last line, with and without a final line end (`noendofline nofixendofline`), below the only line, and a Visual request on the last line were all accepted as one undo step. What refused was a blank last line, the line one opens to write in, and an empty new file: an answer that writes into that blank line, rather than keeping it and adding below, was refused with "it must keep the cursor's line as it is". D131's blank-line rule is the fix.
3. **Also seen, not changed:** when the anchor line is the window's top line (`zt`), the overlay's rows hang below the line above it, off screen, so the whole proposal is unseen until the window scrolls; a fix behaves the same. Recorded under Open threads.

## What was done, and why

1. **Rows above line 1** (`preview.lua`): a diff whose edit starts on the buffer's first line draws its head and why rows below its old lines, before its new lines; a stale proposal with no marks draws its head row below line 1 when it stood there (`add_rows_above_or_first()`). Elsewhere nothing moves.
2. **Keys per kind**: each proposal kind names its `<Plug>` mappings (`kinds.FIX.plugs`, `kinds.WRITE.plugs`); the preview maps its keys to them and names them in the head row, the stale row and the stale message when no key is mapped. `plugin/aineo.lua` defines `<Plug>(aineo-write-accept|reject|diff)` beside the fix's, acting on the proposal the buffer shows. `aineo.entry`'s `write()` hands written code `\Wa`, `\Wr`, `\Wd`. The keys table lists `\Wa`, `\Wr`, `\Wd` after the fix's keys in "While a proposal shows"; the fix's rows now say "the fix".
3. **The blank anchor** (`write.lua`, `request.lua`, `kept.lua`): where code goes is one of `below_line`, `in_blank_line`, `in_request_lines`; a typed request whose anchor is empty or white space alone asks for one edit whose `old` is that line and whose `new` is the code alone, placed byte for byte; the refusal names the place; the kept key holds the place.
4. **Docs**: help (`aineo-write`, the new `<Plug>` tags, `\vc`'s key list, the cheatsheet's sections), README, health.

## Decisions (the implementer's, within A645 and A646)

- **One set of actions for both kinds of `<Plug>` mapping.** `<Plug>(aineo-write-accept)` and `<Plug>(aineo-fix-accept)` both act on the proposal the buffer shows (there is one at a time, A640); only which key is mapped, and which mapping is named, differs by kind. Rejected: a refusal when the kind does not match, which no user path reaches, since each kind maps only its own keys.
- **The fix's rows in the keys table say "the fix"** ("accept the fix"), the written code's "the written code", so the cheatsheet tells the two pairs apart.
- **An answer for a blank line whose `new` starts with that blank line is not refused**: it is applied as the insertion after it that it is (A643 (4)), which leaves the blank line. The prompt asks for the code alone; refusing a usable answer for a blank line was judged worse.
- **Rows above line 1 are moved, not scrolled to.** Rejected: setting each window's `topfill` so the rows above line 1 show, which any scroll undoes and which differs per window.
