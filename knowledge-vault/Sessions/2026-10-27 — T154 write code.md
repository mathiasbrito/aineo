## What was done, and why

1. **The request** (`aineo.explain.write`). In Normal mode the steering float of T150 opens empty, titled `Write code` (`Write code, reading the project` for `\W`), with no default and no name, so it maps no `R` and remembers nothing: a request is not a steer (A640). `aineo.explain.steer` takes `name` and `default` as optional for this; the deep and fix floats are unchanged. The request sent asks for code below the cursor's line; the line is checked again at send (a buffer that lost it gets one message, nothing is sent). In Visual mode the selected lines, whole lines, are the request (A641), sent at once; blank lines alone are refused with one message.
2. **The prompt** (`request.write_prompt()`): below the cursor, the file, its language, the line, the request as typed, then the rules (one edit whose `old` is that line and whose `new` is that line unchanged followed by the code, in the file's style and indented as the code around it; write only into this file; no edits and a summary when it cannot be done) and the numbered buffer; for selected lines, those lines named as the request, to be replaced, the first line of code indented as the first of them. The answer has the fix's schema, so `answer.fix_in()` reads it.
3. **The placement and its guard.** `placement.place()` places the edit byte for byte, as for a fix; on top of it written code must be exactly one edit of exactly the anchor's lines, and, below the cursor, its new lines must start with the cursor's line as it reads, so nothing outside the request changes (refused with the reason otherwise). A moved `b:changedtick` while it was asked refuses the answer, as a fix's does.
4. **The preview, shared.** The preview's `issue` became a `subject` (a text and the look it is drawn in): the issue in the issue look for a fix, the request on one line of at most 60 characters in a new look for written code (`kinds.WRITE`, `AineoWrite*`, label `write`, accent of `Special`). Accept, reject, the diff view, the read-only buffer, the stale mark and the keys are the fix's code paths; accepting written code says "code written (u undoes it)".
5. **One proposal per buffer.** `fix.replace()` (was the local `replace_fix()`) stops the running request of either kind (`kinds.PROPOSALS`) and rejects what shows; `write.lua` calls it before showing or asking, so a fix and written code replace each other both ways.
6. **Kept code** under `kept.write_key()` (anchor lines, request text, model, effort) with the buffer's whole text, reused at once with a message for the same request on unchanged text; `\vc` drops it with the rest.
7. **Keys, command, settings.** `\w` (`write.model`, `haiku`, no tool, no `--effort`, `write.timeout_ms` 120000) and `\W` (`write.deep_model`, `sonnet`, `--effort write.deep_effort`, `high`, Read, Grep and Glob, `write.deep_timeout_ms` 300000), in Normal and Visual mode, rows of the keys table in a Write section after Fix; `:Aineo write [deep]`, the second subcommand that takes a range (the range refusal now names both); the health check's "Write code" section; help (`aineo-write` and its tags), README.

## Decisions (the implementer's, within A640 and A641)

- **The group is renamed "Explain, fix and write"** (A640 left it open): the cheatsheet's heading then says what the group holds.
- **Asking anew** is changing the request, or `\vc`: the float pre-fills nothing, and a kept proposal is reused only for the identical request text on unchanged text (A640's simplest option). The message says "change the request to ask anew".
- **The request is named in a look of its own** (`AineoWrite`, `Special`'s accent) rather than in the issue look, since a request is not an issue.
- **The accept message** names written code ("code written") instead of "fix applied"; the "no fix is shown" message for `\Va` with nothing shown is the fix's.
