## What was done

**`lua/aineo/send/init.lua`** — a new home, one export, `send()`, requiring `aineo.claude` and `aineo.layout` through their entry points (the direction table allows both). It reads Input (`layout.input_buffer()`), joins its lines with line feeds, removes every control byte — C0 but tab, line feed and carriage return, then C1 — and, when the result holds more than white space and `claude.session_status()` reads `'ready'` at that moment, empties Input with `nvim_buf_set_lines` (which keeps the buffer and its options), then writes `ESC[200~` text `ESC[201~` `\r` in one write. When Input cannot be emptied (not modifiable, a text lock) the clear raises and nothing is written. When the write itself fails — the terminal's stream has closed before Neovim has seen Claude exit — Input's lines are put back and the write's error is raised (correction). Otherwise it writes nothing, keeps Input, and gives one `vim.notify` warning naming the reason.

**`lua/aineo/claude/init.lua`** — one new export, `write_to_session(bytes)`: `nvim_chan_send` to the session's job, raising `aineo.claude: no Claude Code session is running to write to` unless the session runs as `start_session()` counts it (`is_running()`: process alive and terminal not wiped). Nothing else in the file changed.

**Tests** — `tests/test_send.lua` (31 functions, one parametrized two ways: 32 cases after the correction; 30 after the fix round; 19 functions and 20 cases at `b368fb0`), five new cases in `tests/test_claude.lua` (four for `write_to_session()`, one `session_status()` case on the turn screen); helpers `tests/helpers/send.lua` (a 240×42 child, notifications and errors `send()` raises kept as messages, the layout opened around the session's terminal in the same tick as `start_session()`), and in `tests/helpers/claude_session.lua` two new helpers, `received()` and `wait_for_received_after()`, which join the fake's chunks after a byte offset so a case compares exactly what arrived after the send. The fake gains the mode `turn` (screen B of `t6-summary.txt`, answering Ctrl-C as in a turn), its fixture `tests/fixtures/claude/turn-2.1.281.screen` with a header naming its source.

## Decisions & reasoning

- **Remove every C0 control but tab, line feed and carriage return, then every C1 control until none is left** (SD7; widened in the fix round from "every escape byte, then every U+009B" — attack A1). Removing the escape byte leaves no `ESC[201~` and no nested form to rebuild one: the brief review's `ESC[20ESC[201~1~` and `ESC ESC[201~[201~` both arrive as plain text. The C1 controls (U+0080–U+009F, `C2 80`–`C2 9F`; U+009B is CSI) are removed repeatedly, since `C2 C2 9B 9B` becomes `C2 9B` after one pass, and after the C0 pass, since an escape byte between `C2` and `9B` hides the C1 form until it is gone (attack A4). The other C0 bytes go because a control byte inside a paste may reach Claude Code as a key: on the fake, `\3\3` exited an idle Claude and `\3` interrupted a turn; the real CLI was not measured. A lone `9B` byte is left alone: it is a continuation byte of many characters (`😛` is `F0 9F 98 9B`), and an invalid lone one is decoded by a UTF-8 reader as U+FFFD, not as CSI — unmeasured on Claude Code.
- **Empty is judged on the text Send would paste** — after that removal — so an Input of escape bytes and blanks does not send an empty paste whose Enter would submit a draft in Claude's box (the second commit, seen red first).
- **One write, never split** (SD8). A text of 103,423 bytes (1,024 lines of 100 bytes) reached the fake byte for byte after one `nvim_chan_send`: the whole write, 103,436 bytes with the markers and Enter, arrived as 102 chunks of at most 1,022 bytes (the pty's reads), in order, the Enter in the last (`.tests/fixtures/claude-send-long/record.jsonl`, Nvim 0.11.6, macOS). Splitting would add nothing the kernel does not already do, and one write is what the orchestrator measured on the real CLI (23,716 bytes, `t6-summary2.txt` (b)); a 100 KiB text was not measured on the real CLI.
- **Status read last, just before the write.** The checks run in the order Input exists, Input not empty, session ready, so the status that decides the write is read in the same tick as the write. Pinned since the fix round: empty Input behind the trust dialog says "Input is empty".
- **Clear Input before writing, and put it back when the write fails** (fix round, attack A2; the correction, re-measure finding 1). A clear that fails after the write would report failure for a message already sent, and a retry would send it twice; clearing first makes the failure write nothing. `'ready'` implies a running session in the same tick, so `write_to_session()`'s own guard cannot fire after the clear — but `nvim_chan_send()` can raise: when Claude Code's terminal stream has closed before Neovim has processed its exit, it raises `Can't send data to closed stream` (the re-measure: after `jobstop()`, and after a natural SIGKILL in 3 of 3 runs). So Send keeps Input's lines before the clear, writes under `pcall`, and on a failed write puts them back and re-raises the error: Send never loses what the user typed to a write that failed. While the stream is still open, a write into a dead Claude's terminal succeeds without an error and Input is emptied (*Limits*).
- **`write_to_session` raises instead of returning a flag** — `send()` never calls it without `'ready'`, which implies a running session in the same tick, so a call on a stopped session is a caller's error; it raises its own message rather than `chansend()`'s "Can't send data to closed stream".

## Readings for the MVP review

1. **The empty-Input rule** — Input is empty when the text Send would paste (lines joined by `\n`, control bytes removed) holds only Lua `%s` white space (space, tab, CR, LF, VT, FF); a non-breaking space, U+3000 or a zero-width space counts as text (what Claude Code does with such a message is unmeasured). Pinned by the empty, blank-lines, escape-bytes and NUL cases.
2. **No Input** — before the layout first opened, and once Input was wiped, are one case: "aineo: nothing sent — there is no Input; open aineo’s layout to make one" (`layout.open()` makes a new Input then).
3. **`vim.notify` at `WARN` is the channel of every refusal**, once per refusal, and the wording: `aineo: nothing sent — Input is empty`; `… — Claude has not started`; `… — Claude is not ready: it is starting, or a dialog in its window awaits your answer`; `… — Claude has exited`; the no-Input message above.
4. **Send onto a draft** — Send writes only its paste and Enter; the draft Claude's box already holds is left as it is, and the paste joins it; since a paste lands in the box and Enter submits the box (Q1), Claude Code should submit draft and paste as one message — inferred, not measured with a draft on the real CLI. Pinned on the fake's `draft` mode: the bytes after the send are exactly the paste and Enter, no Ctrl-C.
5. **What Send does to the text** — removes every C0 control but tab, line feed and carriage return (NUL, Ctrl-C, BS, Ctrl-U, Ctrl-D, ESC, DEL …) and every C1 control (U+0080–U+009F), because a control byte inside a paste may reach Claude Code as a key — which the fake shows, and the real CLI was not measured; keeps every other byte, tab and CR inside a line included; does not trim leading or trailing blank lines or indentation. Pinned by the every-byte case (fix round).
6. **C1 form** — whether Claude Code ends a paste on `C2 9B 201~` was not measured; Send removes it with every C1 control. A lone `9B` byte is kept (above).
7. **During a turn Send sends** (D14) — pinned on the new `turn` mode: the turn is on screen, the session reads `'ready'` and Send's bytes arrive.
8. **A dead Claude not yet seen** (attack A5; re-measure finding 1) — if Claude Code dies before Neovim has processed its exit, `session_status()` still reads `'ready'`. While the terminal's stream is still open, Send empties Input and writes into the dead terminal without an error; `u` in Input restores the text. Once the stream has closed, the write fails: Send puts Input's lines back and raises the write's error (correction). Listed under *Limits*.
9. **The failed write's error is raised as it is** (correction) — `error(failure, 0)` re-raises `nvim_chan_send()`'s error unchanged, `…/lua/aineo/claude/init.lua:<line>: Can't send data to closed stream`, as a failed clear raises Neovim's own error. Not taken: restoring Input and giving the `exited` refusal's one WARN (the re-measure's design note), which would read better to the user but call a failure a refusal the status did not report. How T7's `\s` shows the raise is T7's.

## Limits

- **R4, accepted with D14** — the session turns `'starting'` 10.8 to 29.5 ms (ten cycles) after a permission dialog's bytes reach the terminal (the re-measure of PR #11, finding 8). A Send inside that window writes its paste and Enter into the dialog, where the Enter would likely pick its highlighted `❯ 1. Yes` — inferred, not measured; what the dialog does with the pasted bytes is unrecorded. The recorded permission dialog's footer is "Esc to cancel · Tab to amend" (`tests/fixtures/claude/permission-dialog-2.1.281.screen`); "Enter to confirm", which this note first cited for it, is the trust and MCP-server dialogs' footer (attack A6). The 11–30 ms is a **lower bound**: it runs from the dialog's bytes reaching the terminal to the status turning, and leaves out Claude Code's own input and render latency (bytes written before the dialog is drawn but read after it is mounted) and dialogs drawn in several writes (the box stays on screen, and `'ready'`, until the write that removes it). The permission dialog numbers its choices (`1. Yes`, `2. Yes, and don't ask again …`, `3. No`): what a pasted digit does there is as unmeasured as the Enter — a `2` could grant a standing permission. The send path does not close this.
- **A second Send soon after a first may be refused by Claude Code's own redraw**: a redraw of the input box reaching the terminal in two writes 20 ms or more apart turns the session `'starting'` for about 1.5 s (the settle). The fake cannot show this — its echo is not Claude Code's redraw (it overwrites the box's lower rule, so a second send to the `ready` fake reads `'starting'` from then on); every case that expects a send's bytes sends once, on a fresh session (the dialog case's second send is refused by design).
- **A dead Claude not yet seen** (attack A5; re-measure finding 1) — `session_status()` reads `'ready'` until Neovim processes the exit. "Read at call time" means as fresh as the last event Neovim processed — the same class as R4. Two variants:
  - the terminal's stream still open (probe P11 of the attack review: SIGKILL, 300 ms with no event processed) — `send()` returned without an error and Input was emptied; the status read `'exited', 137` afterwards. `u` restores Input.
  - the stream closed (the re-measure's P1, `jobstop()` then `send()` in one chunk, and P2, a natural SIGKILL, in 3 of 3 runs) — the write raises `Can't send data to closed stream`. Since the correction, Send puts Input's lines back and re-raises; pinned by "keeps Input and raises when the write fails after Input is emptied".
- **A closing marker split across reads** (attack A3) — the fake reads a write in pieces of at most 1,022 bytes, so for texts of about 1,011–1,015 bytes the closing `ESC[201~` arrives split. The orchestrator measured the real Claude Code 2.1.281 with no model turn (`t6-summary3.txt`, landing in the wave's `evidence/` with the knowledge pass): at 15 of 15 text lengths from 1,006 to 1,020 bytes — the marker at bytes 1,012–1,026 of the one write — the box showed one `[Pasted text #1]` with no stray `201~`, and a double Ctrl-C then exited as keys. Whether the pty actually split the marker between Claude Code's reads in any of those runs is not observable from Neovim.
- **An Enter delivered as a read of its own** (re-measure finding 2) — Send's write stays one write at every length measured (1 byte to 1 MiB, a spy on `nvim_chan_send`), but the fake reads it in pieces of at most 1,022 bytes (this Mac): when the text is 1,010 bytes mod 1,022, the Enter arrives in a read of its own. On a 1,010-byte Send, the fake's `asks` mode received reads of 1,022 and 1 bytes, drew its permission dialog, and the status turned `'starting'`. "Never a lone `\r`" holds for the 9-byte message the `asks` case pins, not at every length. Send cannot place read boundaries; what the real CLI does with a split-off Enter is as unmeasured as the split marker above.
- **Bytes that still pass** (re-measure finding 5) — a lone `9B` byte, overlong encodings, and every other byte from `80` to `FF` outside `C2 80`–`C2 9F` are kept. They are harmless if Claude Code decodes its input as UTF-8, which is unmeasured: it needs the real CLI.
