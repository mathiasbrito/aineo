## What was done, and why

The explain home grows five files, each one concern: `test_window` (the window and its bar, the port `aineo.explain.TestLayout`), `context` (the code around a line), `checklist` (the float of listed tests), `test_writing` (the `\WT`/`\WI` flows) and `new_files` (writing a new file on its first accept). `asking` takes the start of a request that `write` had inline, so the list request shares it instead of copying it; `folders` takes the project folder lookup out of `init`. `write` gains an `anywhere` place (edits wherever they belong, no anchor required, at most 20, placed byte for byte), `brief` parts of the prompt, a float `title`, and `refine()`.

The test layout is a port: `aineo.entry`'s new `test_writing.lua` is the one place that requires `aineo.test_layout` and hands it to the explain home in every order, so the explain home requires no other home and its suites hand it a stand-in (`tests/helpers/fake_test_layout.lua`); the entry suite stands the stand-in in `package.loaded`. After the rebase onto T160 the real module answers in the editor; its `Place` matches A667's shape, and its `correct()` answers whether it kept the correction, which the test window now tells when it did not.

## Decisions (the implementer's, within A673–A679)

1. The test window lives in the explain home, not the layout home: `\WT` and `\WI` open it and write into it, and the layout home may require `aineo.config` alone; it is a split below the source window, which in aineo's layout is the middle column.
2. `describe()` is called with the source's path; T160's `describe()` answers for a source or a test file alike.
3. `\Wp` and `\Wn` are global keys that tell `aineo: this works in a test window` elsewhere, rather than buffer-local maps on a buffer that may show in other windows; their `<Plug>` mappings are `<Plug>(aineo-test-path)` and `<Plug>(aineo-test-next)`, which A678 did not name.
4. The list request runs as a request of the write kind (its working line says `writing code…`), on `write.model` with no tool, as A678 says.
5. The chosen tests, and `\WI`'s code, are asked as code written anywhere in the file: no anchor edit is required, and the cursor moves to the first proposal (A674 "jumped to the first").
6. `\Ws` is mapped while any written code shows, `\w`'s, `\W`'s and `\WW`'s too (A677). A refinement is asked as the first request when no proposal was decided yet, so `\w`'s and `\W`'s placement rules still hold; once some were decided, wherever the code belongs. Showing written code replaces the proposal shown first, so the new code never stands beside the old (the A679 mutant) and the buffer is given back modifiable.
7. A new file waits for its first accept (`\Wa` or `\WA`), then is written with `:write`, its missing folders and the place's companions (empty, only when missing); one already on disk by then (the user wrote it) is left alone.
8. A correction the layout refuses is told once and leaves the test window as it was; the bar drops `new` once its file is written.
