## What was done

- **The names (A538).** `git.names_at(found, ids, done)` runs one `git for-each-ref` with a `--points-at` per commit asked and gives each commit's local branches, then its remote-tracking branches, then its tags, each kind in name order; a remote's `HEAD` and every other reference are left out; an annotated tag names the commit it tags. The pure `names_text()` cuts at three and adds `…`.
- **One decision for both (A538).** `against.sides(filter, against_head, source, resolved)` gives `{ left, right }` for every kind of filter (Session work, Uncommitted, a commit of any list, Landed, a branch, another worktree), for what Enter shows and for what `h` shows (against `HEAD`). A side is a commit with the words saying where it came from, or `working tree`, `empty tree` or `?`. `heading()` and `bar()` render the same sides with the same colours; the bar doubles percent signs.
- **What git alone tells.** `against_read.read()` resolves `HEAD`, a commit's parent (`<id>^`; none for a root commit), and Landed's merge base (`git diff base...tip` compares from that, not from the session's base), one git run after another and then `names_at`, all asynchronous. A failing run leaves its value unread and the side shows its words alone; the next read tries again.
- **Where a base came from.** The sections of other worktrees and of local branches keep `base_origin`: `{ kind = 'reported' }` when `read_effective_base()` chose the reported base (it now says so as a third result), else a merge base with the working branch's name, or with the editor's comparison commit by its id when the working branch gives none. `branch.reported_base` is left as it was: it says a report exists, not that the base is the reported one.
- **The pane.** `files_page()` adds the row (`lines.files_window`'s new `against`); each read of the files list asks `read_against()`, the last answer winning, so the line shows the ids until the names arrive. A diff shown is tracked per buffer (`track_against()`) and its bar drawn into every window showing it (`draw_bar()`), when shown, when the read answers and when F reads the diff again; the bar is a window-local option for the buffer, as the run pane's winbar is. `branch_named()` and `diff_source()` moved above `files_page()`.
- **The suites.** Every suite that pins the files a window lists drops the new second line in its readers (`git_repo.without_against_line()`, `without_against_colours()`, `files_window_line()`, and child-side equivalents) and has its cursor lines one further down; `tests/test_changes_against_pane.lua` owns the new line and the bar.

## Decisions

- D101 and A538, from the brief's spec file; the user's confirmation of the placement ("go with heading + diff bar") is in D101's row as the user's choice.
- **`session start`.** A538's four words (`reported base`, `merge base with <ref>`, `HEAD`, `parent`) have none for Session work, whose base is the commit `HEAD` named when the session began, kept for the Claude Code session. It is not a merge base, not the reported one, and `HEAD` would say the wrong commit once `HEAD` moves. I worded it `session start` and report it; a ruling replaces or keeps the word.
- **Head diffs.** A538 words the diff Enter shows. For `h`'s diff against `HEAD`, the side that is `HEAD` says `HEAD`, the commit side none: `<commit> ↔ <head> HEAD` under a commit, `HEAD ↔ working tree` under Session work, Uncommitted and a worktree, `HEAD ↔ <tip>` under Landed and a branch.
- **Landed's left side is the real merge base**, read with one more git run, since `git diff base...tip` compares from it; the session's base would be wrong once the working branch was rebased.
- **A comparison commit is named by its abbreviated id**: A538 says "the ref or commit it was taken against" and the comparison commit is a commit, not a ref.
- **The existing suites were adapted through their readers**, not by editing hundreds of expected lists: a suite that pins files has no business pinning an `Against:` line whose ids differ per repository.
- **Heading read after every files read.** The line is asked for again with each read of the files list rather than only when its filter changes: `HEAD` moves under Uncommitted without the filter changing. It is 2 or 3 git runs, off the main loop.

## Open threads

- **A538's words for Session work.** `session start` is mine; the plan note records A538 as the orchestrator wrote it and T113's row says so.
- **Names of a kept diff** do not change when a branch moves: the bar of a kept diff says what it compared when it was read, and its names refresh only when the diff is read again. The files window's heading reads them again when a branch or tag moves (A543).
- **A nested annotated tag** (a tag of a tag) is not matched to its commit by `names_at`, which reads one level of peeling.
- **`reported_base` and `base_origin` overlap** on the branch section; folding `reported_base` into `base_origin` is a clean-up for a packet of its own.

## Fix round (A543, the attack review of PR #310)

Five rulings, each test first and seen red first.

- **The bar from the worktree the diff is read from.** A file of another worktree carries two copies of that worktree: the filter's, from the commits window's last read, and the entry's, from the files window's fresh read. The diff reads the entry's, the heading had been moved to it, the bar had not, so after the merge base moved the bar named a base the diff did not use. `filter_read_in()` gives the heading, the bar and the read of the bar's names the same worktree. Red: the case with the commits window frozen as the heading's case freezes it, the bar naming the old merge base.
- **Names read again when a reference moves.** `follow_change()` calls `read_against()` when the branch moved or a reference was written. Red: two cases, `dev` moved off the base (the name stayed) and a tag made while the pane is open (never named).
- **No stale id while a read is pending.** `against.kept_while_reading()` keeps an earlier read's names, which belong to ids, and none of its commits; `read_against()` applies it before the heading is drawn (the `show` callback now reads, then draws) and `write_reread()` applies it to the bar F reads again. Red: the heading under Uncommitted after a commit, and the bar after F, both held with the names read pending, still named the old HEAD. The pre-existing F case ("HEAD that moved is told") passed on a stale bar because it waited the stale bar out; it now holds the names read, asserts the words alone, then releases the read and asserts the new HEAD and its names.
- **`Against: reading…`** for a local branch the pane has not read yet (`sides()` returns nil, `heading()` and `bar()` say `reading…`), instead of `empty tree → ?`.
- **Only a remote's HEAD left out of the names.** The names read asks git for the symbolic target (`%(symref)`) and leaves out the references that have one; `topic/HEAD` and `v/HEAD` are named.

The help and the README say that the names are read again when a branch or tag moves, that a pending side says its words alone, and that an unread branch says `reading…`.
