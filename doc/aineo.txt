1. INTRODUCTION                                                        *aineo*

aineo turns Neovim into a console for Claude Code. Claude Code's own
interactive CLI runs in a terminal on the left; on the right, the Agent
Report shows what Claude says it is doing, above an Input buffer where you
write your next message. Files you open land in a column between the two.

Every command sits behind one prefix key, `\` by default, in Normal mode (and
most behind its twin in Terminal and Insert mode, below):
`\s` sends Input to Claude, `\o` opens or restores the layout, and `\r`, `\i`
and `\c` move to the Report, Input and Claude — `\c` in Terminal mode, so
that what you type next goes to Claude, unless Claude Code has exited.
`\tcn` hides or shows the line numbers of Claude's window. `\S` lists the
sessions Claude Code lists for the folder and opens the one you pick in a new
tab, or moves to the tab that has it (|:Aineo-sessions|). `\N` starts a new
Claude Code session: on a new id once Claude Code has exited, where `\o`
resumes the last, and with `/clear` while it runs (|:Aineo-new|). `\pa`,
`\g` and `\pt` switch the right column between the agent pane, the Report
over Input, the changes pane, and a shell's terminal, each filling the column,
and move to the Report, to the changes pane's commits and into the shell, in
Terminal mode (|aineo-panes|). `\x` asks for a command and runs it in the
folder, in a terminal of the run pane, a stack of the services you run while
you develop, and `\X` adds a shell to that stack (|aineo-run|). `\e` shows
the explorer, a tree of the folder Claude works in, and moves into it
(|aineo-explorer|). `\T` opens a
tab page with a Claude Code
session of its own, `\1` to `\9` move to the tab page of that number, and
`\Q` closes the current tab (|aineo-tabs|). `\d` closes the diff the changes
pane shows in the middle column, from any window of the tab (|:Aineo-diff|).
`\f` finds a file under the folder Claude Code works in and opens it in the
middle column, from any window of the tab but a floating one (|aineo-find|).
`\z` zooms the window of the right column the cursor is in, to the column's
whole height, and gives the heights back when pressed again (|aineo-zoom|).
`\Z` zooms the window the cursor is in to the whole tab page, every other
window shrinking to a sliver, and gives the sizes back when pressed again
(|aineo-zoom-full|).
`\O` shows the office over the right column, an animation of your Claude Code
at work (|aineo-office|).
In Visual mode, in Input, `\s` sends the selection alone and removes it from
Input (|aineo-v_\s|).

In Terminal mode and in Insert mode, `<C-\>` followed by the same letters
does the same: `<C-\>i` moves to Input, `<C-\>r` to the Report, `<C-\>c` to
Claude, `<C-\>pt` into the shell, `<C-\>x` to run a command, each after
leaving the mode you were in (|aineo-terminal-keys|).

aineo answers none of Claude Code's questions: its permission prompts, its
trust dialog and every other dialog are yours to answer, in its terminal.
aineo allows three tools of its own without asking, the report tool,
`announce_work` and `run_output` (|aineo-report|, |aineo-run-tools|), and
nothing else: Claude Code asks you before every run or stop of a process.

2. REQUIREMENTS AND INSTALLATION                               *aineo-install*

Requirements:
- Neovim 0.12 or later. aineo is tested on the newest Neovim release,
  0.12.5.
- Claude Code, the `claude` command, installed and signed in. aineo's
  behaviour was measured on Claude Code 2.1.281; the resume of Claude's
  session, and the new session that takes the place of a resume Claude
  Code has no conversation for (|aineo-claude-session|), on 2.1.283; how
  Claude Code tells of a session switch, on 2.1.292.
- git 2.36 or later, the `git` command, for the changes pane
  (|aineo-changes|). aineo is tested with git 2.50.1.
- Optional: a file picker, snacks.nvim, fzf-lua, telescope.nvim or mini.pick,
  for `\f` (|aineo-find|). With none installed `\f` lists the files through
  |vim.ui.select()|.

With lazy.nvim, load aineo at startup, so that its autostart can run
(|aineo-autostart|): >lua
    { 'mathiasbrito/aineo', version = '*', lazy = false }
<
`version = '*'` takes the newest release tag (`vX.Y.Z`). The next start of
Neovim clones aineo by itself, and `:Lazy update` moves it to a newer release
when one is tagged. To stay on one release, give a `tag`, such as
`tag = 'v0.2.53'`, in place of `version`. To get the same commit on another
host, commit lazy.nvim's `lazy-lock.json` with the rest of your configuration
and run `:Lazy restore` there.

aineo works without a `setup()` call. To configure it, see
|aineo-configuration|; then run `:checkhealth aineo` (|aineo-health|).

3. THE LAYOUT                                                   *aineo-layout*

The layout fills one tab page with three windows, and a file column between
the two sides while a file or a diff is open; the right column's two show one
pane at a time, here the agent pane, with the file column open:

    +--------------------+--------------------+--------------------+
    |                    |                    |    Agent Report    |
    |    Claude Code     |    File column     |                    |
    |    (terminal)      |    a file, or a    +--------------------+
    |                    |    diff of one     |       Input        |
    +--------------------+--------------------+--------------------+

The right column's five panes, each behind a key and each filling the
column; the fifth, `\e`, is the explorer, a tree of the project's folders
(|aineo-explorer|):

     \pa  agent        \g  changes        \pt  terminal    \x  run, \X  shell
    +--------------+  +--------------+  +-------------+  +--------------+
    | Agent Report |  | files        |  | your shell  |  | vite         |
    |              |  |  * M auth.lua|  |             |  |              |
    |              |  |    ? notes.md|  | $ _         |  +--------------+
    +--------------+  +--------------+  |             |  | api          |
    | Input        |  | commits      |  |             |  |              |
    |              |  | Uncommitted  |  +-------------+  +--------------+
    +--------------+  | Session work |                   | shell        |
                      | a1b2c3 Fix.. |                   |              |
                      +--------------+                   +--------------+

- Claude Code's terminal takes the left half of the columns.
- The Agent Report, `aineo://report`, takes the top of the right column:
  two thirds of its rows by default (|aineo-config-layout.report_height|).
  It is read-only to you.
- Input, `aineo://input`, takes the rest: a scratch buffer, left out of
  `:ls` and `:bnext`, where you write what Send gives Claude (|aineo-send|),
  kept as a draft until you send it (|aineo-draft|).
- The changes pane shows in the same two windows in their place, and a
  shell's terminal, or the stack of the run pane's terminals, takes the
  whole column in place of both (|aineo-panes|).

The Report and Input wrap long lines between words, a wrapped line keeping
its indent ('wrap', 'linebreak', 'breakindent'), whatever your own settings.
In the Report a wrapped line continues under the `[` of its `[status]`, or
under an item's text (|aineo-report|).
Opening or restoring the layout sets this again: `\o`, or `\r`, `\i` or `\c`
when their window is gone, and so does `\pa`, `\r` or `\i` showing the agent
pane again. A `:setlocal nowrap` in either lasts until then. Claude's
terminal, the changes pane, and a file shown in or split from those two
windows, keep yours.

Opening the layout closes the tab's other windows (floating ones stay); their
buffers stay loaded. The cursor starts in Input's window, which shows the
changes pane's commits instead when the layout is opened anew while the
changes pane shows, and in the shell's window while the terminal pane shows,
which has no Input window (|aineo-panes|). The Neovim startup buffer becomes
Input; a file the current window shows stays, as the file column.

Panes ~
                                                                 *aineo-panes*
The right column shows one of five panes, each filling its whole height: the
agent pane and the changes pane in two windows, switched in place (the same
two windows, at the same sizes, show the other pane's buffers), the terminal
pane and the explorer pane in one, and the run pane in one window for each
process.

- The agent pane: the Agent Report over Input, as the layout opens.
- The changes pane: `aineo://changes-files` in the Report's place, over
  `aineo://changes-commits` in Input's. The commits window lists
  Uncommitted, Session work and the session's commits, and the line under
  its cursor decides which files the files window lists; each other
  worktree of the repository has a section of its own in the commits
  window (|aineo-changes|). Each is a scratch buffer, read-only to you;
  `:edit` there writes its list again. A buffer of yours under either name,
  such as one a restored session made, gives the name up: it is wiped out,
  or kept unnamed when you changed its text.
- The terminal pane: a shell's terminal alone in the right column, which it
  fills from top to bottom: the Report's window takes the whole column, and
  Input's window is closed while the pane shows, Input kept as it is. The
  shell is your 'shell', run in the folder aineo started in, whatever `:cd`
  or `:tcd` says since, with `$AINEO_CHILD` set in its environment, as in
  Claude's terminal. Each tab has a shell of its own (|aineo-tabs|).
- The run pane: the processes you run, each in a terminal and a window of its
  own, stacked from the top of the column to the bottom (|aineo-run|).
- The explorer pane: `aineo://explorer`, the tree of the folder Claude works
  in, alone in the right column, Input's window closed as under the terminal
  pane (|aineo-explorer|).

`\pa` (|:Aineo-pane|) shows the agent pane, `\g` the changes pane, `\pt`
the terminal pane, `\x` the run pane and `\e` the explorer pane, moving the
cursor into its tree; the pane already shown stays as it
is (the changes pane is read again, and `\g` in it switches its views,
|aineo-changes-s|), unless one of its windows shows the other
pane's buffer there, as a refused switch or you can leave it (the commits
buffer in Input's window, say): they then show the pane's own buffer there.
Either way the cursor moves into the pane: into the Report under the agent
pane, into the commits window under the changes pane, where `j` and `k`
choose the filter, and into the shell under the terminal pane, in Terminal
mode, as `\c` enters Claude's prompt: what you type next goes to the shell.
From another tab page they switch the pane in the layout's tab page,
restoring the layout there first when one of its windows is gone, and move
you there. `\r` and `\i` show the agent pane first, then move to the Report
or Input, the terminal pane and the run pane giving way to it too, which
opens Input's window again, unless you had closed it before `\pt` or `\x` and
asked for the Report (`\pa`, `\g` and `\i` open it); `\c` and `\tcn` leave the
pane as it is. Send sends Input while the changes pane, the terminal pane or
the run pane hides it (|aineo-send|).
When a window will
not take its buffer — 'winfixbuf' is set there, say, or you are in the
command-line window — aineo tells you why, once, and gives each window back
the buffer it showed. A window that will not take that one back either
keeps the other pane's buffer; `\pa` or `\g` then shows its pane in both
windows.

The shell lives until it ends: `\pa`, `\g`, `\r` and `\i` hide it and leave
it running, and `\pt` shows the same terminal again, with its output and its
cursor line, starting nothing. `\pt` starts a shell only when the tab runs
none. When the shell ends, by `exit` with any status, or when you wipe its
buffer with `:bdelete!` or `:bwipeout!`, its buffer is gone and the agent pane
shows again, the Report back in its window and Input in a window below it,
at the Report's share, with its draft and cursor as they were; the cursor goes
to the Report when it was in the shell's window. A window of the layout you
had closed stays closed then, Input's included when you closed it before
`\pt`. When 'shell' names a program that is not
executable, `\pt` tells you so, once, and changes no pane. Closing a tab stops
its shell (|aineo-tabs|).

The Report and Input are kept while hidden, with Input's text and its draft.
A buffer shown again comes back as it was scrolled. When a report arrived
while the agent pane was hidden, the Report's cursor is on its last line,
where an arriving report puts it, once the agent pane shows again with the
Report in its window — by `\pa`, `\r`, `\i` or `\o`.

aineo keeps the pane shown until the editor quits: `\o` restores the layout
with it, and so does the layout opened anew once its windows were closed;
the terminal pane is kept while its shell lives, and the run pane while a
process of it remains.

Run pane ~
                                                                   *aineo-run*
`\x` (|:Aineo-pane|) runs a command in the right column, which the run pane
takes whole as the terminal pane does, with Input's window closed and Input
kept as it is. Each process has a terminal and a window of its own. The
windows are stacked from the top of the column to the bottom at equal heights
(a row more for the first ones when the rows do not divide), the oldest at
the top and the newest at the bottom. The winbar of each window names the
command and the state of the process, `sleep 30 — running` or `sleep 30 —
exited 1`. Each window starts at the end of its output and follows it, as a
terminal window does while its cursor is on the last line; a window you
scroll up in Normal mode stops following.

What `\x` does depends on where the cursor is:
- With no process in the tab, or with the cursor in one of the run pane's
  windows, it asks for a command (|vim.ui.input()|, completing shell
  commands), and runs it in a terminal that joins the bottom of the stack.
  An empty answer or Esc starts nothing, and with no process the pane is not
  shown. The cursor moves to the new window, in Normal mode: press `i` to
  type to the process. With the cursor in the stack, the windows you closed
  with `:q` come back first.
- With processes running and the cursor anywhere else, it shows the run pane
  and moves the cursor to the bottom window, asking nothing.
`\X` (|:Aineo-run|) adds a shell, your 'shell', to the bottom of the stack
instead, asking nothing; the cursor goes into it in Terminal mode, and its
winbar says `shell`. A shell that exits with status 0 is wiped by Neovim and
leaves the stack; one that exits otherwise stays with its status, like any
other process.

A command runs through your 'shell' (the words of 'shellcmdflag' and the
command after it), in the folder aineo started in, whatever `:cd` or `:tcd`
says since, with `$AINEO_CHILD` set in its environment, as the terminal pane's
shell is. A shell that is not executable, or a folder that is gone, is told
once, and nothing starts or shows.

The processes live until they end or you stop them. `\pa`, `\g`, `\r` and `\i`
hide the stack and leave them running, and `\x` shows them again with their
output. A process that ends keeps its window and its output, its winbar
saying `exited` and its status, until you close the window, and then it
leaves the stack; with the last one gone the agent pane shows again. To stop a
process press Ctrl-C in its terminal, which leaves the window with its status
shown, with what is left of its group stopped, or run `:bdelete!` on its
terminal, which stops it with its children and takes it out of the stack.
`:bdelete!` reaches the process group alone: a job that an interactive shell
(`\X`, or a command run under 'shellcmdflag' with `-i`) started in a group of
its own, and that ignores the hangup, outlives it, since Neovim has freed the
shell's job and hung up its terminal before aineo can find what runs below
the shell; a quit, `\Q` and the close of a tab page do reach it while the
shell is still there. A job that outlives its shell is reached by none of
them, a quit included, since no code can find it: a command that runs
`set -m` and is then stopped with Ctrl-C, and the job of a `\X` shell that
exits (`sleep &` and `exit`, under sh or bash) are such. zsh hangs up its
jobs when it exits, by default. Closing the window of a process that runs,
with `:q`, only hides it: it runs on and comes back with the next `\x`. When
the screen has no room for another window, the process runs on, hidden, and
aineo says so. Each tab has a stack of its own (|aineo-tabs|). Processes are
not started again at the next start.

Quitting stops them. Before `:qa`, `:q` in the last window, `:wq` or `:x`
quits Neovim with processes running, aineo asks once, listing the commands:
`aineo: 2 processes will be stopped (npm run dev, cargo watch) — quit?`, with
Quit and Cancel. Cancel keeps Neovim open, as it was. A quit you typed with a
bang for this very quit, `:qa!` or `:q!` on the last window, stops them
without asking; any other quit asks, `ZZ` and `ZQ` and a quit run by a
mapping or by Lua among them, and so does one after a `:q!` you typed earlier
for another purpose. `\Q` on a tab that runs processes asks the same, with
Close and Cancel, and Cancel keeps the tab. Every process is stopped with its
children: a termination signal to its process group and to what its shell
started below it, and a kill to what has not ended within a second and a
half, at a quit, at `\Q` and when the tab page closes (|aineo-limits|).

Explorer pane ~
                                                              *aineo-explorer*
`\e` (|:Aineo-pane|) shows the explorer in the right column, one window over
the column's whole height, as the terminal pane shows, and moves the cursor
into it: a tree of the folder Claude works in, `aineo://explorer`, read-only
to you. `\pa`, `\g`, `\pt` and `\x` swap it out as they swap each other, and
`\z` and `\Z` zoom it as any window of the column. Each tab has its own
explorer, whose folds, toggles and filter last as long as the tab.

    ~/project  ·  ignored hidden  ·  dotfiles shown
    ▾ • lua/
      ▸   aineo/
        M init.lua
    ▸   tests/
        .gitignore
      ? notes.md

The first line names what the tree shows and the toggles, and the filter
when there is one. Folders come first, then files, each alphabetically,
`▸` before a folded folder and `▾` before an unfolded one. In a repository
git's mark sits before a file's name: `M` modified, `A` added, `D` deleted
(a file gone from disk still shows, with its mark), `R` renamed, `T` its
type changed, `?` untracked; a folder holding a change, at any depth, has
`•`. A submodule, and a repository nested in it, is a folder listed from
disk as it unfolds (|aineo-limits|). What git ignores is hidden, dotfiles
show, and `.git` never does, a folder or a file. A name holding a control
character shows quoted, as the changes pane shows such a path. While the
explorer shows, the tree is read again whenever the repository changes (a
file written, a commit, a checkout), the folds, the filter and each
cursor's entry kept; hidden, it watches nothing, and reads the tree again
as it shows.

Outside git the tree lists a folder, one level, as you unfold it, with no
mark; `R` reads it again.

The keys of the tree, in Normal mode, in its buffer alone:

    `l`        unfold a folder, or fold it again
    `<CR>`     unfold or fold a folder; on a file, open it in the file
             column and move the cursor there, as a link opens
             (|aineo-links|): a text file in aineo, anything else with
             your system; a deleted file, or one that is a folder on
             disk, opens nothing, and aineo says why
    `h`        fold an unfolded folder; on a file or a folded folder, fold
             the folder that holds it and move to it
    `@`        paste `@` and the path of the entry under the cursor, from
             the folder shown, a folder's with a `/`, then a space, into
             Claude Code's prompt, with no Enter, the cursor staying in
             the tree; while Claude is not ready it pastes nothing and
             tells you so, once (|aineo-send|)
    `I`        show what git ignores, or hide it again; outside git it
             tells you, once for the tab, that nothing is ignored there
    `H`        hide dotfiles, or show them again
    `f`        ask for a filter (|vim.ui.input()|): only the files whose
             path from the folder shown holds it, ignoring case, show, in
             their folders, all unfolded; a line says so when none does;
             an empty answer clears it
    `R`        read the tree again
    `s`        pick the worktree or branch to show alone, as `s` in the
             changes pane does: it is the same pick (|aineo-changes-s|)

The current file: when the file column shows a file under the folder
shown, the tree unfolds the folders above it and highlights its line
(|hl-AineoExplorerFollowed|, linked to |hl-Visual|); the cursors stay where
they are. A file elsewhere changes nothing.

One pick for both panes: what the explorer shows follows the worktree or
branch the changes pane shows alone (|aineo-changes-s|), picked with `s` in
either pane and remembered for the Claude Code session as that pick is. A
worktree shows that worktree, and so does a branch checked out in one; a
branch no worktree has checked out shows the folder Claude works in, the
first line saying the branch has no folder on disk; the reported work shows
the first worktree or branch it shows alone. Files open for editing in the
worktree shown.
The changes pane's default view (`\g` in that pane) shows the folder Claude
works in again. A worktree shown that is gone from disk gives way to the
folder Claude works in, and aineo tells you once.

The tree shows in colour. A file git sees changed has its mark and its name
in the group the changes pane gives that kind of change, the groups `\g`
shows its files in (|hl-AineoChangesAdded|, |hl-AineoChangesModified|,
|hl-AineoChangesDeleted|, |hl-AineoChangesRenamed|,
|hl-AineoChangesTypeChanged|, |hl-AineoChangesUntracked|), so that the
colours you give those groups apply to both panes. A folder's sign and name
show in |hl-AineoExplorerFolder|, and the `•` of a folder holding a change in
|hl-AineoExplorerChanged|. An entry git ignores, shown by `I`, shows whole in
|hl-AineoExplorerIgnored|, its own mark's colour not applied. Each of the
explorer's groups is a default link, which a colour scheme or you may
replace.

                                                     *hl-AineoExplorerChanged*
AineoExplorerChanged	The `•` of a folder holding a change, linked to
			|hl-AineoChangesModified|.
                                                      *hl-AineoExplorerFolder*
AineoExplorerFolder	A folder's sign and name, linked to |hl-Directory|.
                                                    *hl-AineoExplorerFollowed*
AineoExplorerFollowed	The line of the current file in the tree.
                                                      *hl-AineoExplorerHeader*
AineoExplorerHeader	The tree's first line.
                                                     *hl-AineoExplorerIgnored*
AineoExplorerIgnored	An entry git ignores, whole, linked to |hl-Comment|.

The explorer opens, renames and deletes no file. See |aineo-limits| for what
it does not show.

Zoom ~
                                                                  *aineo-zoom*
`\z` (|:Aineo-zoom|) zooms the window of the right column the cursor is in,
under any pane: it takes the rows the column's other windows can spare, which
is the column's whole height, and they shrink to the least height Neovim gives
a window, 'winminheight' lines (one by default; none where it is 0). Their
winbars and status lines stay, so each still says what it shows: a run pane
window, whose winbar takes a row, keeps the winbar and one line of text. Rows
come from the right column alone: a window across the whole width below the
layout, the quickfix list say, and Claude's window keep their heights. `\z`
again gives every window the height it had when you zoomed, a resize you made
by hand before it included, not the layout's own proportions.

The zoom stays with the window it began in while the cursor goes elsewhere, as
tmux's zoom does, so that you can look into Claude's window or the file column
and come back. `\z` pressed in another window of the column moves the zoom
there; `\z` in the zoomed window ends it. With the cursor in none of the
windows aineo shows in the right column — Claude's window, the file column, a
tab page that is none of aineo's, or a window you split off the column by hand
(`:split`) — `\z` changes nothing and tells you once so. A window split off by
hand is outside the zoom: it neither changes the zoom nor ends it, and `\z`
there does not zoom it.

The zoom ends by itself, the windows given back the heights they had, when
another pane shows (`\pa`, `\g`, `\pt`, `\x`, `\e`, and `\r` and `\i` when
they show the agent pane) and when a process joins the run pane or leaves its
stack, which changes the windows of the column. Asking for the pane already
shown — `\pa` under the agent pane, `\x` under the run pane when it only
moves the cursor into it — keeps the zoom; a `\x` that starts a process ends
it, as any process joining the stack does. When you close one of the
column's windows, the zoom ends and the layout puts its proportions back, as
it does for any closed window. The terminal pane's one window, and the
explorer pane's, fill the column already, so `\z` there changes nothing
visible and tells you nothing; it still toggles, and ends as the pane
changes.

When the editor is resized, the zoom stays: the zoomed window takes the rows
the column gains or loses, and the others stay at their least height. `\z`
then gives back the heights recorded when you zoomed, scaled to the rows the
column holds now, proportionally, with the last window taking the rows that
remain; with the same rows as when you zoomed they come back exactly. `<C-w>=`
while the run pane is zoomed equalizes the stack on screen but not the zoom:
it stays on, and the next `\z` gives back the recorded heights, not the equal
ones.

Full zoom ~
                                                             *aineo-zoom-full*
`\Z` (|:Aineo-zoom-full|) zooms the window the cursor is in to the whole tab
page: every other window shrinks to the least size Neovim gives a window,
'winminwidth' columns or 'winminheight' lines (one of each by default), and
the zoomed window takes the rest. The others stay open and visible as
slivers, their winbars and status lines kept. It works in any window of an
aineo tab page that does not float: Claude's window, the file column, a window
of the right column under any pane, or a window you split off by hand
(`:split`). In a tab page that is none of aineo's, or in a floating window,
`\Z` changes nothing and tells you once so.

`\Z` again gives every window the size it had when you zoomed, a resize you
made by hand before it included, unless a window opened or closed meanwhile —
the file column when Claude opens a file, the quickfix list, a split of the
zoomed window: the sizes recorded no longer fit, and the layout's proportions
are put back instead, the new windows keeping the size they have. `\Z`
pressed in another window moves the zoom there; `\Z` in the zoomed window ends
it. `\z` (|aineo-zoom|) pressed with the cursor in a window of the right
column ends the full zoom first and then does what it does; a `\z` zoom that
was on before the full zoom is on again once it ends. A `\z` that would change
nothing leaves the full zoom as it is.

The full zoom stays with the window it began in while the cursor goes
elsewhere, as `\z`'s does. A window you split off by hand takes at least
'winwidth' columns as you enter it, as Neovim does for any window; aineo's own
windows keep their sizes. It ends by itself, every window given back the size
it had, when another pane shows and when a process joins the run pane or
leaves its stack, as the zoom of `\z` does (|aineo-zoom|), and when the
terminal pane's shell ends or its terminal is wiped and the agent pane shows
in its place. When the zoomed window closes, the zoom ends and the layout puts
its proportions back; when another window closes, the zoom stays.

When the editor is resized, the zoom stays: the zoomed window takes the
columns and rows the tab page gains or loses. `\Z` then gives back the sizes
recorded when you zoomed, scaled to the editor's size now, the last window of
each row and column taking the cells that remain; with the same size as when
you zoomed they come back exactly.

The agent's run tools ~
                                                             *aineo-run-tools*
Say "run the backend" to Claude Code and its agent can start the command in
this stack, through three tools of aineo's server, `run`, `run_output` and
`run_stop`. The tab whose Claude Code makes the call is the tab that acts: the
start token of the call routes it, as it routes `announce_work`
(|aineo-report|), and a call that no tab of the editor runs is answered `not
taken`, as an error. The agent is told, in what aineo appends to Claude Code's
system prompt and in each tool's description, to run or stop a process only
when you explicitly ask it to, and never on its own initiative. Instructions
cannot guarantee that, so the gate is Claude Code's permission prompt: `run`
and `run_stop` are not allowed without asking, and aineo marks them in the
tool list (`_meta["anthropic/requiresUserInteraction"]`) so that Claude Code
asks you for every call, showing the command, even in its auto and
bypass-permissions modes, and offers no "don't ask again" for them; an allow
rule that matches them does not skip the prompt either. In `dontAsk` mode,
which never prompts, the call is denied. The marker was read from Claude Code
2.1.302's program, not run. `run_output` only reads, and is allowed without
asking.

`run` {command, name?, directory?} starts `command` through your 'shell', as
`\x` does, at the bottom of the stack, and answers at once without waiting for
it to end. The run pane is shown, in the tab page you are in, and the cursor
stays where it is; aineo tells you once, `aineo: started backend in the run
pane`. In another tab page the layout is left as it is, and the pane lists the
process the next time it is shown. `name`, what `run_output` and
`run_stop` call the process and the winbar shows, is the command's first word
(without its control characters) when not given, and a name the stack holds
already, a process that ended included, gets `-2`, `-3`: a command called
`shell` becomes `shell-2` beside the `\X` shell. `directory` is the folder
aineo started in when not given, and is refused unless it is that folder or a
worktree of its repository, as `git worktree list` gives them; a relative one
is taken from the folder. Nothing else is accepted: a subfolder, or a folder
whose name only begins like a worktree's, is refused. A `command` is at most
16384 bytes and holds no control character but the tab and the line feed (DEL
and U+0080 to U+009F are refused too); the other arguments are strings of at
most 4096 bytes, and `name` and `directory` hold no control character at all.

`run_output` {name, pattern?, exclude?, ignore_case?, last?, after_line?,
context?} reads what a process printed, so that the agent reads only what it
needs. There is no limit but the one the agent chooses: it is told to filter
first to keep its context small, keep `last` small, and then follow with
`after_line`.
- `pattern`: only the lines that match are read; every line when not given.
- `exclude`: the lines that match are not read, `DEBUG` for example, and not
  as context either.
- `ignore_case`: true when not given, for `pattern` and `exclude`.
- `last`: how many of the matching lines are read, the last ones; 40 when not
  given, with no maximum. How many earlier ones were left out is said.
- `after_line`: only lines numbered after it are read; the `total` of the
  answer before, to follow a process.
- `context`: lines read around each match, once where they overlap, those
  that are not matches marked with a dash instead of a colon; no maximum.
`pattern` and `exclude` are Vim regexes, taken very magic: aineo puts `\v` in
front (|/\v|). `error|warn`, `(GET|POST) /api` and `\d{3}$` work as written,
and `<` and `>` are word boundaries. The characters `= @ % & ~ {` are
operators there, which other regex flavours take as themselves, and must be
escaped with a backslash to match themselves: `level\=error`, `\~/project`,
`a \&\& b`; written bare, `level=error` matches nothing and `~` is the last
substitute string. Two more differences from PCRE: lookarounds are written
`(x)@=`, `(x)@!`, `(x)@<=` and `(x)@<!`, and there is no `(?i)`, so
`ignore_case` takes its place. A regex that does not parse is answered with
the editor's error, as an error. The matching of one call is stopped after 2
seconds in all, and answered as an error that names the field and suggests a
simpler pattern; nothing partial is read. Any other error of the search, as
the engine giving up on memory early, is answered as the editor words it. The
time is bounded, the volume is not: `last`, `context` and the lines of an
answer have no limit. The search runs in a scratch copy of the rows with the
editor's autocommands ignored, so a pattern may span rows with `\n`, and a
positional atom such as `\%23l` counts the rows of the output, from 1.

The answer starts with `backend: running; 120 lines in total` (or `exited 1`),
then the numbered lines, `12: text` for a match and `13- text` for context,
`--` between lines that do not follow one another. aineo cuts no line, but the
terminal wraps them: each line is a row of the process's terminal, from 1,
without the empty rows the terminal pads its last screen with. A line longer
than the terminal is wide spans several rows, no one of which holds it whole
for a pattern without `\n`, and a resize of the pane (showing the stack
narrows its terminals, a wider pane widens them) or the 'scrollback' limit
renumbers the rows: once the output outgrows 'scrollback' Neovim drops the
oldest rows and the numbers shift. `after_line` is valid only while `total`
has not dropped; when it is past the last line the answer says the rows were
renumbered, and the agent is told to read again without it. A progress bar
that redraws itself is several rows.

The tool reads every process of the tab's stack but the interactive shell of
`\X`, whose screen may hold what you typed and which it refuses. A command you
started with `\x` or the agent started with `run` is read even when it is an
interactive program (`sh -i`, `python`, `psql`): what its screen shows, and
what you type into it, can be read without asking. A name that two processes
have, as two `\x` runs of one command do, is refused rather than guessed.

`run_stop` {name} stops the process as `:bdelete!` does, with its children,
and takes it out of the stack (|aineo-run|, |aineo-limits|).

Tabs ~
                                                                  *aineo-tabs*
aineo can hold several Claude Code sessions in one Neovim, one in each of
several tab pages. A tab, in aineo's sense, is a tab page with the layout
above in it. Every tab has a Claude Code, a Report, an Input and a changes
pane of its own, and they follow that tab's session alone
(|aineo-claude-session|): a `/clear` in one tab's Claude Code changes that
tab's Report, Input and changes pane, and no other tab's. Every tab has its
own shell too, when you start one with `\pt` (|aineo-panes|), and its own
stack of processes, when you run some with `\x` (|aineo-run|). With one tab
aineo behaves as it always has.

The first open of aineo in a Neovim, the autostart or `\o`, makes the current
tab page aineo's first tab; its buffers are `aineo://report` and
`aineo://input`. `\T` (|:Aineo-tab|) opens a tab page at the end, after the
last tab page, so that no tab changes its number, with an aineo tab in it: a
layout of its own around a Claude Code started on a new session, and the
cursor in its Claude window in Terminal mode. Its buffers are named with a
number that is never given again (`aineo://report-2`, `aineo://input-2`), and
so are its changes pane's buffers and the diffs it shows, which carry
`copy{n}/` after `aineo://` (`aineo://copy1/changes-files`,
`aineo://copy1/diff/{path}`), {n} counted the same way: two tabs never share
a diff buffer, whether their changes panes follow one repository or two.
With no aineo tab yet, `\T` makes the current tab page the first one, on a
new session. Starting a tab starts a Claude Code, which costs what a session
costs, as `\o` does.

`\S` (|:Aineo-sessions|) opens the session you pick in a new tab at the end,
resumed, attached to where it runs in Claude Code's background service, or
resumed with a warning where it is open in another interactive Claude Code;
the cursor lands in its Claude window in Terminal mode. A session that a tab
of this Neovim shows already, the current tab's own included, is not started
again: the pick moves you to that tab. Nothing is written into the current
tab's prompt, and its Claude Code goes on as it was.

Every tab after the first starts its Claude Code in the folder: the
directory of this Neovim's first start of aineo, whatever `:cd` or `:tcd`
say later, since a tab holds a session of that folder alone. The first tab
starts where Neovim is, as it always has, each directory resuming its own
session (|aineo-claude-session|).

`\1` to `\9` (|:Aineo-tab|) move to the tab page of that number, an aineo tab
or not, as `{n}gt` does; the cursor lands where it was in that tab page, in
Normal mode. With no tab page of that number nothing moves and aineo says so.
The number is the tab page's place: closing a tab page, or `:tabmove`, changes
the numbers after it, and the titles with them. A new tab opens at the end, so
it changes no number; `:tabmove` reorders the tab pages.

A tab's title is `<number>: <name>`: its number, a colon, and, for an aineo
tab, the name of its session, the name Claude Code gives it (`Claude Code`
until it gives one); for any other tab page, the name of its current buffer.
While 'tabline' is empty when the first aineo tab opens, aineo sets it to a
tab line of its own that draws those titles, the current tab in
`AineoTabLineSel`, the others in `AineoTabLine` (|aineo-tabline|), each
clickable. A 'tabline' you set is left in place.

aineo's tab line draws every name whole while the titles fit the width of the
editor. When they do not, it cuts the longest names first, all to one width,
the widest at which the line fits, with `…` at the end of each name it cut; a
name no wider than that stays whole. A wide character that would cross the
edge is left out, so a cut name may take a cell less than that width. The
number, the indicator and the `tabs.padding` spaces are never cut. No name is
cut to fewer than 8 cells, `…` included, apart from such a left-out cell. When
the titles overflow even then, the line draws the run of them that holds the
current tab and fits. The line is fitted again at every redraw, so a resize, a
tab opened or closed, and a name or an indicator that changes all move the
cut.

An aineo tab's title ends with an indicator of what its Claude Code is doing,
after a space: ◒ and ◓ in turn, twice a second, while the tab's Claude Code
works or a subagent of its runs; ● once that has ended while you were in
another tab, until you enter that tab; nothing otherwise, so that an idle
title has no trailing space. The tab you are in shows ◒ and ◓ while its
Claude Code works, and never ●. The indicator reads the title Claude Code sets
on its terminal (|aineo-limits|), and is part of the title, so it takes the
tab's highlight group and counts in the cells the line fits. It shows where
the tab line does: aineo sets 'showtabline' to 2 when its first tab opens, so
with one tab page too (|aineo-config-tabs.always_show|).
                                                             *aineo-tab_title*
`require('aineo').tab_title({n})` gives the title aineo would draw for the
tab page numbered {n}, for your own tab line, the activity indicator of
|aineo-tabs| included and the name whole: a tab line of your own knows its
width and fits the titles itself; nil when there is no such tab page, and an
error when {n} is not a whole number from 1. While a tab's Claude Code works
aineo draws the tab line again twice a second, whoever draws it. Whoever
draws the tab line, aineo sets 'showtabline' to 2 once, when its first tab
opens, unless `tabs.always_show` is `false`
(|aineo-config-tabs.always_show|); a value you set afterwards is kept.
`:checkhealth aineo` says which tab line is in use and what 'showtabline' is
(|aineo-health|).
                                                               *aineo-tabline*
aineo's tab line draws the current title in `AineoTabLineSel`, the other
titles in `AineoTabLine` and the rest of the line in `AineoTabLineFill`. Their
defaults: `AineoTabLineSel` is |hl-TabLineSel|'s colours in bold;
`AineoTabLine` is the foreground of |hl-Normal| over the background of
|hl-TabLine|, linked to |hl-TabLine| when |hl-Normal| has no foreground;
`AineoTabLineFill` is linked to |hl-TabLineFill|. aineo defines them when it
takes the tab line and again after every |:colorscheme|, which clears them,
and every change of 'background'. A group you define is kept as you defined
it; define it again in a |ColorScheme| autocommand to keep it across
colorschemes: >lua
    vim.api.nvim_set_hl(0, 'AineoTabLineSel', { fg = '#ffffff', bold = true })
<
Every title has `tabs.padding` spaces either side of it
(|aineo-config-tabs.padding|). A terminal draws one font size, so the line
cannot be made taller or its letters larger; padding makes the titles wider.

What the actions do with tabs:
- Every action acts on the current tab when the current tab page is an aineo
  tab. From any other tab page it acts on the aineo tab used last, and moves
  you there: `\o`, `\r`, `\i`, `\c`, `\g`, `\pa`, `\pt`, `\x`, `\X`, `\e`,
  `\tcn`, `\N`, `\S`, `\s`, `\d` and `:Aineo claim`. `\d` makes no tab: with
  no aineo tab it only tells you there is no diff to close.
- A report goes to the tab whose Claude Code sent it. A session hook goes to
  the tab whose start it names. Each tab is listed among the running editors
  for its own session (|aineo-report-claims|). A report of no known session
  from a Claude Code that no tab of this Neovim runs is shown in no tab: the
  report server tells Claude that it was not delivered.
- `:Aineo claim {id}` claims the session in the current tab. When another
  tab of this Neovim runs the session, it moves you to that tab and claims
  nothing.
- Two tabs on one session, as when a `/resume` in one tab names the session
  of another, both follow it; aineo warns once, `aineo: this session is also
  open in tab {n}`.

`\Q` (|:Aineo-tab|) closes the current tab while another aineo tab remains,
and a tab page closed by Neovim's own commands, `:tabclose`, `:tabonly` or the
close of its last window, closes its tab the same way: its Input's draft is
saved, its buffers and handlers are let go (the first tab's stay, for the next
tab opened to take up; |aineo-limits|), and its entry among the running
editors is removed. Its shell, if it runs one, is stopped and its buffer
wiped, before its Claude Code is stopped as quitting stops it (Ctrl+Z alone
for one attached to a background session) once the command has ended, those
of all the tab pages the command closed together, without holding the
editor. Its Report, draft and changes base stay on disk, under its session,
and `\S` brings the session back in a new tab. The other tabs go on as they
were. On the last aineo tab `\Q` quits Neovim as `:qa` does: Neovim refuses
while a buffer has unsaved changes, and nothing is stopped then; otherwise
every Claude Code is stopped as quitting stops it, and the session is the one
the next start lands in. From a tab page that is none of aineo's `\Q` closes
nothing and says `aineo: this tab holds no Claude Code session`. Quitting
stops every tab's Claude Code at once and saves every tab's draft
(|aineo-limits|).

The folder keeps the list of its tabs: the session of each aineo tab, in the
order of the tab pages, and the place of the tab that is current (the aineo
tab used last, when the current tab page is none of aineo's). A session two
tabs show is listed once, at the lower place. It is kept as a tab opens or
closes, when a tab's session changes, and when Neovim quits, in a file of its
own beside the session kept for the folder (|aineo-claude-session|): under
`stdpath('state')` in `aineo/claude-tabs/`, one file per folder that only you
can read and write. Whenever it is kept without the session kept for the
folder, the session at its place becomes the session kept for the folder, so
that a tab you closed is not brought back alone by the next start. The first
open of aineo in a Neovim reopens every tab of the list when the list holds
the session kept for the folder: the autostart, or the first `\o`, `\c`, `\i`,
`\r`, `\pa`, `\g` or `\T`, or the `:Aineo` command that is the same. The
first tab is in the current tab page, the others in tab pages after it, in the
order of the list, each with a Claude Code on its own session, resumed or
attached to where it runs in Claude Code's background service, as a start does
(|aineo-claude-session|), in the folder, whatever `:cd` said since; all start
at once, each listing the folder's sessions. The tab that was current at the
quit is current again, and a reopened tab shows the agent pane. At most 20
tabs open; aineo says how many more stay in the list. A tab that cannot start
stops the reopening: aineo names its session and the sessions not tried, which
stay in the list. A list that is missing, unreadable or does not hold the kept
session opens one tab on the kept session, as before. Only the first open
reopens: a Neovim a session plugin restored opens no tab, and a later `\o`
reopens nothing either. A tab closed with `\Q` or by Neovim's own commands is
no longer in the list and does not reopen; `\S` brings its session back. `:qa`
keeps every tab in the list, and so does `\Q` on the last tab.

The changes pane ~
                                                               *aineo-changes*
The changes pane lists what changed in your repository since the base of
the Claude Code session it shows; below your own lines, its commits window
lists what landed in your working branch (below), then each of the
repository's other worktrees with its commits since a base of its own
(below), and the line under its cursor chooses what the files window lists,
what landed or a worktree's change included. Its repository is the one
Claude Code's working directory was in when aineo first started Claude Code
in this editor, for the editor's life. A session
aineo has not seen takes as its base the commit `HEAD` names when aineo
starts following it: when Claude Code, started on it, is first ready for
input, which can be long after the start, while a dialog is up say, when
you switch to it inside Claude Code, or when you claim it by its id
(|:Aineo-claim|) — except a session that takes the place of one whose resume
found no conversation, which takes over that session's base and saves,
whichever repository they name (|aineo-claude-session|). A Neovim that
claims a session before it has first started Claude Code lists nothing in
the pane until it does: the pane then shows the claimed session. A file
saved while a claim holds is marked for the claimed session (see the `*`
below). aineo keeps each session's base, and the files you save while it
shows that session, under `stdpath('state')`: a restart of Claude Code or
of the editor, or a switch back to an earlier session, shows that session's
base and saves again; when a resume of it finds no conversation, the
session that takes its place shows them (|aineo-claude-session|). A start
aineo could not make — `claude.cmd` not executable, say — takes no base. A
Claude Code that fails before it is first ready for input is never
followed: the pane takes `HEAD` at that start as its base, as at any start,
and keeps it for no session.

The first line of the files window, `aineo://changes-files`, names what it
lists: `Files in: Session work`, `Files in: Uncommitted`, or `Files in: `
and a commit's line as the commits window shows it, its abbreviated id,
author and age, and subject; `Files in: Landed in <branch>` for what landed
in your working branch (below); or, for another worktree, `Files in: ` and
the worktree's heading as the commits window shows it, or a commit's line
followed by
`(worktree <folder>)`; the commits window chooses (below). The window
lists the files of that one choice and nothing else, no other worktree's
heading or files among them, whichever choice it is. It shows its first
line, the cursor on it, each time the choice changes, and when a list is
read again for the same choice the cursor stays on its file.

                                                    *aineo-changes-against*
The second line, `Against: <left> → <right>`, says what Enter on a file of
that list diffs, both sides, so that no diff is read against the wrong
base. `<left>` is the side the diff runs from: the abbreviated id of its
commit; between parentheses the branches, remote-tracking branches and tags
whose tip that commit is, local branches first, then remote ones, then tags,
comma separated, the first three and `…` when there are more, no parentheses
for none; and where the commit came from, in words, one of:
>
    reported base          the base an agent reported for a worktree or
                           branch, when aineo reads from it
                           (|aineo-changes-reported-section|)
    merge base with {ref}  the base aineo works out for a worktree or
                           branch: its merge base with the working branch,
                           named, or, where that gives none, with the commit
                           your own branch compares against, by its
                           abbreviated id; under Landed, the merge base of
                           the session's base and the working branch
    HEAD                   under Uncommitted
    parent                 under a commit, its first parent; a root commit
                           says `empty tree` alone
<
Under Session work the commit is the one `HEAD` named when the session
began, said `session start`. `<right>` is `working tree` where the diff reads
the files on disk (Session work, Uncommitted, a worktree's whole change),
else the abbreviated id and names of the commit it reads (a commit; the tip
of Landed's working branch or of a branch). With no base at all, `<left>` is
`empty tree`. The line shows the id alone until aineo has read the names,
with one git run off the main loop each time the files window is read and
each time a branch or tag moves, a fetch included; it never waits for them.
While aineo reads the commit `HEAD` names, a commit's parent or the merge
base of Landed, the line says that side by its words alone, as in
`Against: HEAD → working tree`, never the id of an earlier read, and the
same holds for the bar of a diff read again with F. A branch aineo has not
read yet says `Against: reading…`. The same line, for the same choice, is
what the diff bar below says. The label shows in |hl-AineoChangesFilter|,
an id in |hl-AineoChangesCommitId|, names in
|hl-AineoChangesReportedBranch| and the words in |hl-AineoChangesNote|.

Under Session
work the window lists every file that differs from the base, committed
since or not, staged or not, and every new file your ignore rules leave
in, one per line, in git's order: >
    * M lua/aineo/init.lua
      ? notes.txt
      R old.txt → new.txt
<
The letter is the kind of change: `A` added, `M` modified, `D` deleted, `R`
renamed, after its old path, `T` turned into a link or back, `?` new and
untracked; a copy shows as added. The `*` marks a file saved since the
base was taken, from this editor, or from another one following the same
session in this repository once this editor next saves a file it had not
saved, or follows the session again — `:write`, `:update`, `:wall`, a part of
a buffer written to a file or appended to one, the file written whatever its
buffer is named, a file opened through a symbolic link included. A file you
saved before aineo started following the session carries no `*` for it, though
it is still listed against the base: when Claude Code starts, that is at least
the 1.5 seconds it waits for Claude Code's input to settle, longer while a
trust or MCP-server dialog is up (a real Claude Code's start was not
measured), and a save made then is marked for the session followed before, if
any. A file you and Claude both changed is marked too: aineo cannot tell who
changed what. A path holding a line break, a control character, a double quote
or a backslash is shown between double quotes, each of those escaped as git
escapes it; characters outside ASCII are kept as they are, where git writes
them in octal. With nothing changed, the window says "No files changed on this
session".

Under Uncommitted the window lists every file that differs from `HEAD`,
staged or not, and every new file your ignore rules leave in, in the same
form and with the same `*` marks, or says "No uncommitted changes"; before
the first commit every file is new. Under a commit it lists the files that
commit changed, against its first parent, with no `*` on any line: a merge
lists what it brought in, a root commit its files; an empty commit says "No
files in this commit".

Under the Landed heading the window lists the files that differ between the
merge base of the session's base and the commit the working branch named
when the commits window last read it, and that commit, in the same form and
with no `*` on any line, or says "No files changed in what landed"; with no
base, every file of that commit is new. Under a commit that landed it
lists the files that commit changed, against its first parent, with no `*`,
as under any commit.

Under another worktree's heading the window lists the files that differ in
that worktree from its base, in the same form, with no `*` on any line, or
says "No files changed in this worktree"; under one of its commits, the
files that commit changed, against its first parent, read in that
worktree, also with no `*`, or "No files in this commit". The worktree's
base is read again each time the files are, and never kept (below).

The commits window, `aineo://changes-commits`, starts with two lines that
are always there, Uncommitted and Session work, then lists the session's
commits, newest first, by abbreviated id, author and age, and subject (below),
or says "No commits on this session". Its cursor is on Session work when the
pane first shows, and when the buffer is made anew; `\g` keeps your line, and
switches the view while a worktree or a branch is shown alone (below). The
line under the cursor chooses what the files window lists, once the cursor has
stayed on it for 150 milliseconds, however it moves - keys, a click, or the
mouse wheel over the window while the cursor is in another one: Uncommitted,
Session work, that commit; on the Landed heading, everything that landed; on
a commit that landed, that commit; on another worktree's heading, that
worktree's whole change; on one of its commits, that commit, read in that
worktree. The same commit listed under two worktrees, or among your own and
among those that landed, is two choices. A line that lists none of these -
a note - keeps the last choice. The files window keeps its first line and
its list until the new list is read. The choice goes back to Session work,
the cursor with it, when aineo follows another Claude Code session, when
the chosen commit is no longer listed after a reset or a rebase, when the
chosen commit that landed is no longer listed after the working branch was
reset or pushed over, when the Landed section is no longer shown, and when
the chosen worktree is no longer listed; when the worktree is listed but a
commit of it that was chosen is not - the agent amended or rebased it - the
choice becomes that worktree's whole change, the cursor on its heading.

                                                *aineo-changes-author-column*
Every commit line the pane draws - your own, those that landed, another
worktree's or branch's, and the commit named on the first line of the files
window, the commit graph's excepted (|aineo-changes-graph|) - is the
abbreviated id, a space, a column of the commit's author and
age, a space, and the subject: >
    1a2b3c4 Ada Lovelace 3h      Add the report
    5d6e7f8 Bartholomew Mont… 2d Fix the build
<
The column is 20 display cells wide whatever the name, so the subjects line
up: the author's name as git recorded it (`%an`), a space and the age of the
commit's author date, padded with spaces. The age is told in whole units,
rounded down: `now` under a minute, then `<n>m`, `<n>h`, `<n>d`, `<n>w`,
`<n>mo` (30 days) and `<n>y` (365 days); a date ahead of the clock is `now`.
The age is never cut; a name too long for what it leaves is cut, by display
width, with `…`, and a control character of a name shows as a space. The
ages are told as of the moment a list is written: they move on when the pane
writes a list again, not by themselves. The name shows in
|hl-AineoChangesCommitAuthor| and the age in |hl-AineoChangesCommitAge|.
Uncommitted, Session work, the headings and the notes are as they were.

                                                           *aineo-changes-l*
`l` in the commits window moves the cursor to the files window, the choice
the line under the cursor makes kept: it makes it at once, without waiting
for the 150 milliseconds, and the files window then lists it. The cursor goes
to its first file, or to the file it was on when the window already listed
that choice; on a line that lists no file, a note, it still moves. `<BS>` in
the files window moves the cursor back to the commits window, onto the line
that chose what the files window lists. `h` in the files window keeps
showing the diff against `HEAD` (|aineo-changes|).

                                                   *aineo-changes-graph*
`t` in the commits window shows the commit graph in place of its whole list,
the Reported section included (|aineo-changes-reported|), and `t` again shows
the list as it was, the line chosen before the graph chosen again. There it
replaces Vim's |t|{char}, in Normal mode. The graph is what this command
draws: >
    git log --graph --all --abbrev-commit --date=relative
<
of every branch, tag and remote-tracking branch, newest first: the graph as
git draws it, then, on each commit's line, its abbreviated id, its age, its
subject, its author and the names that point at it: >
    * 1a2b3c4 - (3 hours ago) Add the report - Ada (HEAD -> main)
    | * 5d6e7f8 - (2 days ago) Fix the build - Grace (origin/fix)
    |/
<
A control character of a subject, an author or a name shows escaped, as C
escapes it (`\t`, `\033`). The graph lasts for the tab: it stays shown as you
move between windows and the pane is shown again, and a new editor starts on
the sections. It is read again each time `t` shows it, as the pane is shown
again, and as the repository changes: a commit, a checkout, a branch or tag
made or deleted, a fetch. A read keeps the cursor on its commit while the
graph lists it; when it no longer does, the cursor goes to the nearest commit
line, which the files window then lists, whether the commits window is the
current one or not. A read that fails keeps the graph shown and says so
above it.

`j` and `k` go from commit line to commit line, over the graph's own lines,
such as `|/` and `|\`, and take a count: `3j` goes three commits down; over
the sections they stay Vim's own. The cursor never rests on a line of the
graph alone: any other move that lands there - `<Up>`, `-`, `<C-p>`, `G`, a
click - goes on to the commit line beyond it in the direction it moved,
above for a move up, below for a move down; when the cursor did not move,
as when a read changes its line, it goes to the nearest commit line, the
one below when two are as near. The commit under the cursor chooses what
the files window lists, as a commit line of the sections does
(|aineo-changes|), and `l`, `<BS>`, Enter, the diff that follows the cursor
of the files window and `F` work on it as on any commit. `s` does not
change the graph.

The graph draws the newest 1000 commits, or as many as
`changes.graph_limit` says (|aineo-config-changes.graph_limit|), and ends
with "Older commits not shown" when it left older ones out.

Every colour of the graph comes from your colour scheme: the abbreviated id
in |hl-AineoChangesCommitId|, the age in |hl-AineoChangesGraphAge|, the
subject in |hl-AineoChangesCommitSubject|, the author in
|hl-AineoChangesGraphAuthor|, the names in |hl-AineoChangesGraphRef|, and
each mark of the graph in the group of its lane, |hl-AineoChangesGraphLane1|
to |hl-AineoChangesGraphLane6|, the seventh lane coloured as the first, a
`/` or a `\` as the lane on its right.

Below your own lines, which have no heading, the commits window lists what
landed in your working branch: the heading `Landed in <branch>`, then the
commits of that branch your session's base cannot reach, newest first, each
as your own are listed, a merge commit among them, or "Nothing landed in
<branch> on this session". It is the work merged into the branch since,
by anyone: the commits of a rebase merge are listed under their new ids.
The working branch is the branch `changes.working_branch` names
(|aineo-config-changes.working_branch|), as git reads a name, `origin/dev`
say, or, when you set none, the default branch of the remote `origin`,
which `origin/HEAD` names; a repository with neither shows no such section.
When the name names no commit, the heading is followed by the line
"<branch> names no commit". With no base, a session begun before the
repository's first commit, every commit of the working branch is listed.
aineo never fetches: the section shows the working branch as your
repository last knew it (|aineo-limits|).

Below those, the commits window lists the repository's other worktrees, in
the order `git worktree list` gives them, each under a heading naming its
folder and its branch, or `detached`: >
    Worktree agent-1 (feature/x)
    1a2b3c4 Add the report
<
then that worktree's commits since its base, in the same form, or "No
commits in this worktree". With no other worktree, the pane shows only your
own lines. A worktree git marks
prunable, one whose directory is gone, locked or not, and the directory of
a bare repository are left out; a locked one is listed. A worktree's base
is read again at each read and never kept: its merge base with the commit
the working branch names now (above), so that its commits are what a pull
request of its branch into the working branch would hold, and its whole
change also includes the files changed in its working tree, uncommitted and
untracked ones. Where the working branch gives no base - you have none, its
name names no commit, or the worktree shares no history with it - the base
is its merge base with the upstream of the branch your own worktree is on,
with that branch when it has no upstream, or with your `HEAD` when it is
detached. A worktree that shares no history with that either, or has no
commit yet, is listed with no base: every file new, every commit its own.
When the working branch cannot be read, each worktree's section says why,
over what it listed before.

                                                          *aineo-changes-s*
`s`, in the commits window or the files window, offers the other worktrees
and the local branches to show alone, in |vim.ui.select()| under the prompt
"Show alone in the changes pane": one list, each item marked by its kind.
The worktrees come first, each named as its heading names it,
`[worktree] agent-1 (feature/x)`, or `(detached)`, in the order the commits
window lists them; then the branches, `[branch] feature/x`, the name quoted
as a path is, the one with the newest commit first. A branch is offered
unless a worktree has it checked out, yours included — that is read when you
press `s`, so a branch you have checked out since is left out — or it is the
working branch (below), their short names compared: `origin/dev` leaves out
the local branch `dev`, as do `refs/heads/dev`, `heads/dev`,
`refs/remotes/origin/dev` and `remotes/origin/dev`. Neovim's own
|vim.ui.select()| is a numbered list with no search; a picker plugin that
replaces it (telescope, fzf-lua, snacks, dressing and the like) searches
that text. While Claude Code has reported work, the list begins with the
Reported section's tree, each line `[reported] ` and the line as the
section shows it, indented, then `[reported] All reported work (<n>)`
(|aineo-changes-reported-section|); picking a line shows what it names
alone. `s` is a
Normal-mode map of the two buffers of the pane and of the explorer's buffer,
where it is the same pick (|aineo-explorer|); in every other buffer it is
Vim's own.
The branches are listed off the main loop and the picker opens once they
are; pressing `s` again meanwhile opens no second picker. Branches that
cannot be listed leave the worktrees alone, and aineo says so once, as a
warning. With neither a worktree nor a branch to offer, `s` opens nothing
and says "aineo: no other worktree or branch to show alone"; when the other
worktrees could not be listed and none is known, it says the line the
commits window shows, and reads no branch, as nothing then says which are
checked out; while there is no repository, or aineo is reading it, `s`
opens nothing and says what the windows say. When aineo has not read the
other worktrees yet, as before the pane was first shown, `s` says it is
reading the repository, reads them, and opens the picker once they are. A
picker that raises is told once, as an error; an answer that is none
of the items offered is ignored. Dismissing the picker changes nothing. `s`
does not wait for 'timeoutlen', whatever global maps begin with `s`.

Picking a worktree shows it alone. The commits window then lists nothing
but its heading, `Worktree <folder> (<branch>)`, whole in
|hl-AineoChangesFilter|, and below it that worktree's commits, newest
first, or "No commits in this worktree", with the line saying its last read
failed when it did: no Uncommitted, Session work, commit of your own, Landed
section, other worktree, or line saying the worktrees could not be listed;
nor the lines saying the session's own read failed, the watch stopped, or the
base is no longer behind `HEAD`, which the default view shows.
The heading is chosen, the cursor on it, and the files window lists the
worktree's whole change, `Files in: Worktree <folder> (<branch>)`; the
cursor chooses among its commits as ever. `s` under it offers the same
list, and a pick replaces the worktree shown. aineo reads what it reads
without it; only what the commits window shows differs.

Picking a branch shows it alone the same way. The commits window lists its
heading, `Branch <name>`, whole in |hl-AineoChangesFilter|, and below it the
branch's commits since its base, newest first, or "No commits on this
branch", with the line saying its last read failed when it did: nothing else.
The branch's base is its merge base with the commit the working branch names
now (|aineo-changes|, Landed), so that its commits are what a pull request
of it into the working branch would hold, not what the working branch holds
that your session has not seen; where that gives none — no working branch, a
name that names no commit, no shared history — it is the branch's merge base
with the same comparison commit the other worktrees' bases fall back on
(above). A branch with no base lists every commit it reaches. The tip and the
base are read again at every read of the commits window and never kept: a
commit added to the branch shows at the next one. The heading is chosen, and
the files window lists the branch's whole change, `Files in: Branch <name>`:
the committed files that differ from its base to its tip, with no `*` and
none of what is uncommitted in your worktree; the cursor chooses among its
commits, `Files in: <id> <subject> (branch <name>)`, read in your repository.
A commit the branch no longer lists, after a reset or a rebase, gives way to
the branch's whole change. A branch checked out in a new worktree stays the
scope; one deleted or renamed so that its name names no commit is gone, as
a worktree no longer listed is (below): the default view shows, Session
work is chosen, and aineo says once "aineo: Branch <name> is gone; the
changes pane shows the default view" - also when the default view hides it.

`\g` (|:Aineo-pane|), pressed with the cursor in one of the pane's two
windows, switches between the default view and the worktree or branch shown
alone, read again each time. It is kept while the default view shows.
Back in the default view, the choice stays, the worktree's heading or one of
its commits, the cursor on its line; the default view lists no branch, so a
choice of a branch's gives way there to Session work. Back in the scope
view, the choice stays when it lists it, else the whole change is chosen.
Pressed anywhere else — Claude's window, Input, the Report, a diff in the file
column — `\g` does not switch: it moves the cursor into the commits window,
the pane in the view it was last shown, read again; when the pane is not on
screen it is shown in that view. The worktree or branch is shown alone until
`s` picks another, until it is no longer listed (a branch: until it names no
commit), until aineo follows another Claude Code session than one it
followed before (the first session followed keeps it), or until the tab
closes; each tab keeps its own, and the pick is kept on disk for each
Claude Code session and shown again when aineo follows that session
(|aineo-changes-view-kept|). When a read no longer lists the worktree,
the default view shows, Session work is chosen, and aineo says once
"aineo: Worktree <folder> (<branch>) is gone; the changes pane shows the
default view". Following another session says nothing.

Enter on a file's line shows its unified diff in the middle column (the
file column, below), within what the files window lists: from the base
under Session work, in `aineo://diff/{path}`; from `HEAD` to the working
tree under Uncommitted, in `aineo://uncommitted/{path}`; under a commit,
the commit's header and that file's change in it, in
`aineo://commit/{id}/{path}`, {id} its full id. Enter on Uncommitted shows
the whole diff from `HEAD` to the working tree, new files included, in
`aineo://uncommitted`; on Session work the whole diff from the base, in
`aineo://session-work`; on a commit that commit's diff, in
`aineo://commit/{id}`, a merge's against its first parent. Enter on the
Landed heading shows the whole diff from the merge base of the session's
base and the working branch to the working branch, in `aineo://landed`; on
a file listed under it, that file's change there, a renamed file with both
paths, in `aineo://landed/{path}`; on a commit that landed, and on a file
under it, the diff shows as for your own commits. A new file
enters a whole diff through a copy of git's index, so your own index is
never touched; an untracked repository with no commit yet is left out. A
diff is read-only: a buffer with 'filetype' `diff`, wiped once hidden.
For another worktree, Enter on a file listed under its whole change shows
that file's diff from the worktree's base, in
`aineo://worktree{top}//diff/{path}`; on a file listed under one of its
commits, the commit's header and that file's change in it, in
`aineo://worktree{top}//commit/{id}/{path}`, {id} its full id; in the
commits window, on one of its commits, that commit's diff, a merge's
against its first parent, in `aineo://worktree{top}//commit/{id}`, and on
its heading the whole diff of the worktree from its base to its working
tree, its untracked files included, in `aineo://worktree{top}//since-base`.
All are read in that worktree, and {top} is its top level, so two
worktrees' diffs of one path are two buffers; no key opens another
worktree's file. For a branch shown alone, Enter on its heading shows the
whole diff from its base to its tip, committed changes only, in
`aineo://branch/{name}//since-base` (before the branch's first read, aineo
says it is reading the repository and shows nothing); on a file under its
whole change, that file's change between them, a renamed file with both
paths, in `aineo://branch/{name}//diff/{path}`; on one of its commits, and
on a file under one, the diff shows as for your own commits, in
`aineo://commit/{id}` and `aineo://commit/{id}/{path}`. {name} is the
branch's name quoted as a path is; git refuses `//` in one, so the
separator is safe. Once the diff is shown, the
cursor moves to its window, in the mode you were in: Normal mode, as in the
pane; no Insert mode starts. When you have left the pane's window before the
diff is shown, the diff is shown and the cursor stays where you are, in
your mode, Terminal mode included. When you press Enter again before a diff
was read, only the last Enter's diff is shown. Enter on any other line
does nothing. When the middle column has no room for the
diff, aineo says so, shows nothing, and the cursor stays in the pane; so it
does when showing the diff fails.

                                                     *aineo-changes-diff-bar*
Each diff window aineo opens shows in its 'winbar' `<left> ↔ <right>  <path>`:
the two sides as the `Against:` line says them (|aineo-changes-against|),
and, for one file's diff, its path as the files window shows it; a whole
diff has no path. The bar belongs to the diff, not the window: a diff kept
in a window, or opened earlier, still says what it compares, and another
buffer shown in that window later draws your own 'winbar'. `h` shows a diff
against `HEAD`, and its bar says so: from `HEAD` to the working tree under
Session work, Uncommitted and a worktree, from `HEAD` to the tip under
Landed and a branch, and from the commit to `HEAD` under a commit. `F`
reads the diff again and the bar with it; the diff that follows the cursor
draws the bar of the file it shows. Colours are the `Against:` line's.

The name of every diff and of every file `gf` shows, here and below, is the
first tab's. A tab after it names them with `copy{n}/` after `aineo://`, as it
does its pane's buffers (|aineo-tabs|): `aineo://copy1/diff/{path}`,
`aineo://copy1/session-work`, `aineo://copy1/show/{id}/{path}`.

`gf` on a file listed under a commit, one of yours, one that landed or one
of another worktree's, shows the file as that commit has it, in the middle
column as Enter shows a diff, in `aineo://show/{id}/{path}`, {id} the
commit's full id and {path} quoted as the files window quotes it. Under the
Landed heading it shows the file as the working branch's commit has it, and
under the whole change of a branch shown alone as the branch's tip has it,
in `aineo://show/{tip}/{path}`. The
buffer is read-only, not modifiable, wiped once hidden, with the 'filetype'
the path and the content give, so its syntax shows, and holds the bytes git
printed, cut at 1 MiB; a virtual line under the last line shown says how much
of the file's whole size is shown, so that a yank or a `:write` of the
buffer carries only the file's bytes. aineo takes no more than that 1 MiB
from git and stops it once it has come, so the editor's memory does not
grow with the file; git itself may unpack a file stored in a pack whole
first.
The cursor moves to its window as it does for a diff, and only the last key's
file or diff is shown when you press keys again before one was read, a `gf`
that opens the working tree's file included. A file the
commit deleted opens nothing, and aineo says it was deleted in that commit;
any other failure is told once, naming the file; and when the middle column
has no room, aineo says so and shows nothing.

Under Uncommitted and Session work, `gf` on a file's line opens the working
tree's file in the file column, as any file opened from one of the layout's
windows is; with none of the layout's windows open, it opens in the window
the pane is in, as |:edit| does. On a file no longer in the working tree it
opens nothing, and aineo says the file is gone; on a line whose path is a
directory, a submodule, a nested repository or a worktree inside your tree,
it opens nothing, and aineo says it is a directory, not a file; on a file
listed under another worktree's whole change it opens nothing, and aineo
says the changes pane opens no other worktree's file; on any other line it
does nothing and says nothing. An edit
Neovim refuses is told once, naming the file; one you abandon at a swap
file's prompt is dropped without a word, as Vim's own |gf| drops it. It is a
Normal-mode map of the files window's buffer alone, made again whenever that
buffer is made anew, so |gf| in every other buffer, the commits window and
the diffs included, is Vim's own, and no `<Plug>` mapping stands for it.
Enter and `gf` take a file's name from the list itself, whatever characters
it holds, spaces, quotes and an apostrophe among them: a name that fails to
open from the pane is a fault to report.

                                                       *aineo-changes-edit*
`\<CR>` (the prefix, `\` by default, and Enter) on a file's line opens the
file for edition, as does `<S-CR>` (Shift and Enter). The file is opened as
it is now in the working tree its line belongs to, with no diff and no
commit's version: a file of your own worktree, whatever filter lists it, a
commit of yours included; a file listed under another worktree, in that
worktree (`<top>/<path>`, which `gf` refuses); a file of a local branch, in
the worktree that has the branch checked out, which aineo asks git for when
you press the key (when git cannot list the worktrees, aineo says so and
opens nothing; when you press another key or leave the window meanwhile,
nothing opens). It opens in the file column,
as `gf` opens the working tree's file, a normal buffer that `:write` writes
into that worktree, the cursor in it, in Normal mode. A branch no worktree
has checked out has no file to edit: the file opens as the branch's tip has
it, read-only, as `gf` shows a branch's file, in `aineo://show/{tip}/{path}`,
and, once the tip's file is read, aineo says once "aineo: the branch <name>
is checked out in no worktree, so <path> cannot be edited; it is shown as
the branch's tip has it". A file the branch's tip no longer has opens
nothing, and aineo says only that it was deleted in the branch. A file no
longer in that working tree opens nothing, and aineo says the file is
gone; a path that is a directory, a submodule or a nested repository
opens nothing, and aineo says it is a directory, not a file. The path is
taken whole, as for `gf`: no character of it is a wildcard or the end of a
command. Enter, `h`, `l` and `gf` are unchanged, and `\<CR>` and `<S-CR>`
on any line that lists no file do nothing. `\<CR>` follows the prefix
(|aineo-config-prefix|) and is a map of the files window's buffer alone;
with the prefix `false` it is not mapped, and `<S-CR>` is the only key. In
that buffer it replaces a global mapping of your own on the same keys; in
every other buffer your mapping stays.

Neovim receives `<S-CR>` only when your terminal tells it apart from Enter,
which many terminals do only once asked for extended keys. Inside tmux, tmux
must pass them on: set `extended-keys` to `on` (or `always`) in your tmux
configuration. `extended-keys-format` (`csi-u` or `xterm`) is the format
tmux uses to report modified keys to the program in the pane. A terminal
tmux does not recognise as sending extended keys is told so with the
`extkeys` feature of `terminal-features`. In iTerm2, give Shift+Return a key
mapping (Settings, Profiles, Keys) whose action is "Send Escape Sequence"
with `[13;2u`.

The diff of the file under the cursor follows the cursor in the files window
while a diff is open: once Enter, `l` or `h` showed one in the middle column,
the diff appears there as the cursor moves, with no key, whether `j`, `k`, the
mouse, a search, `gg` or `G` moved it, once the cursor has stayed on a line
for 120 ms, so that holding `j` draws only the file it stops on. While no diff
is open, moving the cursor opens none: not as the cursor lands in the files
window, nor after `l` in the commits window moved it there. No diff is open
when the middle column shows another buffer, a file opened for edition, `gf`'s
file or nothing, and following stops once `\d` closed the diff or a file
replaced it, until Enter, `l` or `h` shows a diff again. The cursor stays in
the files window, on its line, and the commits window's choice is not
changed. The diff is the kind `l` or `h` chose last: against the file's
previous version until one of them is pressed. A line that lists no file, a
heading, a note or an empty one, shows nothing new, and the last diff stays; a
diff a window of the tab page shows already is not drawn again. The cursor
must still be in the files window when the 120 ms end.

`<BS>` in a diff the pane showed in the middle column, whether Enter, `l`, `h`
or the cursor's following showed it, moves the cursor back to the files
window, onto the line of the file the diff shows, when the window still lists
it, in Normal mode. When the right column shows another pane, `<BS>` shows
the changes pane first, as `\g` does. It is a map of the pane's diff buffers
alone: a file opened for editing, in the working tree or as `gf` shows it,
keeps Vim's own `<BS>`.

`l` and `h` on a file's line show that file's diff at once, as Enter does, `l`
against the file's previous version, `h` against `HEAD`, choose the kind of
the diffs that follow the cursor from then on, and keep the cursor in the
files window, on that line, in Normal mode; only Enter moves the cursor to
the diff.
`l` shows what Enter shows on the line, in Enter's buffer. `h` shows,
under a commit of yours or one that landed, the file from that commit
straight to `HEAD`, a renamed file with both its paths, in
`aineo://head/commit/{id}/{path}`; under a commit of another worktree, to
that worktree's `HEAD`, in
`aineo://worktree{top}//head/commit/{id}/{path}`; under the Landed heading,
from `HEAD` straight to the working branch's commit, in
`aineo://head/landed/{path}`; under the whole change of a branch shown alone,
from `HEAD` straight to the branch's tip, in
`aineo://branch/{name}//head/{path}`, and under one of its commits as under
one of yours; under Uncommitted and Session work, from
`HEAD` to the working tree, in `aineo://uncommitted/{path}`, which is
Enter's diff under Uncommitted; under another worktree's whole change, from
that worktree's `HEAD` to its working tree, in
`aineo://worktree{top}//head/{path}`. A file `HEAD` lacks is shown wholly
added or removed. Both show only the last key's diff when you press keys
again before one was read, and tell a failure or a middle column with no
room as Enter does; `F` works in the diff they show, once the cursor is there,
and `\d` closes it from wherever the cursor is (|:Aineo-diff|).
When `h` finds no difference from `HEAD` - every file of the newest commit,
every file under Session work once the work is committed - it shows nothing
and the cursor stays; aineo says "<path> is as HEAD has it", once. The diff
that follows the cursor says nothing of such a file: the message is for `h`,
`l` and Enter. When `HEAD` names no commit, `h` says so under every filter,
Landed and a branch's whole change included.
On a line that lists no file they do nothing and say nothing. Each is a
Normal-mode map of the files window's buffer alone, made again whenever that
buffer is made anew, so it shadows Vim's `h` and `l` there, where the arrow
keys, `0` and `$` still move along a line; in every other buffer, the
commits window and the diffs included, they are Vim's own, and no `<Plug>`
mapping stands for them.

In a diff the pane showed, `F` reads that diff again with the whole file as
its context when its text shows three lines, and again with three lines of
context when it shows the whole file, so that it always changes what the
diff shows, even in a diff shown before an `F` in another one. It is a
Normal-mode map of the diff's buffer alone, so it shadows Vim's `F{char}`
there, and no `<Plug>` mapping stands for it. The diff is written into the
same buffer, under the same name, with the commit's header when it has one,
and the cursor of every window showing it stays on the same line of the same
file, or goes to the first line when the diff no longer shows that line. It
holds for every diff the pane shows, another worktree's too, the whole diffs
of Uncommitted and Session work among them. The context `F` chose is kept
until the editor quits, not on disk: each diff Enter shows after `F` is read
in it, one already being read when `F` is pressed included, and the editor
starts with three lines. A diff shown in another window keeps its text until
Enter shows it again. `F` says nothing; when the diff cannot be read, aineo
tells it once and leaves the buffer as it was, and the next diff Enter shows
is read in the context `F` chose all the same. When you press `F` again
before a diff was read, only the last one's is written.

The pane is read again whenever it is shown — `\g`, `:Aineo pane changes`,
`\o`, or the layout built anew showing it — and, from its first showing
until the editor quits, when a file is saved, when a file of the working
tree changes, and when the branch moves: a commit, even one that changes no
file, an amend, a reset, a checkout. The other worktrees are listed again,
and each one's commits read again, whenever the pane is shown and
whenever aineo's watch of your repository sees a change: in another
worktree, its `git add` or commit, a worktree added or removed, or a file
written in one inside your top level; so are the files of the worktree
whose whole change the files window lists; or in the repository, a
reference written by anyone — a fetch, a tag, a branch made or deleted
(but see |aineo-limits|). What landed is read again with your own commits:
at every showing, when the session takes a new base, and whenever the watch
sees a reference written, a fetch run from any worktree of the repository
included; the files under its heading are read again when the working
branch names another commit. The branch shown alone is read after the
worktrees, at every read of the commits window, its tip and base anew. A
worktree added shows at the next read, and
one removed goes, its diffs left as they are. One read of each window runs
at a time, in the commits window your own worktree's with what landed, and
the others', one after another, one git at a time; your own lines asked for
meanwhile are read before the next worktree's, not after them all. The
cursor stays on the line it was on while that line is listed. A diff
already shown stays as it was until you press Enter on its line again.
A list or a diff read while Neovim allows no change of text — an
expression mapping waiting for a key or in |input()|, or a completion
function still running — is shown once Neovim allows it again, with nothing
told, and so is a diff read while the command-line window is open, once it
closes (but see |aineo-limits|).

Until git has answered, each window says aineo is reading the repository.
When Claude Code's working directory is in no repository, both windows say
so, naming the directory, and give git's words below, which tell a
repository git refuses — one of another owner, or a bare one — from none;
when `git` is not found, both say that. aineo then looks again whenever the
pane is shown or a file is saved, and a repository made since — by
`git init`, say — becomes the session's, its `HEAD` then the base. When the
base is no longer behind `HEAD` — after a reset to before it, or a checkout
of another branch — the commits window says so above what git lists, and
the base stays. A read that fails keeps the list shown, under one line
giving git's words; a read of the working branch that fails keeps what
landed as it was, its line under the Landed heading, which reads `Landed
in origin/HEAD` when no name was known yet; so does another worktree's,
under its heading, the other worktrees as they are. When the
other worktrees cannot be listed, one line in git's words follows your own
lines, over the worktrees last listed. When aineo's watch of the repository
fails, both windows say so until the pane is shown again, which starts it
again.

                                                   *aineo-changes-reported*
Claude Code and its subagents tell aineo, through aineo's tool
`announce_work` (|aineo-report|), of each git worktree they work in: the
absolute path of its folder, a short label for their task, and every
branch they are working on there, each with the commit it was made from;
every agent and subagent
must, once per worktree, right after it makes the worktree or a branch in
it, and again whenever the set of branches it works on there changes. An
agent with several worktrees calls once for each. aineo's own hook tells it
too, after a command of Claude Code's `Bash` tool that makes a worktree or
a branch (|aineo-changes-hook|). A report goes to the tab whose Claude Code
made it, whichever tab is current, and to no other editor; one no tab of
this editor runs is not taken.
Before the tab takes a report, each branch it lists must be named exactly
as one of the local branches git lists in the worktree's folder — a
revision of one, `main~1` or `feature/a^0`, is no branch — and its base is
resolved to a full commit id, as git reads a name: first in the worktree's
folder, so that `HEAD` is the agent's own, then in the session's
repository. A branch git does not list, or a base git cannot resolve in
either, refuses the whole report, naming the item, and nothing is
recorded.
That tab's changes pane matches the report against what git lists, as `s`
reads it: the worktree by its folder with every link resolved. What git
does not list yet is looked for again at every read of the commits window
for 60 seconds from the first report of that folder, then let go, and
aineo says once "aineo: Claude Code announced worktree <folder>, which git
does not list; the changes pane is unchanged" — unless none of its reports
listed a branch, as when an agent done with a worktree it removed says so,
which is let go untold. Reports of a folder looked
for are kept, in order, and taken together once git lists it. At most 32
folders are looked for at once in a tab; a report of one more is not taken,
and nothing is said of it. Before the pane is first shown, aineo watches
nothing, so such a report is looked for when it comes, once the repository
is found, and when the pane is first shown. An agent's folder is resolved
off the main loop, so a folder that does not answer holds no keystroke.
What an agent reports is only compared with what git printed: no git, no
shell and no buffer name is made of it.

                                                          *aineo-changes-hook*
aineo's own hook, a `PostToolUse` hook it gives the Claude Code it starts
in `--settings` (|aineo-report|), never in your settings files, reads each
command of Claude Code's `Bash` tool that ran well and starts with `git`,
the subagents' commands included, and reports the work it makes, as an
agent's call of `announce_work` would, with no label. It reads these plain
forms alone, each optionally after `git -C <folder>`:
    `git worktree add [-b|-B <branch>] <path> [<commit>]`, with `-f`,
        `--force`, `-q`, `--quiet`, `--detach` and `--` allowed — a worktree
        with the branch `-b` or `-B` names, else the branch it checks out
    `git checkout -b|-B <branch> [<start>]`, with `-q` or `--quiet`
        — a branch
    `git switch -c|-C|--create|--force-create <branch> [<start>]`, with
        `-q` or `--quiet` — a branch
    `git branch <name> [<start>]` — a branch
A branch is reported in the worktree the command ran in, by that
worktree's top level. The base is the start point or commit the command
names, else `HEAD`, resolved in the folder the command ran in when the hook
runs. A hook's report adds its branch to that worktree's branches, keeping
the others and the label; it never removes a branch. A worktree no report
holds yet becomes one with that branch and no label, until an agent's call
gives one. A command joined to another (`cd x && git …`, `;`, `|`),
redirected, holding anything the shell expands (`$`, a backtick, a leading
`~`), with another option or more words, whose base git cannot resolve, or
that adds a worktree on no branch (`--detach`), is reported by nothing: the
agent's call still is. The hook runs in the background, never holds or
changes the tool call, says nothing when it fails, and ends itself after 6
seconds whatever the editor does, one held at a prompt say. A failed
command runs no `PostToolUse` hook at all. A worktree Claude Code makes
itself for a subagent (`isolation: worktree`) runs no hook aineo could read
without taking that creation over: the subagent is asked to call
`announce_work` with the absolute path of its worktree's folder instead.

An agent's call for a worktree replaces that worktree's label and every
branch reported of it: a branch it no longer lists leaves the Reported
section, and a call listing no branch takes the worktree out of it. Each
call, and each hook's report that adds a branch, moves the worktree to the
top of its label's worktrees, and its label to the top of the Reported
section, and its age starts again. A worktree new to the reported work,
other than your own, makes the reported work the focused view, from the
default view or from a worktree or branch picked with `s`, that worktree's
whole change chosen, the cursor on its heading, and aineo says once "aineo:
Claude Code started work in Worktree <folder> (<branches>); the changes
pane shows the reported work", <branches> the branches the agent reported of
it, joined by ", ", whatever git lists its HEAD as at that moment, with "tab
<n>: " before it when that tab is not the current one. Your own worktree,
reported as the main checkout's folder for work there, is listed in the
Reported section but changes no view and is told nothing: its work is the
default view's. The changes pane is not brought into view: when it is not
on screen, the next `\g` shows the reported work. The focused view of the
reported work shows each worktree under its own heading, `Worktree <folder>
(<branch>)`, then each reported branch its worktree has not checked out,
`Branch <name>`, in |hl-AineoChangesFilter|, newest first, and below each
its commits, or its note and the line saying its last read failed, as a
worktree or branch shown alone does; nothing else. Enter, `l`, `h` and `gf`
under a branch's lines read that branch, as under a branch picked.

Each reported branch is read from the base its report gives, wherever the
pane shows it, in place of a base of its own, while that base is behind
the branch's tip and descends from the pane's own base; else — the
reported base older than the pane's, unrelated to it, or left behind by a
rebase onto newer work — from the pane's own, so that it never lists
commits the agent did not make. A worktree is read from the base of the
branch it has checked out: its commits from that base to its `HEAD`, and,
under its heading, its files since that base, the uncommitted ones
included. A reported branch its worktree has not checked out has nothing
uncommitted, and its heading says so: `Branch <name> (not checked out:
commits only)`, its commits from its base to its tip and its files between
the two. A report made before reports gave a base is read from a base of
its own, as any worktree or branch is.

While there is reported work, the default view of the commits window starts
with a `Reported` section, above Uncommitted: a tree of the agents' labels,
newest first by their newest report, under each the worktrees reported
with it, newest first, and under each worktree its branches, in the order
reported: >

A label's line gives the label, or `(no label)` for the worktrees aineo's

(|aineo-changes-author-column|). A worktree's line, indented two cells,
gives its folder's name. A branch's line, indented four cells, gives the
branch's name, a `*` when its worktree has it checked out now, `from` and

Enter on that line shows — or `from ?` for a report made before reports
gave one.
Below a branch's line, indented six cells, are its commits from that base,

in |hl-AineoChangesNote|, and Enter on it picks the branch as its line
does. They are read off the main loop, once the pane has read the work of
the branch, and read again each time the pane reads its worktrees: until

under a branch is a commit line like any other: the files window lists its

listed under it, and the diff following the cursor and `h` act as on a
file of any commit. Under a branch another worktree than yours has

that worktree's commits, as in its own section: the files window names the
worktree, and Enter, the diffs, `h`, `gf` and `<S-CR>` act in it, `h`
against that worktree's `HEAD`.
The line under the cursor chooses the files window's list, as any line
does, and Enter on it shows what it names alone, as picking it with `s`

Your own worktree's line, and that of the branch it has checked out, show

each tab keeps its own, and the focused view is kept on disk for each
Claude Code session (|aineo-changes-view-kept|).

                                                  *aineo-changes-view-kept*
The changes pane remembers its focused view for each Claude Code session,
beside the session's base and saves, under `stdpath('state')` in
`aineo/changes-sessions/`, in `<sha256 of the session id>.view.json`. It
keeps what you picked with `s` (a worktree by its folder, a branch by its
name), each reported worktree, by its folder, with its label, when its last
report came and its branches, each with the base reported, and whether the
focused view or the default view showed; nothing else: not the pane the
right column shows, not a cursor, not a commit expanded, not the label
picked, which comes back as all the reported work. The file is written at
once, whole, whenever one of these changes, through a file beside it that
then replaces it, so a crash keeps what the last change left, and not when
nothing changed. Quitting aineo and coming back (the tab reopened at start,
`\S`, a resume of that session) shows the view again as soon as git has
listed the worktrees and the branches: a worktree or a branch that is gone
is dropped, untold, and the default view shows when what the focused view
showed is gone. Reports a file kept before reports were a tree come back
as one: a worktree's report as that worktree with the branch it has checked
out now, and its label; a branch's report as that branch under the worktree
that has it checked out, else under the repository's main checkout. A
restore tells nothing, the reported work included. A session with no view
kept starts with the default view, as does one whose file is missing,
unreadable, malformed, or of another repository; that file is written over
once the view changes. A worktree or branch picked before the pane follows
the session is not given up for the view kept. Two tabs on two sessions
keep two files, and a tab that follows another session shows that
session's view. When a session's Claude Code finds no conversation and
another session takes its place, the view moves with its base and saves.
When the file cannot be written, aineo warns once, "aineo: the changes pane
cannot keep this session's view, and goes on without: <why>".

The file column ~
                                                          *aineo-file-column*
A file you open from one of the three windows — `:edit`, a picker, a jump,
`\f` (|aineo-find|) — moves to a column between Claude's and the right
column, created on first use and reused afterwards; the aineo window keeps
its own buffer. While the file column is open, the three columns take a
third of the screen each. Only file buffers move: help, terminals and
scratch buffers stay where they were opened until `\o` restores the layout.

A diff Enter shows from the changes pane (|aineo-changes|) takes the file
column's window as a file does, and the next file or diff takes its place:
the column keeps one window for both. A changed file that cannot leave that
window keeps it, and the diff opens above it. `\d` closes the diff's window
(|:Aineo-diff|); when it was the file column's last window the column goes,
and the two columns left take half of the screen each again.

Finding a file ~
                                                                  *aineo-find*
`\f` searches the files under the folder the tab's Claude Code works in, or
under the top of the repository that folder is in, and opens the one you pick
in the file column as any file opened from the layout (|aineo-file-column|):
modifiable, written by `:w`, with the cursor in it in Normal mode. It works
from any window of the tab but a floating one, Claude's terminal included,
where its twin `<C-\>f` leaves Terminal mode first (|aineo-terminal-keys|);
from a floating window, a picker's own among them, it starts nothing and
tells you, with one warning, `aineo: a file is found from a window of the tab,
not from a floating one`. A diff shown in the file column gives its place to
the file as it does to any other file. From a tab page that is none of
aineo's it acts on the aineo tab used last and moves you there; with no
aineo tab it tells you, with one warning, `aineo: there is no aineo tab to
find a file in`, and opens nothing (|:Aineo-find|).

aineo has no picker of its own and depends on none. With `find.picker` set to
`auto`, it hands the search to the first of snacks.nvim
(`Snacks.picker.files`), fzf-lua (`files`), telescope.nvim
(`builtin.find_files`) and mini.pick (`builtin.files`) that is installed,
each given the folder as its working directory; the picker's own keys choose
the file and open it in a window of the tab, which the file column's
redirect moves to the file column. Set `find.picker` to one of their names
to use that one alone (|aineo-config-find.picker|). With none installed, or
with the one forced missing, aineo lists the files through
|vim.ui.select()|: the files of the repository, as the git home lists them
(the tracked ones and the untracked ones its ignore rules leave in), and,
whenever git cannot list them (outside a repository, or git failing or
running past its limit), the files found by a walk of the folder; in byte
order, at most 20000. In a search, aineo tells you once, with a warning,
that the picker forced is missing; once, that git could not list the files
of a repository and the list is a walk of the folder; once, when the list
stops at 20000; and once, with an error, when the file picked cannot be
opened, as `:edit` refuses a window whose unsaved buffer cannot be hidden.
A `vim.ui.select` of yours, from a picker plugin, then gives the search its
matching. `:checkhealth aineo` says which picker aineo will use
(|aineo-health|).

Explaining code ~
                                                               *aineo-explain*
`\v` and `\V` ask a Claude Code of its own to explain the code of the current
buffer, a file's, or, in Visual mode, of the lines selected, and show each
explanation as virtual lines right above the line it explains. That Claude
Code is never the session's agent: aineo starts one `claude` process for the
request, in the top of the repository holding the file (else the nearest
folder of the file that exists), and it ends with its answer. From
`claude.cmd` it takes the program, the words before the first one that starts
with `-`, and none of its flags (`--mcp-config`, `--settings`, `--verbose`
and the others). Nothing of the session is used or kept: the request has no
MCP server, none of aineo's settings, and no session to resume
(`--no-session-persistence`). It loads your own Claude Code settings alone
(`--setting-sources user`): the `.claude/settings*.json` of the project, with
its hooks, `env` and `apiKeyHelper`, never apply to it, as `claude -p` asks
no trust of the folder it runs in.

`\v` hands Claude Code the code alone: it has no tool. `\V`, the verbose one,
lets it read the project with `Read`, `Grep` and `Glob`, each without asking,
and no other tool. The prompt gives the file's path from that folder, its
'filetype', the lines asked for, and the buffer's text, unsaved changes
included, each line numbered. Claude Code answers a list of line numbers and
explanations, each tied to the first line it explains, and ends.

An explanation shows above its line as a band of the window's width. A `▎`
stands beside each of its rows in the number column, and the first row's
carries the label `expl` (cut to the cells the number column has, `ex` in four
and nothing in fewer than four, and there is no `▎` where the window shows no
number, sign or fold column). The
band starts at the indent of the explained line (by half the window's text
width at most), each row after `┊ `, wrapped at the window's text width less
that indent, in |hl-AineoExplain|. The number of the explained line shows in
|hl-AineoExplainNr|. The marks move with the edits made to the buffer and
vanish with a line deleted. When the window gets another number, sign or fold
column (a sign appears, 'number' is toggled), the bands are placed again for
the new gutter. A request for some lines replaces the
explanations above those lines alone. Lines outside the range or the buffer,
empty texts and repeats are dropped, and several explanations of one line are
joined in order.

`\vi` and `\VI` ask the same Claude Code, in the same way, for the potential
issues of the code instead of explanations: bugs, unhandled cases, gaps in
error handling, and security or performance risks, each tied to the first line
it concerns, briefly and with no remarks on style. `\vi` hands it the code
alone, `\VI` lets it read the project with `Read`, `Grep` and `Glob`; in
Visual mode they ask about the lines selected. When it finds none, you are
told once: `aineo: no potential issues found`. Issues show as explanations do,
in a namespace of their own and in the look of |hl-AineoExplainIssue|, the
accent being the foreground of |hl-DiagnosticWarn|, `#e5c07b` without one, and
the label `issue`. Since `\v` starts `\vi` and `\vm`, and `\V` starts `\VI`,
Neovim waits 'timeoutlen' for a following `i` or `m` before it runs `\v`, and
for a following `I` before it runs `\V`.

Explanations and issues are shown together on a buffer, and each key toggles
its own kind: pressed in Normal mode on a buffer that shows what the key asks
for, `\v` and `\V` clear the explanations, `\vi` and `\VI` the issues. A
buffer may have one request of each kind running at once: `\vi` while `\v` is
waiting for its answer starts the issues request beside it, and the reverse.
Pressed while a request of its own kind runs for the buffer, a key stops that
request alone and tells you; the other kind's goes on. On a line both kinds
show, the explanation rows sit above the issue rows, whichever answer came
first (not on an empty line, where the one that came first sits above).

While a request runs, one virtual line above the first line asked for, in the
same look without the label, says `┊ ⠋ explaining…` (`┊ ⠋ looking for
issues…`), its spinner advancing every 100 ms, and a badge in the top right
corner of the window the request was made in says ` ⠋ explaining… 12s `: the
seconds it has run. A badge lists the requests that run for its window, in the
order they started, joined by ` · `
(` ⠋ explaining… 12s · looking for issues… 3s `); a part leaves when its
request ends, and the badge closes with the last, unless issues are marked
(|aineo-explain-mark|). The badge, the line and the
timers end with the request, whichever way it ends: its answer, a key that
stops it, `explain.timeout_ms`, an error, the buffer wiped out,
`:Aineo explain clear`, or Neovim quitting; a window closed takes its badge
and the request goes on.

                                                          *aineo-explain-jump*
`]v` and `[v` move the cursor to the line of the next and the previous
explanation or issue of the buffer, of either kind, after and before the
cursor's line, at the line's first non-blank. A count moves that many on, and
the jump wraps around at the ends of the buffer. A line that shows both kinds
counts once. The jump sets the previous context mark first, so `''` and
|CTRL-O| come back, opens the folds that hide the line, and, for a line at
the top of the window, scrolls up to show the explanation above it. In Visual
mode it extends the selection; after an operator it is a charwise motion, as
`d}` is. With nothing to jump to, you are told
once, `aineo: no explanation to jump to`, and the cursor stays. The keys are
local to a buffer: they are mapped, in Normal, Visual and Operator-pending
mode, when the buffer first shows an explanation or an issue, and removed
when it shows none (cleared, toggled off, or every line they were above
deleted). A key you mapped yourself, local to the buffer or global, is never
replaced or removed. They are |<Plug>(aineo-explain-next)| and
|<Plug>(aineo-explain-previous)|, which are mapped in all three modes before
anything is explained.

                                                          *aineo-explain-mark*
`\vm` marks the issues shown above the cursor's line, or above each selected
line in Visual mode, and unmarks those already marked: each issue toggles on
its own. A marked issue shows `✓` where `▎` is, on all its rows, keeping its
label, and its band is blended 25% toward the accent, in
|hl-AineoExplainIssueMarked| and |hl-AineoExplainIssueMarkedGutter|. A line
with no issue tells you once, `aineo: no issue on this line` (`on the selected
lines` in Visual mode); explanations are never marked. The badge of every
window that shows the buffer says, last, how many of its issues are marked
and what sends them: ` 2 issues marked · \s sends ` (`1 issue marked`), with
a request running or not. It names the key that sends as configured (the
`prefix` and `s`, `:Aineo send` when `prefix` is false), follows the buffer a
window shows, and closes at none.

`\s` (|aineo-send|), pressed in a window whose buffer has marked issues, sends
them to the Claude Code of the tab that Send acts on, at once, and leaves
Input as it is. The message is `explain.issues_prompt`
(|aineo-config-explain.issues_prompt|), then one line for each marked issue,
in the order of the buffer: `- <path>:<line>: <text>`, the path of the file
the issue was asked about (kept with the issue, whatever the buffer is called
later) from the folder that Claude Code runs in when it lies inside it, else
absolute, the line the issue is above now, and the text of the issue on one
line. The marks
are cleared once it is sent; the issues stay shown. When Claude Code cannot
take it, Send tells you why as it does for Input, and the marks stay. A buffer
with no marked issue sends Input, and Visual `\s` does what it does everywhere
else. A mark lives with its issue: an edit that deletes its line, a new answer
for its lines, hiding the issues (`\vi`) and `:Aineo explain clear` drop it,
and an answer kept (above) placed again comes unmarked.

Every answer that was shown is kept in memory, for the buffer, by its kind
(explanations or issues), whether it had tools, the lines asked about (the
whole buffer, or the lines of a range) and the text of those lines. Asking
again for the same while the text of those lines reads as it did (a write of
the buffer changes nothing) starts no request: the kept answer is placed at
once, wrapped for the window it is placed in now, and you are told once
`aineo: the earlier answer, the code unchanged (:Aineo explain new asks
again)`. Hide an answer with the key again and the key shows it again. Another
kind, tools or lines start a request; so does a change in the text of the
lines, which drops the answer kept. `:Aineo explain new` asks again whatever
is kept, and keeps the new answer in its place (|:Aineo-explain|). A buffer
wiped out forgets what was kept; nothing is kept on disk.

A request that outlasts `explain.timeout_ms` is stopped and you are told once,
as you are when Claude Code exits with a code other than 0, answers an error,
or answers nothing aineo can read: nothing is shown then. When the text of the
buffer changed while the request ran (a write of it changes nothing), nothing
is shown and you are told to ask again. The Claude Code of every request that
runs is stopped when Neovim quits. The buffer must hold a file: in aineo's own
panes, `\v`, `\V`, `\vi` and `\VI` tell you so (|:Aineo-explain|). The model
is `explain.model` (|aineo-config-explain.model|). Each request is a model
call, billed as Claude Code's own usage is.

The groups are computed from your colour scheme when aineo first needs them
and again after every `:colorscheme` and every change of 'background', and a
group you define yourself is kept, as a default too. The accent is the
foreground of |hl-DiagnosticInfo|, `#61afef` without one. For a terminal
without true colour the groups carry the accent's `ctermfg`, the `ctermbg` of
|hl-LineNr| in the number column, and the `ctermbg` of |hl-CursorLine| behind
the text, none when the colour scheme has none.

Claude's session ~
                                                        *aineo-claude-session*
Each Claude Code session aineo starts gets an id of its own, which aineo
keeps for the directory Claude Code starts in: the working directory of that
start, which `:cd` changes. The next start there — in a new Neovim, or `\o`
once Claude Code has exited — resumes that session (`--resume`), and the
conversation goes on where it stopped. A directory where aineo has started
no session gets a new one (`--session-id`). The ids are kept under
`stdpath('state')` in `aineo/claude-sessions/`, one file per directory that
only you can read and write, and are never removed.

`:Aineo new` (|:Aineo-new|) starts a session on a new id in place of that
resume, once Claude Code has exited, and keeps the new id for the directory
from then on: the next `\o` resumes it.

With several tabs (|aineo-tabs|) the id kept for the directory is the one the
last new session or switch in any tab made, and, whenever the folder's list of
tabs is kept without it, the session at the list's place. The list is another
file and is used only when it holds that id: the first open then starts each
tab on its own session from the list. A tab started so keeps no id for the
directory, except that the new session which takes the place of a session
Claude Code has no conversation for is kept, as it is for any start.

A start that would resume first asks Claude Code where the session runs, by
`claude agents --json` for the directory (|aineo-limits|), and Claude's
window stays empty, drawing its status line, until Claude Code answers: for
up to 5 s, usually far less. Claude Code then starts in that same window. A
session open in another interactive Claude Code is warned of, in one line,
`aineo: this session is also open in another Claude Code`, and resumed all
the same. A list that cannot run, fails or does not answer in time tells
nothing, and Claude Code resumes the session. A start on a new session lists
nothing and starts Claude Code at once, as does the new session that takes
the place of a resume with no conversation (below). While Claude's window
waits, Send refuses as it does at any start before Claude Code is ready
(|aineo-send|), and quitting Neovim has no Claude Code to stop.

A session that runs in Claude Code's background service is attached to
instead of resumed, at once and without a question:
Claude's window runs `claude attach` for it and shows its conversation, and
aineo tells `aineo: attached to a background session (no Report)`. Claude's
status line reads `<name> (attached) — <folder>` while it runs. The attached
session keeps the arguments it was started with, so what aineo gives Claude
Code at its own start is missing: the session hooks, so aineo follows no
switch made inside it (|aineo-report|), the Report server, the instructions
appended to the system prompt, and the tools aineo pre-allows, for which
Claude Code may ask. The session stays the one kept for the directory, so
the next start lands in it again while it runs; once it no longer runs, the
start resumes it as above. `\N` (|:Aineo-new|) gives a new session there
too: it detaches the attached Claude Code and starts a new one in its place,
and writes no `/clear` into the background session. When the list shows
the session both open in another interactive Claude Code and in the
background, aineo attaches and warns of nothing. An attach that exits with
a failure within 2 seconds of its launch did not take, say because the
session ended between the list and the attach: aineo tells `aineo: the
attach failed; resuming the session` and resumes it in its place
(|aineo-limits|). Quitting Neovim detaches an attached Claude Code with
`Ctrl+Z` and never presses `Ctrl-C`, which would cancel the background
session's running turn (|aineo-limits|); the session runs on.
Wiping Claude's terminal hangs it up, which leaves the session running too.

A session in which nothing was sent leaves no conversation, and Claude Code
cannot resume it: it prints "No conversation found with session ID: …" and
exits. aineo then starts a new session in its place, in the windows that
showed it, and keeps its id instead. The new session takes over what aineo
kept for the one it replaces — the Report's records, Input's draft, and the
changes pane's base with its saves — and panes that showed that session go on
showing the same under the new one from that moment, before it is ready: the
Report's lines and cursor, Input's text, cursor and undo, and the changes
pane's lists and marks stay as they were. Nothing is handed over while a
Claude Code aineo knows of still runs on that session (|aineo-limits|). At
each start that follows a session in which nothing was sent, Claude Code
2.1.283 shows nothing for about a second, then the message for about half a
second before the new session takes its place. If you were typing in
Claude's window you are left in Normal mode there: `\c` puts you in the new
prompt. A resumed Claude Code that exits any other way shows its exit as
usual, and its id stays kept. A resume that fails some other way — a Claude
Code that words the message otherwise, or exits with another code — then
fails the same way at each start there: removing `aineo/claude-sessions/`
under `stdpath('state')` makes every directory start a new session.

                               *b:aineo_session_name* *b:aineo_session_folder*
Claude's window draws a status line of its own for Claude's terminal: the
session's name, then the folder Claude Code started in, written from your
home directory, as in `Claude Code — ~/projects/app`. The name is Claude
Code's own for the session, as Claude Code writes it in its terminal title
(`b:term_title`), without the status glyph before it, such as `✳`: Claude
Code 2.1.292 titles a session `✳ Claude Code`, and one started with
`--name {name}` `✳ {name}`. It reads `Claude Code` until Claude Code sets
a title, while the title is empty, and once Claude Code has exited,
however it ended; the status line follows each new title by itself. The
name and the folder are drawn as written, a `%`, digits alone, a leading
comma or space among them; a control character shows in caret notation,
as `^[` for Escape, and a name longer than about 4 KB loses its start.
The folder is the directory Claude Code started in, whatever `:cd` and
`\o` do while it runs; a Claude Code `\o` starts once the last has exited
starts in the working directory then, and the folder is that one. The
status line is set for Claude's terminal as `:setlocal` sets it: Claude's
window draws it, and so does a window split from it or any window you show
Claude's terminal in; another buffer in those windows, and your other
windows, keep your own. It replaces the whole of Neovim's default status
line there, the terminal's `term://` name, its ruler and its exit code
with it; the terminal keeps its name, which `:ls!` shows, since it is not
a listed buffer. For a status-line plugin, the name and the folder are
kept, current, on Claude's terminal as `b:aineo_session_name` and
`b:aineo_session_folder`. See |aineo-limits| for what can replace it.

                                                                 *aineo-links*
A link in Claude's terminal opens in aineo when you double-click it, in
Terminal or Normal mode, or press |gx| on it in Normal mode. A link is a
path, found as the Report finds one (|aineo-report|), with a `:<line>` or a
`#L<line>` at its end naming its line; a `file://` address; or a web
address. A relative path is looked up in the folder Claude Code started in;
a path that starts with `~/` is looked up in your home folder, and a `~`
anywhere else in a path, or `~name/`, is left as written.
A regular text file opens in the middle column, at its line, as `<S-CR>`
opens a file from the changes pane, whether it lies in the project or not;
a file is text when its first 8 KiB hold no NUL byte. Anything else goes to
your system, through |vim.ui.open()|: a file that is not text, such as an
image or a PDF, a directory, and a web address. A link that names nothing
that exists opens nothing, and you are told so once. A double-click on no
link does what Neovim's own does: in Normal mode it selects the word, and
in Terminal mode it reaches Claude Code. A ⌘-click is not aineo's: see
|aineo-limits|.

aineo follows a switch you make inside Claude Code: `/clear`, `/resume`
and `/branch` each put Claude Code on another session, and the Report,
Input's draft (|aineo-draft|) and the changes pane (|aineo-changes|) then
show that session's, whichever pane is shown: the windows that show them
at once, a hidden pane when it is next shown. `/clear`'s new session has
an empty Report and an empty Input, and `HEAD` then as its base; `/resume`
back to a session brings its Report, its draft and its base back. The next
start in that directory resumes the session Claude Code was last on in
aineo's terminal there. Claude's status line follows too, through Claude
Code's title, but a title is not a session's id: two sessions can share
one. Claude Code tells aineo of a switch through the hooks aineo gives it
at each start (|aineo-report|): Claude Code 2.1.292 ends the session it
leaves (`SessionEnd`), then starts the next (`SessionStart`). `/compact`
stays on the same session, and changes nothing. A conversation Claude Code
moves to another process of its own — its background service runs it there
on a new session id, under the hooks of aineo's start — is followed as a
switch too, while aineo's own Claude Code runs: the tab whose start gave
those hooks follows the new session, and the reports from that process
reach its Report. A process Claude Code started with another tab's hooks,
or with none of aineo's, moves nothing. Where hooks do not run,
aineo follows the session it started: see |aineo-limits|. Two Neovims in
one directory resume the session of the last switch in either. A switch
made by a Claude Code whose editor is gone — it quit while Claude Code ran
on — is kept all the same, as the session the next start in that directory
resumes. A Neovim that follows a session by a claim (|:Aineo-claim|)
follows its switches too, and its claim moves with them; while it follows
a session its own terminal does not run, a switch in its own Claude Code is
kept for the directory and leaves its panes where they are. aineo ignores
a conversation you ran in a plain terminal in the same directory.

The panes follow the session a start of Claude Code is on once Claude Code
is ready for input the first time, and every switch after that; until
then they show what they showed before, and what you type in Input is
kept there. At an editor's first start, that is the working directory's
Report and draft, which the session takes when it has none of its own.
When it has its own, the panes show those, and what you typed in Input
meanwhile leaves Input and stays the directory's draft (|aineo-draft|).
The Report is drawn again then, its cursor on its first line, even when it
shows the same reports. The changes pane takes the session's base then too
(|aineo-changes|). A start that is never ready — a trust dialog answered
"No, exit", a Claude Code that exits before its input box settles — is not
followed, and nothing moves. A resume Claude Code finds no conversation
for is never ready either. The new session that takes its place (above)
takes over what the resumed session kept, at once: panes that showed the
resumed session follow the new one from then on, showing what they showed,
and its readiness changes nothing in them; panes that showed another session
follow it once it is ready, showing what it took over. At an editor's first
start it takes the working directory's Report and draft only when the
resumed session kept none (|aineo-limits|). While this Neovim follows a
session its own terminal does not run (|:Aineo-claim|), a start of its
Claude Code, ready or not, leaves the panes on the claimed session, until
`:Aineo claim` without an id returns them.

Input's draft ~
                                                                 *aineo-draft*
What you write in Input is kept as a draft, one per Claude session, beside
the Reports: under `stdpath('state')` in `aineo/drafts/`, in a file only
you can read and write, named `session-` and the SHA-256 of the session's
id. It is saved a second after each change, at once when Input becomes
empty, as Send leaves it, and, for a change not saved yet, when Neovim
quits. Nothing asks you anything at quit, and a crash loses at most the
last second's typing. Until aineo follows a Claude session, the draft is
the working directory's, in a file named by the directory's SHA-256; the
working directory is the one of the first time the layout opened, for the
editor's life.

When aineo follows another session, a change not saved yet is first saved
as the draft of the session it followed until then, and the new session's
draft then takes the place of whatever Input holds — or Input is emptied,
for a session with no draft. The text that leaves Input is not lost: it
comes back when aineo follows its session again. When it cannot be saved,
Input keeps it, as that session's draft, and you are told so at each
switch. A session's draft that cannot be read is told at each switch to
that session, and Input is emptied: aineo never replaces a session's
draft it could not read, so what you then type is not saved, and you are
told so at your first change after each such switch. Until the new draft
is in Input — Neovim may hold the swap until it is done with what it is
doing — what you change in Input is still the old session's. The swap is
not a change of yours: `u` does not take it out, and no `u` reaches a
change or a Send made before it. It is not saved either: a draft another
Neovim keeps for that session stays as it left it. A session that takes
the place of one whose resume found no conversation is no switch for an
Input that showed that session: Input keeps its text, cursor and undo, a
change not saved yet is saved first and goes with the draft, and what you
type next is the new session's (|aineo-claude-session|). The first session
aineo follows in an editor, other than one claimed by its id
(|:Aineo-claim|), takes the working directory's draft, when it has none of
its own; an Input that holds that draft already is then left
as it is, with no swap, and `u` still reaches what you typed before. A
directory's draft written after that is taken by the next editor that
first follows a session with no draft of its own, and is not shown
otherwise. A draft that cannot be moved so is told once
as a warning, and the session keeps its own.

The draft comes back into an empty Input: the first time the layout opens
in this editor, and again once Input's text was dropped — `:bwipeout`,
`:bdelete`, `:edit!` — as soon as Input is shown again. Its coming back is
not a change of yours: `u` does not take it out. Coming back so, it never
replaces text you have written — only following another session does —
and an Input that Send emptied stays empty.

Two Neovims on one session, or in one working directory before aineo
follows a session, share one draft, and the last change in either wins: a
Neovim that quits with no change unsaved leaves the draft as the other left
it.

A change not saved yet is saved as you quit with `:quit`, `:qall`,
`:wqall`, `:xall` or `ZZ`, and again, when that save failed or did not
run, as Neovim unloads Input on its way out. `:cquit` has only that second
save, which a |BufWinLeave| or |BufUnload| handler that fails before
aineo's can skip. A |QuitPre| handler that fails before aineo's — a
Vimscript `:throw`, or any error when the quit runs from Lua — skips both
saves, for every quit that fires |QuitPre|. Either way, the draft then
holds what was saved a second after each change. A Neovim ended by a
signal — its terminal window closed, `kill` — saves nothing as it ends:
like a crash, it loses at most the last second's typing.

A draft that cannot be read, put into Input or written is told once as a
warning; a session's draft that cannot be read is told as above. While
you type in Insert, Replace or Terminal mode — in Input or
in Claude's terminal — the warning waits until you leave that mode, with
`<Esc>`, `CTRL-C` or `CTRL-\ CTRL-N`, so that its prompt never takes a key
you type there.

Restoring ~
The three windows keep their sizes: the layout puts its proportions back
when a window closes, when the editor is resized and when you enter its tab.
`\o` (|:Aineo-open|) restores the layout while any of its windows is left:
it recreates the windows that were closed, in their places, and keeps the
pane the right column shows (|aineo-panes|). The layout lives in one tab;
from another tab, `\o` moves you to it.

4. COMMANDS                                                   *aineo-commands*

                                                                      *:Aineo*
:Aineo {subcommand}	Runs one of aineo's actions. Completion offers the
			subcommands, the panes after `pane`, after `claim` the
			sessions that have a running Claude Code in the
			directory this Neovim started in (|:Aineo-claim|), and
			after `tab` `new` and the number of each tab page
			(|:Aineo-tab|), and `close` after `diff`
			(|:Aineo-diff|), and `tools` and `clear` after
			`explain` (|:Aineo-explain|), and `check`, `states`,
			`preview`, `new` and `pack` after `office`, the names
			of the office packs found after `check`, `states`,
			`preview` and `pack`
			(|:Aineo-office|). Without one of them, or
			with anything else, it tells you, with one error,
			which ones it takes. Only `explain` takes a range;
			given one for another subcommand, it tells you so.

                                                                 *:Aineo-send*
:Aineo send		Sends Input to Claude (|aineo-send|). It takes no
			range: `:'<,'>Aineo send` tells you, with one error,
			that only `:Aineo explain` takes a range.
			A selection is sent by `\s` in Visual mode
			(|aineo-v_\s|).

                                                                 *:Aineo-open*
:Aineo open		Opens the layout around Claude's terminal, starting
			Claude Code when it is not running — again after it
			has exited — or restores the layout while it is open.

                                                               *:Aineo-report*
:Aineo report		Shows the agent pane, then moves the cursor to the
			Agent Report.

                                                                *:Aineo-input*
:Aineo input		Shows the agent pane, then moves the cursor to Input.

                                                               *:Aineo-claude*
:Aineo claude		Moves the cursor to Claude's terminal and enters
			Terminal mode there, so that the keys you type next
			reach Claude Code: its prompt, or the dialog it shows.
			Once Claude Code has exited it stays in Normal mode,
			since a key typed in Terminal mode would close the
			terminal and its exit with it.

When Claude Code exits while you are in its terminal in Terminal mode — after
`/exit`, say, or as it fails at its start — aineo puts you back in Normal mode
there, so that its exit stays on screen and the next key you type is a
Normal-mode command. `i`, `a` and |:startinsert| leave that terminal in Normal
mode too. Any other terminal of yours keeps Neovim's own behaviour.

`report`, `input`, `claude` and `pane` open the layout first when their window
is gone (for `pane`, either window of the right column, or a buffer of the
pane wiped or deleted; for `report` and `input` while the changes pane shows,
the Report or Input wiped or deleted too), around Claude's terminal as it is —
its exit on screen when Claude Code has exited. They start Claude Code only
when there is no terminal to show: before the first start, or again, in a new
terminal, once the terminal was wiped (|:bwipeout|). Wiping it from Claude's
window closes that window; a window Neovim cannot close, such as its last one,
stays on an empty buffer until `claude` opens the layout there again —
`report` and `input` do so only when their own window is gone too. A file
opened in Claude's window as the terminal is wiped stays in view, and moves to
the file column when the layout opens again. Of the actions, only `open`
and `new` restart an exited Claude Code, `open` on the session kept for the
directory and `new` on a new one (|:Aineo-new|); aineo restarts one by itself
only in place of a resume Claude Code has no conversation for
(|aineo-claude-session|).

                                                       *:Aineo-claude-numbers*
:Aineo claude-numbers	Hides the line numbers of Claude's window, 'number'
			and 'relativenumber', when it shows either, and shows
			them again as they were when aineo last hid them,
			whichever buffer Claude's window showed then, when it
			shows none: 'number' alone when aineo has hidden none
			before. It acts on the buffer Claude's window shows,
			whichever it is, changes no other window, and leaves
			the cursor and the mode where they are; from another
			tab it acts on Claude's window in the layout's tab.
			Without a Claude window — the layout or Claude's
			window closed, or Claude's window left without its
			terminal once the terminal was wiped, on an empty
			buffer or on a file Neovim showed there — it changes
			nothing and warns you once.

			aineo keeps your choice until the editor quits, and
			gives it to every Claude terminal new to Claude's
			window — Claude Code restarted by `open` or `new`,
			the new session that takes the place of a resume with
			no conversation, a wiped terminal started again, a
			terminal you bring back there yourself — and to
			Claude's window when it is opened anew. Numbers you
			set yourself in Claude's window afterwards stay as
			you set them, until another terminal or a new window
			comes. Pressed while Claude's window shows another
			buffer, it hides or shows that buffer's numbers, and
			Claude's terminal gets the same when it next comes
			back there; numbers it hides there are also those the
			next toggle shows Claude's terminal again, in place of
			the terminal's own. A file opened from Claude's window
			keeps your own numbers.

                                                             *:Aineo-sessions*
:Aineo sessions		Lists the sessions Claude Code lists for the folder
			(|aineo-tabs|), which `:cd` does not change, and
			offers them in |vim.ui.select()|, one row each:
			the session's name, or the first eight characters of
			its id, its kind, `interactive` or `background`, and
			its status. The row of a session a tab of this Neovim
			shows says `[tab {n}]`, with the number of that tab
			page, and that of every other session some process
			runs says `[running elsewhere]`, in another terminal
			or in Claude Code's background service, and that of a
			session started in another directory than the folder
			says `[another folder]`. A session whose process has
			ended, a background one, has no mark. Only an entry
			whose session id is one Claude Code gives is listed.
			It takes no word, and only one list is read at a
			time: pressed again meanwhile, it says so and starts
			nothing.

			The list comes from `claude.cmd` followed by `agents
			--json --cwd {folder} --all`, which aineo runs
			without waiting for it (|aineo-config-claude.cmd|):
			it is stopped after 5 seconds, or after 1 MiB of
			output. A `claude.cmd` that holds `--add-dir` or
			`--mcp-config` makes Claude Code refuse `agents`, and
			aineo tells you so in Claude Code's words.

			A pick:
			- of a row a tab shows, the current tab's own
			  included, moves to that tab and starts nothing;
			  when several tabs show it, to the lowest numbered,
			  or nowhere when the current tab is one of them.
			- of a row whose Claude Code a tab just closed still
			  stops opens no tab: aineo tells you to pick it
			  again in a moment.
			- of a row started in another folder, or a row running
			  in the background with no short id for `claude
			  attach`, opens no tab and tells you why.
			- of a row running elsewhere reads the list again and
			  opens a new tab at the end on that
			  session. A session running in Claude Code's
			  background service is attached to, as a start
			  attaches (|aineo-claude-session|): `claude attach`,
			  none of aineo's arguments, `(attached)` in the
			  status line, and `aineo: attached to a background
			  session (no Report)`. A session open in another
			  interactive Claude Code, which `claude attach` does
			  not take, is resumed instead, unless the list also
			  shows it in the background, which is attached to,
			  and you are told
			  `aineo: this session is also open in another Claude
			  Code`: both terminals then drive it.
			- of any other row reads the list again, as the menu
			  may have been open for long, and opens a new tab
			  that resumes the session only if it is still listed
			  and still stands for a new tab.
			A tab a pick opens is a tab as `:Aineo tab new` opens
			one (|:Aineo-tab|), with a Claude Code on the session
			in the folder, and the cursor lands in its Claude
			window in Terminal mode. The session becomes the one
			the next start lands in (|aineo-claude-session|). The
			current tab is not touched: nothing is written into
			its prompt, whether the prompt holds text or not, and
			its Claude Code goes on.

			It lists nothing, and tells you once, with a warning
			starting `aineo: no session list`, while the current
			tab's Claude Code is not ready for input — it has not
			started, is starting or behind a dialog, or has
			exited, as for Send (|aineo-send|) — while a claim of
			another session holds (|:Aineo-claim|), when `claude
			agents` fails, is stopped or prints what is not a
			JSON list, and when Claude Code lists no session. A
			pick made after the state changed tells you the same,
			starting `aineo: not switched`. What it cannot know
			is in |aineo-limits|.

                                                                  *:Aineo-new*
:Aineo new		Starts a new Claude Code session. It takes no word.
			- When no Claude Code runs in this Neovim, because it
			  has exited, has not started here, or its terminal
			  was wiped, it starts one on a new session id
			  (`--session-id`). It lists no session and resumes
			  none, and keeps the new id for the directory, so
			  that `:Aineo open` resumes it after the next exit
			  (|aineo-claude-session|). The layout opens, or is
			  restored, around the new terminal as `:Aineo open`
			  does, and the cursor moves to Claude's window in
			  Terminal mode (|:Aineo-claude|). The Report, Input's
			  draft and the changes pane follow the new session,
			  empty, with `HEAD` as its base, once it is ready
			  (|aineo-claude-session|). Claude Code's exit leaves
			  Terminal mode in Claude's window, so press `\N`
			  there: the twin `<C-\>N` acts in Terminal and Insert
			  mode only.
			- When Claude Code runs, is ready for input and the
			  prompt shows no text, it moves the cursor to
			  Claude's window in Terminal mode and writes `/clear`
			  as a bracketed paste, as Send writes text
			  (|aineo-send|), and Enter, in one write. Claude Code
			  switches to a new session and aineo follows it
			  (|aineo-claude-session|), and the cleared session
			  stays resumable. In a window attached to a
			  background session (|aineo-claude-session|) nothing
			  is written: the attached Claude Code is detached by
			  `Ctrl+Z` and a new session starts in its place, kept
			  for the directory, with the prompt checked as
			  above.
			The prompt shows text unless the input box is one line
			and Claude Code's cursor sits right after its `❯`: the
			grey example it draws in an empty prompt is not text.
			Aineo never clears the prompt.
			Nothing is written and nothing is started, the cursor
			goes back to the window and the mode it came from, and
			you are told once, with a warning starting `aineo: no
			new session`, when the prompt shows text (clear it,
			then press the key again), when Claude Code is
			starting, behind a dialog or waiting for the session
			list of a resume, when a claim of another session
			holds (|:Aineo-claim|), and when Claude's window does
			not enter Terminal mode within a second. While a turn
			runs the prompt is on the screen and `/clear` is
			written all the same; what Claude Code does with it
			then is in |aineo-limits|.

                                                                 *:Aineo-pane*
:Aineo pane {pane}	Shows {pane} in the right column, `agent`,
			`changes`, `terminal`, `run` or `explorer`
			(|aineo-panes|), and moves the cursor into it: into
			the Report for `agent`, into the commits window for
			`changes`, into the tab's shell for `terminal`, in
			Terminal mode, into the tree for `explorer`
			(|aineo-explorer|).
			`terminal` starts the shell, in the folder, when the
			tab runs none. `run` shows the stack and moves the
			cursor to its bottom window when processes run, and
			otherwise, or with the cursor in the stack, asks for
			a command and runs it (|aineo-run|). When the pane
			shows already, the layout stays
			as it is (the changes pane is read again, and
			`changes` from one of its two windows switches it
			between the default view and the worktree or branch
			shown alone, |aineo-changes-s|), unless one of
			its windows shows the other pane's buffer there:
			it then shows {pane}'s buffer there. The cursor
			moves all the same. Without a pane, or with
			anything else, it tells you, with one error,
			which ones it takes.

                                                                  *:Aineo-run*
:Aineo run shell	Adds an interactive shell, your 'shell', to the
			bottom of the run pane's stack, in the folder aineo
			started in and with `$AINEO_CHILD` set, shows the pane
			and moves the cursor into the shell, in Terminal mode
			(|aineo-run|). Without the word, or with anything
			else, it tells you, with one error, what it takes.
			`\X` and, in Terminal mode and in Insert mode,
			`<C-\>X` do the same (|aineo-keys|).

                                                                *:Aineo-claim*
:Aineo claim [{id}]	Claims a Claude session for this Neovim: each report
			of that session comes here first, even while the
			Neovim that started its Claude Code answers, until
			another Neovim claims it (|aineo-report-claims|).
			With {id}, the Report, the changes pane and Input's
			draft follow that session, at once in the windows
			that show them, while this Neovim's own Claude
			terminal runs on its own session; nothing is sent to
			Claude Code. Completion offers the sessions that
			have a running Claude Code in the directory this
			Neovim started in, which `:cd` does not change; any
			id of Claude Code's form is taken, running or not,
			and shows that session's kept Report and draft. Any
			other word is refused with one error naming it.
			Without {id}, it depends on what this Neovim
			follows:
			- its own Claude terminal's session: it claims that.
			- a session claimed by its id: it returns the Report,
			  the changes pane and Input to its own terminal's
			  session, and claims that. The claimed session's
			  draft is kept as that session's, and Input shows
			  its own session's draft again.
			- its terminal runs no session, as before Claude
			  Code has started here: it warns once and changes
			  nothing. `:Aineo claim {id}` follows another
			  session, and `:Aineo open` starts Claude Code.
			Until the start of this Neovim's Claude Code is
			ready, it warns once that Claude Code is not ready
			yet, and changes nothing. `:Aineo claim` with the id
			of this Neovim's own session does what it does
			without one. It takes at most one word.

			While this Neovim follows a session its own
			terminal does not run, a report of its own Claude
			Code is not shown here: it goes to another Neovim
			that shows that session, or else is kept — with the
			working directory's records, unshown, until this
			Neovim's own session has taken them, and on disk
			for its session after that (|aineo-report-claims|).
			`:Aineo claim` without an id then shows it with the
			directory's records. A switch in its own Claude
			Code, and a start of it, are kept for the directory
			(|aineo-claude-session|) but leave the panes on the
			claimed session; and Send sends nothing
			(|aineo-send|). A claim never moves the working
			directory's records or draft: they stay the
			directory's until this Neovim first follows its own
			terminal's session. A file saved while the claim
			holds is marked for the claimed session
			(|aineo-changes|).

With tabs (|aineo-tabs|) `:Aineo claim` acts in the current tab: the Report,
the changes pane and Input of that tab follow the claimed session. When
another tab of this Neovim runs the session {id} names, `:Aineo claim {id}`
moves you to that tab instead and claims nothing.

                                                                  *:Aineo-tab*
:Aineo tab new		Opens a tab page at the end with a tab of
			aineo's in it (|aineo-tabs|): a layout of its own
			around a Claude Code started in the folder on a new
			session id, as |:Aineo-new| starts one when no Claude
			Code runs, and the cursor in Claude's window in
			Terminal mode (|:Aineo-claude|). With no aineo tab
			yet it opens the first one in the current tab page.
			When Claude Code cannot start, the tab page it made
			is closed again and aineo tells you why.
:Aineo tab close	Closes the current tab (|aineo-tabs|), while another
			aineo tab remains: its Claude Code is stopped as
			quitting stops it, by its keys or, for one attached
			to a background session, by `Ctrl+Z` alone, so that
			the session runs on; its Input's draft is saved, its
			copies are let go, its entry among the running
			editors is removed, and its tab page closes, without
			holding the editor. Its Report, draft and changes
			base stay on disk, and |:Aineo-sessions| brings the
			session back in a new tab. The cursor lands in the tab
			page Neovim makes current. On the last aineo tab it
			quits Neovim as `:qa` does, which Neovim refuses
			while a buffer has unsaved changes, stopping nothing.
			From a tab page that is none of aineo's it closes
			nothing and warns you once, `aineo: this tab holds no
			Claude Code session`.
:Aineo tab {n}		Moves to the tab page numbered {n}, an aineo tab or
			not, as `{n}gt` does. The cursor lands where it was in
			that tab page, in Normal mode. With no tab page of
			that number nothing moves, and aineo tells you once,
			with a warning, `aineo: no tab {n}`. With any word
			but `new`, `close` or a number it tells you, with one
			error, what it takes.

                                                                 *:Aineo-diff*
:Aineo diff close	Closes the diff the changes pane shows in the
			middle column (|aineo-changes|): every window of the
			current tab page that shows one of the pane's
			`aineo://` diffs, from any window, whatever the cursor
			is in, and no other window or buffer, a file of yours
			included. A diff is wiped once hidden, so the next
			Enter, `l` or `h`, or a move of the cursor in the
			files window, shows it again. The cursor stays where
			it was, unless it was in the diff: it goes to
			the changes pane's files window, on the line it was
			on, when that window is open; with the pane not on
			screen it goes where Neovim puts it when a window
			closes, and the layout puts its columns back as for
			any closed window (|aineo-file-column|). A diff that
			is the only window of its tab page is not closed.
			From a tab page that is none of aineo's it acts on
			the aineo tab used last and moves you there
			(|aineo-tabs|); with no aineo tab it makes none.
			With no diff to close aineo tells you once, `aineo:
			no diff to close`. With any word but `close` it
			tells you, with one error, what it takes. `\d` and,
			in Terminal mode and in Insert mode, `<C-\>d` do the
			same (|aineo-keys|).

                                                                 *:Aineo-find*
:Aineo find		Searches for a file under the folder the tab's Claude
			Code works in, or under the top of the repository that
			folder is in, with the picker `find.picker` names
			(|aineo-config-find.picker|), and opens the file
			picked in the file column, from any window of the
			tab but a floating one (|aineo-find|). From a tab page
			that is none of aineo's it acts on the aineo tab used
			last and moves you there (|aineo-tabs|); with no aineo
			tab it makes none and tells you, with one warning,
			`aineo: there is no aineo tab to find a file in`. With
			any word after `find` it
			tells you, with one error, what `:Aineo` takes. `\f`
			and, in Terminal mode and in Insert mode, `<C-\>f` do
			the same (|aineo-keys|).

                                                                 *:Aineo-zoom*
:Aineo zoom		Zooms the window of the right column the cursor is
			in to the rows the column's other windows can spare,
			they keeping 'winminheight' lines each (one by
			default), or, when that window is zoomed, gives
			every window the height it had (|aineo-zoom|). With
			the cursor in another window of the column, the zoom
			moves there. It acts on the aineo tab of the current
			tab page and makes none: with the cursor in none of
			the windows aineo shows in the right column,
			including a window you split off it by hand and a
			tab page that is none of aineo's, it changes nothing
			and tells you, with one warning, so. Under the
			terminal pane, whose one window fills the column, it
			changes nothing and tells you nothing. With any word
			after `zoom` but `full` it tells you, with one error,
			what `:Aineo zoom` takes. `\z` and, in Terminal mode
			and in Insert mode, `<C-\>z` do the same
			(|aineo-keys|).

                                                            *:Aineo-zoom-full*
:Aineo zoom full	Zooms the window the cursor is in to the whole tab
			page, every other window shrinking to the least size
			Neovim gives a window, or, when that window is zoomed
			fully, gives every window the size it had
			(|aineo-zoom-full|). With the cursor in another
			window, the zoom moves there. It acts on the aineo
			tab of the current tab page and makes none: from a
			tab page that is none of aineo's, or a floating
			window, it changes nothing and tells you, with one
			warning, so. With any word after `full` it tells
			you, with one error, what `:Aineo zoom` takes. `\Z`
			and, in Terminal mode and in Insert mode, `<C-\>Z`
			do the same (|aineo-keys|).

                                                             *:Aineo-explain*
:[range]Aineo explain [issues] [tools] [new]
			Explains the code of the current buffer, a file's, or
			of the lines of [range], with a Claude Code of its own
			(|aineo-explain|). With `issues` it asks for the
			potential issues of that code instead. With `tools`
			that Claude Code may read the project with `Read`,
			`Grep` and `Glob`; without, it has the code alone.
			`\v`, `\V`, `\vi` and `\VI` do the same
			(|aineo-keys|). Asked while a request of its kind runs
			for the buffer, it stops that request; asked for the
			whole buffer while it shows what it asks for, it
			clears that. When an earlier answer for the same
			kind, tools and lines is kept and their text is
			unchanged, it places that answer and starts no
			request; `new` asks again whatever is kept or shown,
			and keeps the new answer. The words are written in
			this order, each at most once. In a buffer that holds
			no file it tells you, with one error. With any other
			word it tells you, with one error, what it takes. The
			only subcommand of `:Aineo` that takes a range.

:Aineo explain clear
			Removes every explanation and every issue the current
			buffer shows, and stops the request that runs for it,
			if any.

                                                               *:Aineo-office*
:Aineo office		Shows the office over the right side of the layout, at
			once (|aineo-office|). It acts on the aineo tab of
			the current tab page and makes none: with no aineo
			tab it tells you, with one warning, so. Asked while
			the office shows, it does nothing. With
			'termguicolors' off, or 'ambiwidth' `double`, it shows
			nothing and tells you, with one warning, why
			(|aineo-office|). `\O` and, in
			Terminal mode and in Insert mode, `<C-\>O` do the
			same (|aineo-keys|).

                                                         *:Aineo-office-check*
:Aineo office check [name]

			no aineo tab. With any other word it tells you, with

                                                        *:Aineo-office-states*
:Aineo office states [name]
			Lists what an office pack draws, in a window under

			`waiting`, `resting`) and of the 24 states,

			pack is the one named, or, with no name, the one

                                                       *:Aineo-office-preview*
:Aineo office preview [name]
			Shows the office over the right side of the layout
			with every state of the vocabulary acted out in turn,
			nine seconds each, the state and its number named on
			the first row, over scripted agents: the main agent,
			and the others a state needs to be seen, such as a
			subagent arriving as it delegates, subagents at work
			as it waits, and everyone idle for the random life.
			The pack is the one named, or, with no name, the one
			`office.pack` names (the first of a list). One that is
			not found is told, with one error, and not replaced by
			the default pack; the office that shows then stays as
			it is. The preview follows no transcript and watches
			no file, calls no Claude and spends no token; it takes
			the place of the office that shows and closes as the
			office does, when the cursor enters the right side
			(|aineo-office|). Like `:Aineo office`, it acts on the
			aineo tab of the current tab page and makes none, and
			it shows nothing, and tells you why, with
			'termguicolors' off or 'ambiwidth' `double`.

                                                           *:Aineo-office-new*
:Aineo office new {name}
			Makes the office pack {name} as a copy of the default
			pack, in `aineo-office/{name}/` of Neovim's
			configuration directory (|stdpath()|), with {name} as
			the pack's name, each file writable by you, and tells
			you where it is. Set `office.pack` to {name} to draw
			it, and use `:Aineo office check` and
			`:Aineo office preview` while you change it
			(|aineo-office-packs|).
			It refuses, with one error, a folder of that name that
			exists, which it leaves as it is; a name that any pack
			found has, whatever the case of its letters (`default`
			among them, which every pack falls back to, and
			`Default`, which a disk that ignores case reads as
			it); a name that is not letters, digits, `_` and `-`;
			and a default pack that holds a link, since a pack is
			made of files. A copy that fails is removed. When the
			configuration directory did not exist as Neovim
			started, it is not on 'runtimepath' yet: the pack is
			made there, and `:Aineo office check` and
			`office.pack` find it after a restart. It needs no
			aineo tab.

                                                          *:Aineo-office-pack*
:Aineo office pack [name]
			Makes every office draw the pack {name} from now on,
			in this Neovim: the office of each tab, at once if
			it shows (it is shown again with the pack), else the
			next time it shows. It stands in place of
			`office.pack` (|aineo-config-office.pack|) for as long
			as this Neovim runs, and nothing is written to disk.
			The pack is loaded and checked first, with the art
			files of `office.pieces` over its pieces; a pack not
			found, or that cannot be used, is told with one error
			naming it, and nothing changes: the office that shows
			stays. A preview in progress is not replaced
			(|:Aineo-office-preview|). With no name it tells you,
			with one message, the pack in use and whether it comes
			from this command or from `office.pack`. {name} is
			completed from the packs found. It needs no aineo tab.

When an action fails — `claude.cmd` is not executable, say — aineo tells you
once, with one error message starting with `aineo:`, and opens nothing.

when the editor has started — stays yours, and aineo maps the others: with
your own `\s` in Normal mode, aineo still maps `\s` in Visual mode, and the
other way round. A mapping local to a buffer is not counted: it wins in its
own buffer only. A mapping you make later replaces aineo's. A mapping that
only overlaps aineo's key is not yours in this sense: with your own `\sa`,
aineo still maps `\s`, and `\sa` then waits for 'timeoutlen' after `\s`;
with your own `\t` or `\tc`, aineo still maps `\tcn`, with your own `\p` — or
`<Leader>p` while the leader is `\` — it still maps `\pa` and `\pt`, and with
your own `\gs` it still maps `\g`: yours then waits for 'timeoutlen'.

`setup()` or `vim.g.aineo` that changes it later maps nothing until the next
start. When a plugin manager loads aineo after startup, the keys are mapped
in the next event-loop tick.

`\` is also the leader when |mapleader| is unset or empty, and the local
leader when |maplocalleader| is: a filetype plugin's `<Leader>` or
`<LocalLeader>` mapping local to a buffer then shadows aineo's key there —
Neovim's own ChangeLog plugin maps `<Leader>o`. `:checkhealth aineo` warns
of both (|aineo-health|).

Terminal and Insert mode keys ~
                                                         *aineo-terminal-keys*
Once the editor has started, aineo also maps the terminal prefix
(|aineo-config-terminal_prefix|), `<C-\>` by default, followed by each prefix
key above but Send's, globally, in Terminal mode, in any terminal and not
only Claude's, and in Insert mode: from Claude's prompt, or while you type in
any buffer, to move without leaving the mode by hand. A twin first leaves
the mode it was pressed in, and then runs what its `<Plug>` mapping runs from
Normal mode (|aineo-mappings|). In Terminal mode it leaves as `<C-\><C-n>`
does (|CTRL-\_CTRL-N|). In Insert mode it leaves as `<Esc>` does: an
abbreviation before the cursor is expanded (|i_CTRL-]|) and an insert given a
count is repeated. `<C-\>c` enters Terminal mode in Claude's window again, as
`\c` does, and the others leave you in Normal mode in the window they move
to: `<C-\>pa` in the Report and `<C-\>g` in the changes pane's commits.
`<C-\>pt` enters Terminal mode in the shell's window, as `\pt` does, and
`<C-\>X` in the new shell of the run pane's. Claude Code is sent none of the
twin's keys.

Send has no twin: it acts on a selection or on the line of Normal mode.
`:Aineo claim` has no key of its own, so no twin either.

Neovim's own `<C-\><C-n>` and `<C-\><C-o>` work as ever: aineo maps neither.

The key after `<C-\>` must come within 'timeoutlen' (with 'notimeout' there
is no limit). Typed later, it is not a twin's: in Terminal mode it reaches
the terminal's program, Claude Code at Claude's prompt, and in Insert mode it
is inserted as typed. A longer mapping of your own, such as `<C-\>gs`, makes
`<C-\>g` wait for 'timeoutlen' as well.

A mapping of `<C-\>` alone makes that key wait for the next key, and a
twin's letter typed then runs aineo's action in place of yours. So in a mode
where you have mapped the terminal prefix alone globally, as a terminal
plugin's toggle is, aineo maps no twin. A mapping local to a buffer, such as
that toggle in the plugin's own terminals, cannot be seen when the editor
starts: the key waits there, and a twin's letter runs aineo's action. Set
`terminal_prefix` to another key to have twins in that mode.
`:checkhealth aineo` reports both (|aineo-health|).

A `terminal_prefix` that is a printable key, such as `x`, runs a twin as you
type it in Insert mode, and one that starts with `<C-\><C-n>` or
`<C-\><C-o>` makes Neovim's own keys wait for the next key.
`:checkhealth aineo` warns of both.

Like the prefix, the terminal prefix is read once, when the editor has
started (|VimEnter|), and a key sequence you mapped yourself — a global
mapping in the same mode — stays yours while aineo maps the others.

6. CONFIGURATION                                         *aineo-configuration*

aineo reads its settings from two places, and works with neither:

                                                                     *g:aineo*
vim.g.aineo		A table, set before aineo loads: >lua
			    vim.g.aineo = { prefix = ',' }
<
                                                               *aineo.setup()*
require('aineo').setup({opts})
			Records {opts}, a table shaped as `vim.g.aineo`, and
			does nothing else. Each call replaces the options
			the last recorded. A setting `setup()` gives wins
			over the same setting in `vim.g.aineo`.

The settings are checked when aineo uses them — when the editor has started,
and at each action but Send, which uses no setting. A wrong value is one
error naming the setting, such as
`aineo: layout.report_height: expected a number strictly between 0 and 1,
got 2`; at startup it also means no prefix keys, no terminal prefix keys and
no autostart. A key aineo does not know is ignored, and `:checkhealth aineo`
names it.

                                                         *aineo-config-prefix*
prefix			A non-empty string, or `false`. Default: `'\'`
			The key sequence before each of aineo's keys
			(|aineo-keys|). `false` maps no key; |:Aineo| and the
			`<Plug>` mappings remain. The empty string is
			refused.

                                                *aineo-config-terminal_prefix*
terminal_prefix		A non-empty string, or `false`. Default: `'<C-\>'`
			The key sequence, written as in a mapping, before each
			of aineo's keys in Terminal mode and in Insert mode
			(|aineo-terminal-keys|). `false` maps none; the prefix
			keys remain. The empty string is refused. A printable
			key, or one that starts with `<C-\><C-n>` or
			`<C-\><C-o>`, is accepted and warned of
			(|aineo-health|).

                                                      *aineo-config-autostart*
autostart		A boolean. Default: `true`
			Whether a bare `nvim` opens the layout by itself
			(|aineo-autostart|).

                                                     *aineo-config-claude.cmd*
claude.cmd		A list of at least one string. Default: `{ 'claude' }`
			The command run in the left terminal, as a list of
			words, never through a shell. aineo appends its own
			arguments (|aineo-report|). It must not hold
			`--continue`, `--resume` or `--session-id`, since
			aineo picks the session (|aineo-claude-session|):
			Claude Code 2.1.283 refuses `--session-id` beside
			`--continue` or `--resume`, printing "Error:
			--session-id can only be used with --continue or
			--resume if --fork-session is also specified.", and
			exits 1. A `--settings` in it, inline JSON or a file
			(named from the directory Claude Code starts in), is
			kept whole: aineo adds its session hooks, its
			`SubagentStart` hook, its `PostToolUse` hook and its
			`PermissionRequest` hook after the hooks it gives,
			writes the result to a file only you can read and
			write, in Neovim's own temporary
			directory, which Neovim removes when it exits, and
			passes that file as its one `--settings`. Nothing of
			your settings goes on Claude Code's command line.
			aineo reads only a regular file, never a FIFO, a
			directory or a device, and reads a file that begins
			with a UTF-8 byte order mark, or holds nothing but
			blanks, as Claude Code 2.1.292 does. When aineo cannot
			read your settings, add to their `hooks` or write that
			file, it passes your `--settings` as it is, Claude
			Code starts without aineo's hooks, and aineo warns
			once: a session switch inside Claude Code is then not
			followed. |aineo-health| says why it could not. What
			the file's lifetime means for teammates and background
			sessions is in |aineo-limits|. A `--settings` that a
			wrapper script adds itself is not among these words,
			so aineo cannot see it. Claude Code 2.1.292 reads the
			last `--settings` it is given: one the script adds
			before aineo's words is overridden, and one it adds
			after them, after `"$@"`, overrides aineo's hooks,
			without a warning. Put it in `claude.cmd` instead.
			Claude Code started through another program works,
			its words all in the list: >lua
			    vim.g.aineo = {
			      claude = { cmd = { 'npx', '-y',
			        '@anthropic-ai/claude-code' } },
			    }
<
                                        *aineo-config-claude.hide_multiplexer*
claude.hide_multiplexer	A boolean. Default: `true`
			Whether aineo starts Claude Code without the
			environment variables that tell it a terminal
			multiplexer runs it: `TMUX`, `TMUX_PANE`, `STY` and
			`ZELLIJ`. Claude Code 2.1.301 keeps its terminal title
			still under tmux, screen or zellij, and the activity
			indicator of a tab (|aineo-tabs|) reads that title, so
			a Neovim inside a multiplexer would show no activity.
			Every other variable reaches Claude Code as it
			reaches any terminal job of Neovim; the shell
			terminal and the other jobs Neovim starts keep the
			editor's whole environment. With `false` Claude
			Code gets the environment every terminal job of
			Neovim gets, as before, and knows it runs inside
			the multiplexer; no tab shows activity there, and
			`:checkhealth aineo` warns (|aineo-health|). Under
			tmux a copy made in Claude's window then prints
			`52;c;<base64>` there. What the default costs is in
			|aineo-limits|.

                                           *aineo-config-layout.report_height*
layout.report_height	A number strictly between 0 and 1.
			Default: `2/3`
			The Agent Report's share of the right column's
			rows; Input takes the rest.

                  *aineo-config-changes* *aineo-config-changes.working_branch*
changes.working_branch	A non-empty string.
			Default: none
			The branch work lands in, named as git reads a
			name: `origin/dev`, say. The changes pane's commits
			window lists the commits of that branch your
			session's base cannot reach under a Landed heading
			(|aineo-changes|). When it is not set, the branch is
			the default branch of the remote `origin`, which
			`origin/HEAD` names (`origin/main` in a clone), and
			with neither the pane shows no Landed section. aineo
			never fetches: the branch is what your repository
			last fetched (|aineo-limits|).

                                            *aineo-config-changes.graph_limit*
changes.graph_limit	A whole number of at least 1. Default: `1000`
			How many commits the commit graph of the changes
			pane's commits window draws, newest first
			(|aineo-changes-graph|); it says "Older commits not
			shown" when it left older ones out.

                                                   *aineo-config-tabs.padding*
tabs.padding		A whole number from 0 to 8. Default: `2`
			The spaces either side of every title in aineo's tab
			line (|aineo-tabline|). `0` leaves none. The padding
			counts in the width the titles must fit, before any

			`searching` and `reading`, each a list of matches.

			1024 by a Lua pattern.

7. SEND                                                           *aineo-send*

Send (`\s`, |:Aineo-send|) gives Claude what you wrote in Input, as one
message: Input's lines, joined by line feeds, go to Claude's terminal as one
bracketed paste followed by Enter, and Input is emptied. Control characters
but tab, line feed and carriage return are removed first, so nothing in the
text reaches Claude Code as a key.

Send also works while Claude is in a turn: Claude Code queues the message and
runs it after the turn. A draft already in Claude's prompt stays, and the
paste joins it. It sends Input while the changes pane or the terminal pane
hides it, too.

Pressed in a window whose buffer has issues marked (`\vm`), Normal mode `\s`
sends those issues to Claude in place of Input, and leaves Input as it is
(|aineo-explain-mark|).

Visual Send ~
In Visual mode, in Input, `\s` (|aineo-v_\s|, |<Plug>(aineo-send)|) sends
the selection alone — characterwise, linewise or blockwise — as one message,
the same paste and Enter, and removes it from Input; the rest of Input
stays. What leaves Input is what Vim's own `"_d` removes, and the message is
exactly that text: each line's part of the selection, joined by line feeds.
A line of a block too short to reach the block gives an empty line, with no
spaces for padding; a block with `$` takes each line to its own end; a tab,
a double-width character, or an emoji drawn as one with its modifiers, that
a block cuts is removed and sent whole, and spaces take the place of its
part outside the block. A characterwise selection that takes in the end of
a line (`v$`) takes its line break too, which joins the lines, and sends it
— but not on Input's last line, which has none, nor under 'virtualedit',
where a selection past the end of a line takes no line break and sends no
spaces. A linewise selection is sent as its lines, joined by line feeds,
with none after the last, as a Send of Input is. With 'selection' set to
`old`, a characterwise selection that ends on an empty line ends, as Vim's
`d` ends it, on the line above, or takes whole lines, line breaks and all,
when it starts in a line's indent; when it starts past the end of the line
above, `d` removes nothing and nothing is sent. When 'virtualedit' holds
`all` and no other flag but `none`, it keeps its end. No register is
written, and the cursor stays where `"_d` leaves it, in Normal mode.

Outside Input, `\s` in Visual mode sends and removes nothing, and tells you
once that Visual Send works in Input.

Send sends nothing, and tells you why with one warning starting with
`aineo: nothing sent —`, when there is no Input yet (open the layout), when
Input — or the selection — holds only white space, and when Claude Code is
not ready: not started, still starting, behind a dialog that awaits your
answer, or exited. It sends nothing either while this Neovim follows a session
its own Claude terminal does not run (|:Aineo-claim|): Input then holds the
claimed session's draft, which must not reach another conversation. The
warning names the claimed session, and what works here: `:Aineo claim`
without an id, which returns this Neovim to its own session, or, when its
terminal runs no session, `:Aineo claim {id}` or `:Aineo open`. A Visual Send
that sends nothing removes nothing and ends Visual mode; `gv` selects the
text again.

Undo ~
`u` in Input brings back what a Send removed, one `u` per Send: Input's text
after a Send of Input, the selection, where it was, after a Visual Send —
wherever `\s` was typed, and while the changes pane hid Input. `u` restores
Input only: the message has reached Claude. The draft the layout restores
into Input (|aineo-draft|) is not undone: after a Send, `u` brings the text
back and stops there. A switch of session, a start of Claude Code on
another session once it is ready (|aineo-claude-session|), a claim of a
session by its id and the return from it (|:Aineo-claim|) put that
session's draft in Input, and no `u` reaches a Send or a change made before
it — but a session that takes the place of one whose resume found no
conversation puts nothing in an Input that showed that session, and `u`
reaches as before. At an editor's first start, an Input that holds the
draft the session takes already is left as it is, and `u` still reaches
what you typed before. How many Sends `u` can reach is your 'undolevels'
(|aineo-limits|).

Claude Code counts as ready once its input box has shown, unbroken, for 1.5
seconds. A permission dialog drawn in the few tens of milliseconds before
aineo notices it could receive the paste and the Enter (|aineo-limits|).

8. THE AGENT REPORT                                             *aineo-report*

aineo starts Claude Code with five additions of its own:
- the session it resumes, or the id of a new one: `--resume` or
  `--session-id` (|aineo-claude-session|);
- instructions appended to its system prompt, telling Claude when to call
  the report tool and how to write a report (below), then, after a blank
  line each, one paragraph on `announce_work` (below) and one on the run
  tools (|aineo-run-tools|);
- aineo's MCP server, which Claude Code runs as a headless `nvim`, given
  through `--mcp-config`, with five tools: `report`, `announce_work`, and
  `run`, `run_output` and `run_stop` (|aineo-run-tools|);
- a `SessionStart` and a `SessionEnd` hook, which Claude Code also runs as
  a headless `nvim`, given through `--settings`: they tell the editor when
  Claude Code switches session (|aineo-claude-session|). Claude Code
  2.1.292 ran them beside a project's own hooks, not in their place.
  Beside them, a `SubagentStart` hook, which runs as each subagent starts,
  of any type, and only prints the paragraph on `announce_work` and one
  sentence more for the subagent: a subagent gets neither Claude Code's
  system prompt nor what aineo appends to it. It contacts no editor. And
  a `PostToolUse` hook for `Bash` calls of git, run in the background,
  which tells the editor of a worktree or branch the call made
  (|aineo-changes-hook|). And a `PermissionRequest` hook, run in the
  background, which tells the editor that an agent waits for your answer
  to a permission prompt, and decides nothing (|aineo-office-hooks|).
  aineo puts nothing else in `--settings`, and adds them after the hooks
  of a `--settings` in `claude.cmd`, passing the two together in a file
  only you can read (|aineo-config-claude.cmd|);
- three tools allowed without asking: `--allowedTools mcp__aineo__report
  mcp__aineo__announce_work mcp__aineo__run_output`. `run` and `run_stop`
  are not, and carry a marker that makes Claude Code ask you for each call
  in every mode (|aineo-run-tools|).

`announce_work` is how Claude Code and its subagents tell aineo of each
git worktree they work in and the branches they work on there
(|aineo-changes-reported|), and every one of them must: its description,
which subagents see too, begins "Required for every agent and subagent:
call once per worktree you work in, right after you create the worktree or
a branch in it, and again whenever the set of branches you are working on
there changes, with the absolute path of the worktree's folder, a short
label, and every branch you are working on there with the commit it was
created from." Its arguments, all three required, are `worktree`, the
absolute path of the worktree's folder, the main checkout's folder for
work there — a relative one is refused, "worktree: expected an absolute
path", since every agent and subagent shares one server whose working
folder is no agent's own; `label`, a short name for the task; and `branches`,
at most 32 objects of `name`, the branch's name, and `base`, the commit it
was created from, an id or any name git reads, such as `origin/dev`;
nothing else. `branches` may be empty: the agent is done with that
worktree, which leaves the Reported section. Each string must be
non-empty, at most 4096 bytes, and hold no NUL and no line break, and no
two branches may share a name, or the call is refused, naming the field or
the item, `branches[2].base` say. A call replaces what the worktree's
calls before reported: an agent with several worktrees calls once for
each. The server offers it to the editor that started Claude Code alone,
with the token of that start; the tab checks each branch is a local branch and
resolves its base to a full id in the worktree's folder, else in its
session's repository (|aineo-changes-reported|), waiting at most 4 seconds
for git. The tool only informs, and answers one of four things, nothing
more: `ok` when a tab took it; `not taken`, as an error, when none did — no
tab of that editor runs this Claude Code, the editor cannot be reached or
does not answer within 5 seconds, or that tab already waits for 32 other
folders git does not list yet (|aineo-changes-reported|); `aineo refused the
announcement: branches[<n>].base: <base> names no commit in <folder>`,
followed by `, nor in <repository>` when the worktree's folder was tried
first, or `aineo refused the announcement: branches[<n>].name: <name> is no
local branch in <folder>`, as an error, and nothing is recorded; or `aineo
refused the announcement: ` and the field, as an error, for arguments it
refuses. The paragraph appended to the system prompt reads "Required for
every agent and subagent: call `mcp__aineo__announce_work` once per
worktree you work in, right after you create the worktree or a branch in
it, and again whenever the set of branches you are working on there
changes, with the absolute path of the worktree's folder, a short label,
and every branch you are working on there with the commit it was created
from. It only informs
aineo: if it refuses, correct the call as the refusal says and call again;
otherwise do not act on its reply."
The server and the hooks are given this editor's address, |v:servername|,
and a token of this start of Claude Code; the hooks are also given the
directory Claude Code runs in and its process id, which the shell that runs
them fills in. The server relays each report to an editor (below). Claude
Code also gets `AINEO_CHILD=1` in its environment, so a Neovim started inside
it never autostarts.

                                                         *aineo-report-claims*
Each report belongs to the Claude session its Claude Code is on, which the
hooks record as they run, or, where they do not run, the session Claude Code
started on. The server hands each report on to the first of these that takes
it:
1. a Neovim that has claimed the report's session (|:Aineo-claim|), even
   while the editor that started Claude Code answers;
2. the editor that started Claude Code, as before, and also while it
   follows no session yet — unless it cannot be reached, as when it has
   quit, or follows another session: by a claim, or, until a new start of
   its Claude Code is ready, the session before it. It then shows nothing
   of the report;
3. a running aineo Neovim that shows exactly the report's session, the one
   used last first: last focused, or whose Claude Code last started,
   switched or was claimed. A Neovim listed there that follows another
   session or none, or is no aineo of this version, passes it on;
4. when the editor that started Claude Code follows another session by a
   claim and has not yet moved its working directory's Reports into a
   session of its own: that editor, which keeps the report with them,
   unshown, so that its own session takes them together (|:Aineo-claim|),
   when the report's session has no Reports of its own yet — one that took
   the place of a session whose resume found no conversation has that
   session's, when it kept any — else the report goes on to 5
   (|aineo-limits|);
5. that session's Report on disk: it shows when aineo next follows the
   session, never in another session's Report.
A Neovim that holds the report without answering, at a hit-enter prompt say,
ends the search, as does one that closes the connection before it answers:
no report is shown twice. The tool's answer tells Claude which happened, each
in its own words: delivered to the Agent Report; delivered to the Agent Report
of another Neovim that claimed the session; delivered to the Agent Report of
another Neovim that shows the session; or kept in the session's Agent Report
on disk, which it says too for a report kept with the working directory's.
None of the four is a tool error.

A claim lasts until the claiming Neovim follows another session, returns to
its own (|:Aineo-claim|) or quits, or until another Neovim claims the
session; a claim another Neovim took over does not come back when that one
lets go. When Claude Code switches session — `/clear`, `/resume`, `/branch` —
the claim moves to the new session, and a Neovim that follows the session
left by a claim follows the new one, whether or not the editor that started
Claude Code answers, and while it, or another such Neovim, waits for you at
a hit-enter prompt. What aineo keeps for this, under `stdpath('state')` in
`aineo/editors/`, `aineo/claims/` and `aineo/claude-processes/`, only you can
read: the running aineo Neovims and the session each follows, the claims,
and the session each Claude Code process aineo started is on.

A report holds a `task`, a `status` — `started`, `progress`, `blocked`,
`done` or `failed` — a one-line `summary` and, optionally, `details`. The
Agent Report shows each as: >
    HH:MM [status] task — summary
          - each line of the details,
          - an item of a list under the status
<
A line break in the task or the summary becomes a space. Each line of the
details is an item, `- ` and its text; a line Claude wrote as an item, after
`- `, `* `, `+ ` or `• `, shows aineo's `- ` in place of its own, and a line
that is empty, white space alone or a marker alone shows as an empty line.
The Report follows the newest report.

                                                           *aineo-report-days*
Days ~
A line of its own, a separator, starts each day of reports: >
    ── Sun 18 Oct ──
    09:05 [done] task — summary
    ── Yesterday ──
    10:00 [done] task — summary
    ── Today ──
    11:30 [done] task — summary
<
A report is under the day it arrived on, by your clock. The separator reads
`Today` or `Yesterday` for those days, else the weekday, the day of the month
and the month, `Mon 19 Oct`, with the year, `Sun 19 Oct 2025`, when it is not
this year; the weekday and the month are in English whatever your locale. Two
reports on one day have one separator. The names move on with the days: the
Report names them again whenever it shows a report, and at midnight while it
stays open, so what was `Today` reads `Yesterday` the next morning. A report
with no readable time goes under the separator of the report before it. A
separator is a line of the Report like any other, in |hl-AineoReportDay|, but
it carries no web link and no path: a double-click on it selects its word, as
anywhere else in the Report that is not a path, and it has no address for
⌘-click.

A long line wraps between words: a wrapped first line continues under the
`[` of its `[status]`, and a wrapped item under its text, not under its `-`.
A Report narrower than 18 columns continues a wrapped line further left, to
keep 10 columns of text ('breakindentopt'), and your own 'showbreak' moves
where it continues by its width. Each window showing the Report gets
'breakindentopt' `list:-1,min:10` for the Report alone, as |:setlocal| sets
it, each time it shows the Report; where you turn 'breakindent' or 'wrap'
off, a long line continues as Neovim draws it.

The instructions ask Claude to write each report for a person, in plain
language: what was done or planned, and how, never the reasons for its
decisions. A `blocked` or `failed` report states, as a fact, what blocks the
task or what stopped it. A `started` report of a plan lists the features
planned in its details, one per line; a `done` report lists what was done,
the features, one per line. References go only at the very end of a report,
in parentheses, by number or ID only, such as `(D18, C12, #31)`: on a line of
their own, the last of its details, or at the end of its summary when it has
no details. These rules are for reports only, not for Claude's other replies.
A running Claude Code keeps the instructions it started with.

Links ~
Every web link in a task, a summary or details is underlined, in
|hl-AineoReportLink|, and carries its address: ⌘-click opens it in a
terminal that opens OSC 8 hyperlinks, as iTerm2 does, and |gx| opens it
from the keyboard. A link starts with `http://` or `https://`, in any case,
at the start of the text or after a character that is not an ASCII letter
or digit. It runs up to an ASCII space, a control character, `<`, `>`, `"`,
`|`, a backtick or a byte that is not part of well-formed UTF-8, so a link's
address never holds a control character or a byte that is not well-formed
UTF-8. Any other character, such as `é`, `—` or a non-ASCII space, is part of
the link. It leaves out the `.` `,` `;` `:` `!` `?` `'` `*` `~` it ends in,
and a `)`, `]` or `}` with no opening partner inside it, one after another
until it ends in none of them: `(see https://example.com/a).` links to
`https://example.com/a`. What is left holds at least one character after the
`://`, or is no link.

Paths ~
A path in a task, a summary or details that names a regular file that
exists — not a directory, a FIFO or a device — is underlined, in
|hl-AineoReportPath|. Double-click it to open the file in the middle column,
at its line when it names one, when it is a text file, as a link in
Claude's terminal opens (|aineo-links|); a file that is not text goes to
your system, through |vim.ui.open()|:
`render.lua:112` opens `render.lua` at line 112, a line past the file's end
at its last line, and `:0` at its first. A double-click works from Normal
mode, from Insert mode, as when you click from Input, and from Claude's
terminal; it needs 'mouse' on in Normal and Insert mode, as Neovim's
default, `nvi`, has it. Anywhere else in the Report, a double-click selects
the word, as Neovim's own does; in the Report, it takes the place of a
`<2-LeftMouse>` mapping of your own. A path carries no address: ⌘-click
opens only web links. |gf| and |gF| open a path too, in the middle column,
but find its file as Neovim does, in the current directory and 'path'.

A path runs up to an ASCII space, an ASCII control character, `<`, `>`,
`"`, `'`, `|`, a backtick, `(`, `)`, `[`, `]`, `{`, `}`, `,` or `*`, so a path
in quotes, brackets or Markdown emphasis, `**lua/x.lua**`, is found; it
leaves out the `.` `:` `;` `!` `?` it ends in, one after another, and keeps
a `~`. It holds a `/`, or a `.` that is neither its first nor its last
character: `lua/x.lua`, `./Makefile`, `/etc/hosts`, `README.md` and
`.luarc.json` are paths, `Makefile` and `.gitignore` are not. A `:<line>` or
`:<line>:<column>` at its end is part of it and names the line; a range,
`x.lua:12-20`, or `x.lua#L12` names no file. A relative path is looked up in
the working directory (below), an absolute one as it is; a leading `~/` is
your home folder, and a `~` anywhere else, or `~name/`, is left as
written. After a `:cd`, the relative paths a new Claude Code writes may not
be found. A file name holding a space is never found whole, and text inside
a web link is never a path. A path is looked up when the Report shows its
report: a file made later is underlined the next time the Report shows it,
after `:edit` in the Report, and one removed stays underlined until then. A
double-click looks the path up again: when it names no regular file any
more, or cannot be looked up, the double-click opens nothing and tells you
why.

Colours ~
The Report shows the time in |hl-AineoReportTime|, and the `[status]`,
brackets included, bold, in the group of its status, only where it placed
them, never text like them in a task, a summary or details; web links in
|hl-AineoReportLink|; paths to files in |hl-AineoReportPath|; and the
separators of its days (|aineo-report-days|) in |hl-AineoReportDay|. The bold
is |hl-AineoReportStatusBold|, beneath the group of the status, linked to
Markdown bold, `@markup.strong`: the bold, and whatever else a colour scheme
gives Markdown bold — a background, italic, underline, or no bold at all —
shows on the `[status]`. Its colour does not,
unless the status's own group has no text colour, such as
`AineoReportDone` given only a background (`guibg=`). To turn the bold off
and keep the colour, put this in your config, before or after your colour
scheme, or run it at any time. In Lua: >lua
    local function aineo_bold_off()
      vim.cmd('highlight clear AineoReportStatusBold')
      vim.cmd('highlight link AineoReportStatusBold NONE')
    end
    aineo_bold_off()

Reports are kept per Claude session, under `stdpath('state')` in

aineo follows a Claude session, the reports are the working directory's, in

session's reports; its file is cut back to its newest 2 MiB once it

layout opened, for the editor's life; each new Claude Code starts in the
working directory of its own moment.

9. THE OFFICE                                                   *aineo-office*

The office is a screensaver for your tab's Claude Code: an animated office
that covers the right side of the layout, the whole column and its full
height, whatever the column shows. Your Claude Code is a jelly bean at a
desk. It stands beside the desk while nothing runs, and sits behind it and
types, dots rising over its head, while a tool call runs.

The office shows by itself once the cursor has stayed out of the right side of
the layout for `office.idle_ms` (|aineo-config-office.idle_ms|), three minutes
by default, and only while the layout shows a right side to cover: with the
right column closed or zoomed away, it waits, and shows when the column comes
back if the time has passed. The cursor entering the right side stops the
countdown, leaving it starts it again, and so does a report coming in or
entering a tab page. While the office is hidden, that countdown is the one
timer it holds, and it reads nothing.

`:Aineo office` (|:Aineo-office|), `\O` and `<Plug>(aineo-office)` show it at
once. The cursor entering any window the office covers closes it: a click on
it, `<C-w>w` reaching the right column, `\r`, `\i`, `\g` and the other keys
that move to a window of the right column. Moving to Claude's window or to a
file leaves it as it is. When the office opens, the cursor stays in the
window it was in.

What the office knows comes from the files Claude Code writes: the transcript
of the session, `projects/<folder>/<session id>.jsonl` under
`$CLAUDE_CONFIG_DIR`, or under `~/.claude` when that is not set, and, in the
folder `<session id>/subagents` beside it, the transcript and the meta file
of each subagent. The office reads the end of the transcript when it opens,
and each line added while it shows; a subagent that runs when it opens, or
starts while it shows, is followed until its meta file says it finished or
the user stopped it. A transcript cut short or replaced by another is read
again from its end. It calls no Claude, sends nothing to its terminal, makes
no MCP call or network request, writes nothing and spends no token. While it
shows, one timer draws 12 frames a second, one file watch follows the
transcript, one the subagents' folder and one each subagent it follows, 64 at
most; where the system gives no file
watch, or the file or folder is not there yet, aineo looks at it every half
second instead. Closing the office stops all of them. A session with no
transcript yet shows its agent standing, and the office follows the file
from its first line once Claude Code writes it.

The office draws two pixels to a cell, with half blocks, in the colours of
the art, so it needs `'termguicolors'` and `'ambiwidth'` left `single` (which
`double` makes the half blocks two cells wide). With either wrong the office
does not show: `:Aineo office` and `\O` tell you why, once, the countdown says
nothing, and `:checkhealth aineo` reports it as an error.

Each tab page has an office of its own, that follows its own session. Leaving
the tab page stops its frames and its file watches, and entering it starts
them again, the scene catching up with what the session did meanwhile. In a
window smaller than 60 columns by 24 rows the office draws one line saying so
in place of the scene.

                                                          *aineo-office-cards*
Report cards ~
A report no longer closes the office. The reporting agent's walk to the
printer comes from the transcript; the report itself shows as a card in the
bottom right corner of the office, above the status list: a dot, the status
and the summary on one line, cut to the office's width. The newest card is at
the bottom; three show at most, and a line `+N more` above them counts the
older ones. A card is coloured by its report's status:
|hl-AineoOfficeCardDone| for `done`, |hl-AineoOfficeCardProgress| for
`started` and `progress`, and |hl-AineoOfficeCardProblem| for `blocked` and
`failed`, whose dot also blinks. The cards are kept until the cursor enters
the right side, where the Report shows every report; a report that comes in
while the cursor is there, and the office is hidden, leaves none.

                                                    *hl-AineoOfficeCardDone*
AineoOfficeCardDone     a `done` card, linked to `DiagnosticOk`
                                                *hl-AineoOfficeCardProgress*
AineoOfficeCardProgress a `started` or `progress` card, linked to
                        `DiagnosticInfo`
                                                 *hl-AineoOfficeCardProblem*
AineoOfficeCardProblem  a `blocked` or `failed` card, linked to
                        `DiagnosticError`
                                                    *hl-AineoOfficeCardMore*
AineoOfficeCardMore     the line `+N more`, linked to `Comment`

From 24 rows tall, the last five rows of the office are its status list: a
rule, then a line for each agent, up to four, with a dot in the agent's
colour, its name and what it is doing (the activity's `label`, or the
state's own words), each cut to the cells it has, a character that is not one
cell wide shown as `?`; when there are more agents than lines, the last line
counts the rest. The floor plan is cut to the rows above, and nothing but the
list is painted on its rows.

What a pack can ask of a frame is bounded. A plan places at most 2000 pieces,
and the pieces together paint at most sixteen times the pixels of the plan's
area; when it places more, aineo leaves out first the decorations, then the
furniture, and last the pieces that stand on a spot, show something, have a
screen or have art for when they are in use, the last the plan reads first,
and says so once each time the office shows. A piece is painted only where it
lies on the plan. An agent begins at most eight steps in one update, the rest
in the updates after, and looking for a spot stops at the nearest.

The art is a pack: a folder `aineo-office/<name>/` on 'runtimepath' with
`pack.lua`, a description in the subset of a Lua table that aineo reads and
never runs, `floor.txt`, the floor plan drawn as text, and `art/*.txt`, the
pieces of pixel art. aineo's own packs are `aineo-office/default/`, the one
the office draws, and `aineo-office/space_station/`, a starship bridge based
on it that `office.pack` (|aineo-config-office.pack|) can name in its place.

`:Aineo office check` (|:Aineo-office-check|) lists what is wrong with a
pack, `:Aineo office states` (|:Aineo-office-states|) lists what it draws for
each state, `:Aineo office preview` (|:Aineo-office-preview|) plays every
state over scripted agents, `:Aineo office new` (|:Aineo-office-new|)
starts a pack of your own from the default, and `:Aineo office pack`
(|:Aineo-office-pack|) switches the pack every office draws for this
Neovim's session. How a pack is chosen, found and
written is told next.

                                                         *aineo-office-packs*
Packs ~
A pack is a folder `aineo-office/<name>/` on 'runtimepath': in a plugin, as
lazy.nvim's `{ 'someone/aineo-office-harbour' }` brings one, or in your own
configuration, `~/.config/nvim/aineo-office/<name>/`. Its name is its
folder's, and `pack.lua` says it too. `office.pack`
(|aineo-config-office.pack|) chooses the pack, and `office.pieces`
(|aineo-config-office.pieces|) replaces single pieces of it.

A pack is `based_on` another, the default pack when it says nothing: what it
leaves out it takes from that pack, name by name. A pack of its own art, its
floor and a few activities can leave the rest to the default.

A pack's name is letters, digits, `_` and `-`. A pack reads its own files
only: `floor.plan` and the art files must lie in the pack's folder, a link
to a file of the folder is followed and one to a file outside it is told, and
a file that is no regular file, such as a FIFO, is told and never opened.
`office.pieces` names your own files, anywhere.

What is wrong with a pack is told with its file and line, all at once, by
`:Aineo office check`, and once, when the office shows, in one warning that
names the first problem of each file. A piece, an effect, a pose, an activity
or a state with a problem is left out, so that the one of its name in the
pack it is based on shows through. A pack that cannot be used at all - no
`pack.lua` that is data, no floor, no agent that stands and walks, no activity
for standing - gives way to the default pack. The checks: every value is what
its field says; names are lowercase words joined by `_`; art rows are of one
width and use the letters of their header, with colours the pack has; a
floor's letters are in its legend; every spot can be walked to from the door;
the text of an effect is one cell to a character on your screen; every
name a field gives (a piece, a pose, an effect, an activity, a thing, a
state) exists, in the pack or the pack it is based on; and an activity whose
steps go to a spot the floor lacks is told never to play.

                                                       *aineo-office-pack-lua*
pack.lua ~
`pack.lua` returns a table, written in the subset of Lua that aineo reads as
data and never runs: `return`, tables with named fields (`name = 'tiny'`),
keys in brackets (`['*'] = ...`) and lists, strings in quotes or in long
brackets, numbers, `true`, `false` and comments. A call, an operator,
`function` or a name in a value is a problem at its line, and nothing of the
file runs. A list item wins over a key of its number, as in Lua. A file is
read to 256 KiB.

Field	Default	Means ~
`format`	required	`1`, the version of the pack format
`name`	required	the pack's name, its folder's
`about`, `author`	`''`	one sentence, and who made it
`based_on`	`'default'`	a pack's name; `false` for none
`colours`	`{}`	`#rrggbb` by name, at most 64 names
`text_colours`	highlight groups	by role: `name`, `status`,
		`thought`, `warning`; each `#rrggbb` or a highlight
		group's name (`Comment`, `Normal`, `Special`, `WarningMsg`)
`characters`	the agent's	`agent`, `subagent` and `cat`
`effects`	`{}`	text a character shows
`floor`	required	the plan, its colours and its legend
`activities`	`{}`	what characters do
`things`	`{}`	what an activity leaves behind
`states`	the parent's	the activity for each state
`triggers`	`{}`	custom matches, before a state's activity

                                                     *aineo-office-characters*
Characters and poses ~
`characters` holds `agent`, `subagent` and `cat`. A character has `colours`,
a list of `#rrggbb` it takes in turn (one grey when it gives none), `poses`,
by name, and `like`, another kind it takes the poses and colours of unless it
gives its own. A subagent that is like nothing is like the agent; a pack that
names no cat has none; `how_many` is the cat's number, `1` by default.

The agent needs poses `standing` and `walking`: the engine uses them between
steps. A pose has `art`, a list of pieces drawn bottom first, or `like`,
another pose whose fields it takes unless it gives its own, up to 8 poses
deep; and `sitting` (drawn seated, its feet hidden behind what stands in
front), `effect`, `screen` (what the character's own monitor shows), `holding`
(a prop at the art's `hand` area) and `rises` (pixels it rises by, one number
for each frame).

                                                        *aineo-office-effects*
Effects ~
An effect is text a character shows: `text`, a list of frames, each of
characters one cell wide on your screen; `colour`, a role of `text_colours`, a
`#rrggbb` or a highlight group, `'status'` by default; `place`: `above`,
`above_left`, `above_right` or `beside`, `'above'` by default;
`seconds_per_frame`, `0.25`; and `bold`, `false`.

                                                            *aineo-office-art*
Art files ~
`art/<piece>.txt` holds one piece of pixel art, named by the file. A header of
`field: value` lines, a line `---`, then the frames of the piece, separated by
lines `---`. A row is one character to a pixel, `.` is transparent, and all
rows are of one width; a cell of the picture is two pixels tall.
>
    about: A desk with a drawer.
    colours: W = wood, D = dark_wood
    anchor: 0, 3
    area name: 1, 2, 10 x 2
    ---
    WWWWWWWWWWWW
    DDDDDDDDDDDD
    .D........D.
    .D........D.
<
Header field	Means ~
`about`	what the piece is
`colours`	each letter and its colour: a name from `colours`, or
		`agent`, `agent_light`, `agent_shade`, `agent_blush`, the
		character's own; required for each letter used
`anchor`	`column, row` of the pixel that stands on the cell the piece
		is placed at, counted from 0; the bottom left by default
`faces`	`right` (the default) or `left`: the way the art faces
`stretch`	`columns 3-20`: columns, counted from 1, that repeat to
		stretch the piece to the width the plan draws; none by
		default
`area <name>`	`column, row, width x height`, in pixels from 0, where aineo
		draws: `screen`, `hand`, `name`, `plan`, `time`, `date`,
		`sky`, `page` or `query`
`seconds per frame`	how long each frame shows, `0.25` by default

An art file is read to 256 KiB, 400 pixels wide, 200 tall and 64 frames; of a
pack's art files the first 500, by name, are read and the rest told. The
files of a pack and of the packs it is based on are read up to 2 MiB together,
the files over that told once and left out, so that the pack it is based on
shows through. A pack is read once and kept: the office reads it again only
when one of its files, or the folders it looked in, changed.

                                                          *aineo-office-floor*
The floor plan ~
`floor` in `pack.lua` has `plan`, the file (`'floor.txt'`), `floor_colour`
and `wall_colour`, names from `colours`, and `legend`, what each letter of
the plan is. `floor.txt` draws the plan, one character to a cell, a cell one
pixel wide and two tall.
>
    # Comment lines start with # and come first.
    # The next line marks with ~ the columns that repeat to fill the width.
      ~~
     ####
     D..#
    ~..s.
<
The first line after the comments marks with `~` one block of columns that
repeat to fill the width; the first character of every row is the marker
column and is not part of the plan: `~` there marks one block of rows that
repeat to fill the height, a space a row that does not. A piece or a spot in
a repeated block repeats with it, so one desk becomes a room of desks. `.` is
floor to walk on, `#` wall, a space floor nobody walks on, and any other
character a letter of the legend. A row shorter than the widest is read as
ending in spaces. A plan is read to 400 cells wide and 200 rows.

A legend entry has:
`piece`	the piece standing there, its bottom left corner on the cell; a
	run of the letter on one row stretches a piece that stretches to
	the run
`spot`	a place characters go to, by name; `door` is where they come in and
	go out, `desk` each agent's own
`sitting`	a character at the spot is seated (`false`)
`facing`	`left` or `right` (`'right'`)
`walk_over`	the piece lies on the floor and is walked over (`false`)
`in_use`	the art the piece shows in its place while a character stands
	on the spot nearest to the piece or walks over it
`decorations`	for a run of the letter: pieces placed left to right, as
	many as fit, in this order of preference, each with a spot of
	its own name on the first floor row below it
`from_width`	the piece shows only when the office is at least so many
	columns wide
`shows`	live content aineo draws into the piece's area of that name
	(|aineo-office-live|); for a run of `decorations`, into each
	decoration that has such an area

                                                           *aineo-office-live*
Live content ~
A piece with `shows` is drawn as its art says, and aineo draws into its area
of that name, and nowhere else:
`time`	`07:05`, from the clock, as far as the area holds
`date`	`Oct 03`, the same
`sky`	the pack's piece `sky_night`, `sky_dawn`, `sky_day` or `sky_dusk`
	for the hour of the clock (night from 21 to 5, dawn until 8, day
	until 17, dusk until 21), from the area's top left and cut to the
	area; a pack without the piece draws no sky
`plan`	the main agent's tasks, from `TodoWrite` or `TaskCreate` and
	`TaskUpdate`, a row each: `✓ ` before the ones done, `○ ` before the
	others, cut to the area's width; from the first task not done when
	there are more tasks than rows. A task deleted is left out, and a
	creation whose result is an error takes no number. `TaskUpdate` names
	a task by the number Claude Code gave it, which the transcript does
	not carry: aineo counts the creations it has read, so when the part
	of the transcript it reads at the start begins after some of them,
	an update can tick another row or none
`printing`	the pack's piece `printed_page`, coming out of the top of the
	area a pixel row at a time for four seconds after any agent calls
	the report tool; a pack without the piece prints nothing
`name`	the name of the agent whose desk it is, cut to the area's
	width: the desk of the agent at a `desk` spot is the piece that shows
	names over that spot, and a desk nobody has, or whose spot the width
	cut off, stays blank; a plan without `desk` spots gives the n-th
	such piece to the agent with the n-th place
A monitor besides writes what its agent looks up on the web into its `query`
area while the agent is on the web (the query of a search, the host of an
address it fetches, and only when that has the shape of a host; never the
rest of it), and a `✓` (green) or `✗` (red) at the top left of its `screen`
area for three seconds after a test run. A character that is not one cell
wide, a combining mark among them, or is a control character, shows as `?`.
Nothing is written below the plan: the rows under it are the status list's.

                                                     *aineo-office-activities*
Activities, things and states ~
`activities` says what characters do, by name. An activity has `steps`, in
order, and `about`, `label`, `who` (`'agents'` or `'cat'`), `during` (the
states, `always` among them, in which it may be picked at random), `chance`
(a weight, `1`) and `players` (how many play it together, `1`). A step has
`at` (the spot it is at), `pose` (`'standing'`), `for_seconds` (a number, or
two for a random time between them), `facing`, `effect`, `even_if_taken`,
`the_one_moved_plays` (an activity), `leave` and `remove` (a thing) and
`follow`. Spots aineo knows without a legend: `anywhere`, `an_empty_desk`,
`an_idle_agents_desk`, `next_to_an_agent` and `next_to_the_cat`, and each
thing's name.

How an agent plays an activity: it takes the steps in order. For a step it
goes to the nearest spot called `at` that no other agent has taken, walking
the shortest way over floor (`.`), spots and pieces with `walk_over`, never
over a wall, a space or a piece that stands on the floor, and takes the
step's `pose`, facing the spot's way or the step's `facing`. A spot called
`desk` is the agent's own. An agent has a place from its arrival to its
leaving, the lowest number no other agent has, and its desk, its monitor and
its colour go by it: the agent with the first place has the first desk, the
first monitor and the first colour. After `for_seconds` from its arrival (a
random time between the two numbers when it has two) the next step begins; the
last step lasts until the agent's activity changes, or, when it has
`for_seconds`, until they are over (see below). An agent whose step names
a spot that other agents have keeps the spot it stands on and looks again
every second. An agent that has no place yet, whose step names a spot that
other agents have, or that the plan lacks (as in a room too small for the
desks), or that cannot be walked to, is put on the free floor cell nearest the
spot `door` (the one the random source picks when the plan has no door) and
plays the step there, so that it is always drawn; it is not drawn only when a
character stands on every floor cell, and then it is put on a cell as soon as
one is free. An agent that has a place keeps it: a spot that cannot be walked
to leaves it where it is and its activity goes on. An agent first appears at
the first spot of its first step without walking there, or at the spot `door`
when the step has no `at`.
A step's `effect` shows over the pose's. When the office is resized, each
agent keeps its activity and its step, at the spot of the same name and
number in the new plan.

When the last step of an activity has `for_seconds` and they are over while
the agent's state goes on, the agent plays another activity: one whose
`during` names its state, picked at random in proportion to its `chance`
(`1` unless it says), never the one the agent has just played, and only one it
can play now. It can play an activity when the plan has as many free spots as
`players` for its first step with a spot and a spot for each step after, when
the others that must play it are free, and, for a step that follows someone,
when someone is on the move. An activity with `players = 2` takes along
another agent, picked at random among the free ones in a state its `during`
names (not in a game, upset, sent to clean, or doing this very activity
now): both begin it together, each at a spot of its own of the name, and
each step lasts the same time for both; with no such agent it is not picked.
When one player leaves it, called away by its state, sent to clean or leaving
the office, it ends for the others too: two play it, or none. An agent with
nothing to pick keeps its last pose and looks again every second. When the
agent's state changes, what it picked at random is dropped for what the new
state asks for.

A step's `at` may name a spot aineo knows without a legend: `anywhere` is a
floor cell the random source picks; `an_empty_desk` a desk of the plan no
agent has; `an_idle_agents_desk` the desk of another agent in the state `idle`
who is away from it; `next_to_an_agent` a cell beside another agent who stands
still; `next_to_the_cat` a cell beside a cat that stands still, facing it,
which then keeps its pose and its place until the agent's step is over; and
a thing's name is the cell where a thing of that name lies. With
`even_if_taken` a step goes to the nearest spot of its name, taken or not:
the character that has it is moved when the one coming arrives, and plays the
activity `the_one_moved_plays` names, or, when the step names none, looks for
another spot of the name and, finding none, is done with its step. A chain of
characters moved one by another stops at the fourth, who is left where it
stands.

A pose whose art has frames, or whose `rises` lifts it, begins at its first
frame when the agent takes the pose. A pose with `screen` shows that piece in
the `screen` area of the agent's own monitor, the one nearest to the agent's
`desk` spot (in a plan without `desk` spots, the n-th piece of the plan with a
`screen` area for the agent with the n-th place). `holding` draws a piece at
the `hand` area of the first layer that has one, mirrored with that layer and
as the piece's own `faces` says.

`things` says what an activity leaves behind: `piece`, and optionally
`upsets_agents_within` (cells), `upset_agents_play` and `cleaned_up_by` (an
activity each). A step with `leave` lays that thing on the floor at the
character's feet as the step ends, and a step with `remove` takes away the
thing of that name on the cell the character stands on as it ends; a step
that never ends leaves and removes nothing. A thing is drawn under what stands
on its cell. When one is left, the agents at most `upsets_agents_within` cells
from it, in a straight line, play `upset_agents_play`. The idle agent (the
state `idle`) nearest to it that can walk to it goes to clean it up; with no
idle agent that can, the nearest other agent that is in the office (not
arriving, not leaving, not in an interlude) goes. That agent plays
`upset_agents_play` first, then `cleaned_up_by`, and a thing no agent can walk
to waits where it lies. Both are interludes: when they are over, or when the
agent's state changes, the agent goes back to what its state asks for, a
working agent to its work. At
most 64 things lie at a time, and a resize drops those on cells the new plan
cannot be walked on.

`characters.cat` draws a cat, `how_many` of them (at most 4), once the pack
has activities with `who = 'cat'`. The cat has no state: it plays those
activities at random, as agents do, the ones whose `during` names `always`.
It takes no place among the agents, so it has no desk, no monitor and no row
in the status list, and its colour goes by its number among the cats. A cat's
step may `follow = 'someone_walking'`, the only name there is: the cat trails
the nearest character on the move for `for_seconds` or until it stops. A cat
needs at least one activity with a spot to come into the office: it is placed
by that, and a cat whose every activity follows someone is never placed. A cat
that takes a seat an agent is on, with `even_if_taken`, angers the agent and
the agent leaves, if the pack says so by `the_one_moved_plays`.

`states` maps the name of a state to an activity; a state it leaves out takes
its parent's.

                                                       *aineo-office-triggers*
Triggers ~
`triggers` is a list, tried in order whenever a tool call starts, before the
activity of the state. Each has `when`, the call it matches, and `play`, the
activity it plays while the call runs. `when` holds `tool`, `agent` (`main` or
`subagent`) and any of `command`, `description`, `file_path`, `url`, `query`,
`subagent_type`, `pattern`, `path`, `status`, `summary` and `task`. A value of
plain words matches a value that contains them as whole words, `'docker'`
matches `sudo docker compose up` and not `dockerfile`; a value with `*` or `?`
is a glob over the whole value; `{ lua_pattern = '^make%s+test' }` is a Lua
pattern, which may hold at most one repetition item (`*`, `+`, `-` or `?`,
after a character, a class or a set) so that no match can take long; a
pattern Lua rejects, or with more, is a problem at its line. A trigger costs a
string match on a call already read: a pack and the packs it is based on
hold at most 64 triggers together, the rest told and left out, and the
triggers of one call are tried for 20 ms at most, the rest of them skipped
and told once each time the office shows.
>lua
    triggers = {
      { when = { tool = 'Bash', command = 'docker' },
        play = 'tend_the_rack' },
    }

                                                         *aineo-office-check*
Checking a pack ~
`:Aineo office check [name]` (|:Aineo-office-check|) puts every problem of a
pack in the quickfix list as `file:line: problem`, the file's whole path in
the list, so `:cnext` goes to it.

The office shows the main agent and its subagents, and shows when you ask
for it, not by itself. It stays over the right column as the screen
or a window is resized, and closes when the layout shows no right column, as
under `\Z`; it makes its colours again after a colorscheme. It does not
pause for a tab page you leave or return to.
It follows the transcript Claude Code's `SessionStart` hook names; when no
hook ran, it looks for the session's transcript in `projects/` under Claude
Code's configuration directory, and when none is there, it waits for the file
Claude Code makes in the folder named after the directory Neovim started in.

                                                          *aineo-office-hooks*
Two of the hooks aineo gives the Claude Code it starts in `--settings`
(|aineo-report|) serve the office:
- the `SessionStart` hook, which also tells the editor when Claude Code
  switches session (|aineo-claude-session|), passes on the path of the
  transcript that Claude Code names in its input. A session whose hook
  never ran, as in a folder Claude Code does not trust yet, has its
  transcript looked for in `projects/` when the office shows;
- the `PermissionRequest` hook, which Claude Code runs in the background as
  it is about to ask you to allow a tool. It tells the editor which agent
  asks, the main one or the subagent whose `agent_id` the input names, and
  in which tab. It prints nothing and so decides nothing: the prompt stays
  yours to answer. It starts a headless `nvim` for about 20 ms per prompt,
  which Claude Code does not wait for, and ends itself after 6 seconds
  whatever the editor does, one held at a prompt say. In the permission
  mode `dontAsk`, where Claude Code denies a call without a prompt, it
  tells nothing.
A wait the office is told while it is hidden, or while its tab page is left,
is kept: the agent raises its hand when the office shows, or the tab page is
entered, unless the transcript shows the agent has gone on since, as when you
answered in Claude's terminal. It is kept for 64 agents at most.
The hook was recorded on Claude Code 2.1.308; aineo knows no lowest version
that runs it. Claude Code runs no `PermissionRequest` hook for a sandboxed
command's network request, so the office shows no wait for that prompt.

10. THE AUTOSTART                                            *aineo-autostart*

A bare, interactive `nvim` opens the layout and starts Claude Code by itself,
in the directory Neovim started in. Two scheduled callbacks after |VimEnter|,
so a startup dashboard drawn at `VimEnter` or `UIEnter` — snacks.nvim's,
alpha-nvim, dashboard-nvim, mini.starter — has shown, and the layout
replaces it.

The autostart does not run, and the editor starts as usual, when, in the
order aineo looks for them:
- a setting is wrong (|aineo-configuration|);
- `autostart` is `false` (|aineo-config-autostart|);
- no user interface is attached: `nvim --headless`, `nvim -es`;
- Neovim was given a file to edit: `nvim file`, `git commit`;
- Neovim read its standard input: `echo text | nvim -`;
- Neovim was given something to do besides edit: `-c`, `-S`, `-e`, `-s`,
  `-E`, alone or among other short options (`-Rc`), or a `+` command;
- it runs inside aineo's own Claude terminal or shell terminal
  (`$AINEO_CHILD` set and not empty);
- a session was restored at startup, by a plugin such as auto-session
  from its own `VimEnter` (|v:this_session| set) — `-S` is a startup task
  above;
and, apart from the others, when aineo was loaded after startup, as a
plugin manager loading it lazily does: the keys are mapped then, but
nothing opens. `--cmd`, `-t` and `-q` alone still autostart.

`:checkhealth aineo` tells which of these held, the first in this order
(|aineo-health|).

11. HEALTH CHECK                                                *aineo-health*

`:checkhealth aineo` reads the configuration and the editor's state and

Neovim ~
  The version of the Neovim that runs aineo; an error when it is older

12. LIMITS                                                      *aineo-limits*

The explorer ~
A folder git ignores whole, such as `node_modules/`, shows as one folder
while `I` shows ignored entries, and is listed from disk, one level, as it
unfolds; it has no marks. Outside git, and in such a folder, the filter
matches only the folders already listed, and the tree is read again only by
`R`, as no watch runs there. A path `@` pastes is pasted as it is, spaces
included, which Claude Code may read as the end of the path. The picker `s`
opens is |vim.ui.select()|, whichever picker you installed answers it.

A submodule, and a repository nested in the one shown that git lists as a
folder of its own, shows as a folder listed from disk, one level at a time,
as it unfolds, with no marks inside: its own changes are its repository's;
an untracked nested repository's folder keeps its `?`. Each read of the tree
costs time on Neovim's main loop in proportion to the number of files the
repository lists (some 80 ms for 100 000 files, measured on Neovim 0.12.5),
and so does showing the explorer again, which reads it; the explorer
watches the repository only while it shows.

Links in Claude's terminal ~
Neovim keeps the address of a link a program prints in a terminal (OSC 8)
only in what it draws on the screen: no extmark or other state of the
terminal's buffer holds it (measured on Neovim 0.12.5). aineo reads the text
a link shows (|aineo-links|), not its address, so a link whose text is no
path is not found, and neither is a path the terminal wrapped onto a second
line. A ⌘-click on a link is not aineo's: whether Neovim sees it depends on
the terminal Neovim runs in, which opens the address itself when it opens
OSC 8 hyperlinks, as iTerm2 does (not measured: aineo's tests run without
such a terminal). Claude Code turns the mouse on in its terminal, so in
Terminal mode a single click reaches Claude Code, and only the double-click
is aineo's.

Stopping Claude Code on quit ~
When Neovim quits, aineo stops a running Claude Code from its own
|VimLeavePre| handler, by its keys: one Ctrl-C, then a double Ctrl-C, then
`jobstop()` — up to about 12 seconds. A `VimLeavePre` handler registered
before aineo's that raises an error makes Neovim skip aineo's when the error
is a Vimscript `throw`, or a Lua error and the quit runs from Lua, as aineo's
`\Q` in the last tab does; a Lua error does not when the quit is typed
(`:qa`). Claude Code then only gets Neovim's hangup, and a Claude Code that
hangs outlives the editor. aineo cannot detect this.

A Claude Code attached to a background session (|aineo-claude-session|) is
stopped by `Ctrl+Z` alone, which detaches it and leaves the session running,
then by `jobstop()` when it has not exited in 4 seconds. aineo never presses
`Ctrl-C` in it. How soon `Ctrl+Z` ends the attach was not measured: 4 seconds
is the wait after the second press of a double Ctrl-C, which exceeds the
longest exit measured after it (2.5 seconds).

aineo knows a Claude Code is attached only when it attached it. A Claude
Code that attaches by itself, as when you type `/resume` inside aineo's
Claude for a session that runs in the background, is unknown to aineo:
quitting Neovim presses `Ctrl-C` in it, which cancels that session's running
turn, and `:Aineo new` writes `/clear` into it. Leave such a window with `←`
or `Ctrl+Z` before quitting. Nothing on the screen tells it apart, since the
line Claude Code prints, `Opening "{title}", running in the background
({id})`, also shows in the history of a resumed conversation and after a
`/resume` that attaches nothing; and the list of sessions does not show the
terminal's own attach. What `claude attach` prints, and how it exits, for a
session that has ended was not measured.

The run pane on quit ~
The question before a quit that stops the run pane's processes (|aineo-run|)
is asked from the |ExitPre| event, which `:qa`, `:q` in the last window, `:wq`
and `:x` trigger and `:cquit` and a signal that ends Neovim do not. Neither
that event nor |QuitPre| says whether the command had a bang: aineo notes the
command line you enter (|CmdlineLeave|) until the command it runs is done, so
`:qa!` typed for this quit skips the question, and every other quit asks: a
`:qa!` run by a mapping's `<Cmd>` or by Lua, `ZZ`, `ZQ`, and any quit after a
`:q!` you typed before. A quit that never reaches |ExitPre| (`:cquit`, a
signal) asks nothing, stops the processes all the same, from |VimLeavePre|,
and aineo tells you once, as it begins, that they are being stopped. Neovim
has no way to cancel a quit from a handler: on Cancel aineo opens a tab page,
wipes its empty buffer with it, and closes it again once the command is done,
which makes Neovim give the quit up, and triggers |TabNew|, |TabEnter| and
|TabClosed| autocommands for that page. Neovim unloads every terminal before
|VimLeavePre| and only hangs its pty up, so a process that ignores the hangup
is not stopped by Neovim: aineo stops what is left from a |VimLeavePre|
handler, registered once the first process has opened the layout and Claude
Code has registered its own stop, so that it comes after it. A handler before
it that raises an error makes Neovim skip the handlers after it, and aineo's
stop with them, when the error is a Vimscript `throw`, or a Lua error and the
quit runs from Lua; a Lua error does not when the quit is typed (measured on
Neovim 0.12.5 with `:qa`, `:qa!`, `:x`, `:wq` and `:cquit`, each typed and run
from Lua). A process that leaves its process group and is no descendant of
the shell, as a daemon that calls `setsid` does, is not reached by the stop;
neither is a job that an interactive shell started under job control and
that ignores the hangup, when you `:bdelete!` the shell's terminal, nor a job
that outlives its shell, at a quit or not: a command that runs `set -m` and
is then stopped with Ctrl-C, or the job of a `\X` shell that exits (`sleep &`
and `exit`, under sh or bash), which no code can find (|aineo-run|). zsh hangs
up its jobs at exit by default.

Several tabs ~
Quitting Neovim stops every tab's Claude Code together: each key of the stop
is pressed to every Claude Code that runs, and the waits run side by side,
so the quit takes about the time of one stop, up to about 12 seconds, not
the sum. The tab pages one command closes, such as `:tabonly`, have their
Claude Codes stopped together once the command has ended, in the background:
the editor is not held, and the stop takes the time of one stop, up to 12
seconds, not the sum. The first tab's buffers are taken up again by the next
tab opened only once its Claude Code has ended; a tab opened before is made of
copies, with buffers named with a number. Each tab runs a watch of its
repository once its changes pane has been shown, and each Claude Code that
starts lists the folder's sessions when it resumes one, so several tabs run
several watches and several lists at once. What two real Claude Codes do in
one Neovim, the report each sends and the time a quit takes with several
tabs were not measured: the suites run a fake Claude Code.

The folder's list of tabs is one file for the folder: two Neovims in one
folder write one list, and the last to write wins, as it does for the session
kept for the folder. A reopening of N tabs starts N Claude Codes at once and
runs N lists of the folder's sessions at once (|aineo-claude-session|); the
list is kept again once all have opened. Closing the last aineo tab page with
`:tabclose`, while other tab pages remain, leaves the list as it was before
that tab closed. A reopening resumes a session whose Claude Code in a tab just
closed still stops, without waiting for the stop. A reopening of several real
sessions, one of them attached in the background, was not measured: the suites
run a fake Claude Code.

A tab opened after the first has buffers named with a number that is never
given again (`aineo://report-2`), and a `:tabclose` of the first tab leaves
its buffers `aineo://report` and `aineo://input` in place: the next tab
opened is made of them again.

The terminal pane ~
- `:bdelete` of a shell's terminal needs a `!`: Neovim refuses it without
  one for every terminal that runs a job (E89). `exit` ends the shell
  without it, and so do `:bdelete!` and `:bwipeout!`.
- A Neovim started inside the shell does not autostart aineo, since
  `$AINEO_CHILD` is set there, as it is in Claude's terminal
  (|aineo-autostart|).
- The next start brings no shell back: a shell lives as long as the Neovim
  that started it. Quitting ends it as Neovim ends every terminal's job:
  it hangs the shell up after aineo has stopped Claude Code, and a program
  of the shell's that ignores the hangup, or a job it started with `nohup`,
  outlives the editor.
- The shell's window is as tall as the right column, taller than the Report's,
  so the shell's terminal is resized as the pane shows and as it gives way:
  the terminal redraws, and the top line of its window can differ from where
  it was, the cursor line staying.
- A shell that exits in a tab page you are not in makes Neovim visit that
  tab page and come back, while aineo shows the Report again there. The
  cursor and the mode stay where they were.

Session switches ~
aineo learns of a switch inside Claude Code from Claude Code's session
hooks, which do not always run. Claude Code runs no hook in a folder until
you answer its trust dialog. As its documentation reads, and neither was
measured, it runs none of aineo's under a managed `allowManagedHooksOnly`,
and none under a `disableAllHooks` in any of your settings. aineo gives
Claude Code no hooks when it cannot read the `--settings` of `claude.cmd`
(|aineo-config-claude.cmd|). aineo then hears of no switch, and the next
start resumes the session aineo started. Not seen: what Claude Code does
once a folder's trust dialog is answered "Yes"; and whether a `/fork`
background copy or a subagent tells of a new session. A conversation
moved to the background was seen once running in a new process, started
by Claude Code's background service with aineo's hooks, on a new session
id, with no end of the session aineo followed. aineo follows a new session
that Claude Code's own process in aineo's terminal starts only after it
ends the session aineo follows; one that another process starts under
aineo's hooks, it follows at once, while its own Claude Code runs. The
tab's own Claude Code is the process whose `SessionStart` of the session
the tab started on told aineo first, by its process id — until one has,
the process aineo started in the terminal. Any other process id is
another process, wherever it runs: Claude Code's background service can
be a child of the tab's own Claude Code. So a `/fork` copy whose
`SessionStart` reaches aineo moves the tab to the copy, and a teammate
that runs as a process of its own would too (neither seen). The
teammates and background sessions Claude Code 2.1.292 starts are given its
`--settings`, aineo's hooks among them (read in its program, not run);
aineo ignores every hook that ran after its Claude Code exited, so a
session they start then is not followed. Once aineo follows a session
another process started, a `/clear` or `/resume` in its own terminal is
not followed: it ends a session aineo no longer follows. A hook that
cannot reach the editor tells it nothing, but keeps a switch it completes
as the session the next start in that directory resumes
(|aineo-claude-session|); and once the end of the session
aineo follows is lost, no later switch of that Claude Code is followed,
until it starts again. Each hook starts
a headless `nvim` and returns at once; that `nvim` tells the editor, waits
for its answer, then exits: at once in an idle editor, and once you answer
the prompt in an editor at a prompt.

The settings file ~
The file aineo writes for a `--settings` in `claude.cmd`
(|aineo-config-claude.cmd|) is removed when Neovim exits, also on a hangup
or SIGTERM. A Neovim killed by SIGKILL leaves it in its temporary
directory, readable and writable by you alone (0600), your settings in it,
secrets among them, until the system clears that directory. Each start of
Claude Code writes one more, and none is removed before Neovim exits.
Claude Code 2.1.292 reads the file once, when it starts, so its removal
does not touch a running Claude Code. The teammates it starts and its
background sessions, and their restarts, are started with the same
`--settings` and read the file again at their own start: once Neovim has
exited and removed it, such a start fails. Read in Claude Code's program,
not run.

Reports whose editor is gone ~
Where a report goes when the editor that started Claude Code is gone
(|aineo-report-claims|) rests on what was not measured with Claude Code
itself:
- A conversation moved to Claude Code's background runs as a new Claude
  Code process on a new session id. While the Claude Code it was moved
  from runs in a tab, that tab follows it (Session switches, above) and
  gets its reports. Else no Neovim follows it by itself: its
  reports are kept on disk under that session until a Neovim follows it.
  Once the tab follows it, a report from the tab's own Claude Code, still
  on the session the tab left, is kept on disk under that session, unshown,
  until a Neovim follows it again.
  `:Aineo claim {id}` does, and offers it when its Claude Code has a record
  — written by aineo's hooks, if the background keeps them, else by aineo's
  MCP server at its start. A Claude Code that runs neither aineo's hooks nor
  its MCP server of this version has no record and is not offered.
- How Claude Code runs a hook — through which shell, and whether the shell's
  parent is Claude Code's own process — was measured with stand-ins only.
  Whether Claude Code runs its startup hook before it starts its MCP server,
  and its `SessionEnd` hook and the `SessionStart` after it one at a time or
  at once, was not: aineo orders them by when each hook began.
- "Used last" counts focus: a terminal that sends no focus events, as tmux
  without its `focus-events` option, leaves the last start, switch or claim.
- A process id one of your own processes took after Claude Code ended is
  taken for that Claude Code's until a hook or a server writes over its
  record: `:Aineo claim` may offer its session meanwhile.
- A report held by a Neovim at a hit-enter prompt that, once you are done,
  follows another session is lost: the server has answered Claude already.
- A Neovim listening on `host:port`, or on a socket another user owns, is
  never offered a report but by its own Claude Code, nor told a switch.
- Where the file system refuses hard links, aineo's MCP server writes no
  record at its start: its reports find their session by the id Claude
  Code started it on, and `:Aineo claim` does not offer a Claude Code
  without aineo's hooks there.
- A Neovim that lets go of a claim reads the claim, checks that it names
  that Neovim, then removes it. A claim another Neovim makes in the
  microseconds between that check and the removal is removed with it, and
  the session's reports go to the editor that started its Claude Code
  until it is claimed again.
- A session hook that waits more than 3 seconds for another one to finish
  with the record of their Claude Code records nothing, and a switch it
  completes is not followed.

The 80-column start ~
At startup, a message longer than |v:echospace| — 68 columns on an 80-column
screen — holds Neovim at a hit-enter prompt. aineo's line for a
`claude.cmd` that is not executable fits for a command name of up to 29
characters; a longer one, such as an absolute path, still prompts. Its
line for a `--settings` in `claude.cmd` that it cannot read fits; it says
no more than that, not which file or why: |aineo-health| says why.

The session list ~
- Whether `claude agents --json` starts Claude Code's background service
  was not measured, and aineo does not guard against it: `:Aineo sessions`
  runs it each time, and so does each start that resumes
  (|aineo-claude-session|). That run is bounded as the list of `:Aineo
  sessions` is, at 5 s and 1 MiB of output. When it cannot run, exits with
  a failure, runs past the bound, prints more or prints what is not JSON,
  the start tells nothing and resumes the kept session once the run has
  ended.
- Whether it lists the session of each tab's Claude Code was not measured.
  When it does not, the list holds the others alone and no row says
  `[tab {n}]`.
- Claude Code's documentation says what an entry holds; only the fields
  aineo reads are checked, and an entry with no session id is not listed.

The new session key ~
- Send's paste and Enter in one write was measured with Claude Code
  2.1.281; that Claude Code takes the pasted `/clear` and Enter of `:Aineo
  new` as a command was not measured, only by the fake `claude` of aineo's
  tests.
- What Claude Code does with a `/clear` written while a turn runs was not
  measured: aineo has no sign of a turn on Claude Code's screen, since the
  input box shows during one, and writes `/clear` as Send writes during a
  turn (|aineo-send|). Claude Code may queue it, run it, or take it as text.
- Where hooks do not run (Session switches, above), aineo hears of no switch
  after a `/clear`, and the panes stay on the session left.
- The prompt is read in Terminal mode, where Neovim keeps the window's
  cursor on the terminal's, so the cursor moves to Claude's window before
  the read, and back when the prompt shows text.
- A draft whose cursor you moved back to the start of its first line reads
  as an empty prompt, and `/clear` and Enter are written in front of it:
  Claude Code receives `/clear` followed by your draft as one line, which it
  may run as `/clear` with the draft lost. aineo cannot tell this from the
  grey example of an empty prompt.
- A permission dialog drawn in the few tens of milliseconds before aineo
  notices it receives the paste and Enter of `/clear`, as Send's do (Send
  and a dialog, below).

Send and a dialog ~
A permission dialog drawn in the few tens of milliseconds before aineo
notices it receives Send's paste and Enter. What the dialog does with them
was not measured.

Undo after a Send ~
- A Send can reach a Claude Code that has just ended before aineo notices:
  the write to its terminal then fails, and Send puts Input back as it was
  and shows the error. Emptying Input and putting it back are then one
  undo step: the first `u` changes nothing you can see, and the second
  undoes your own last change. A Visual Send does the same, and `gv` then
  selects the text again.
- 'undolevels' decides how many Sends `u` can reach. At 0, `u` toggles the
  last Send alone: after two Sends, `u` brings back the second's text, a
  second `u` empties Input again, and the first's text never comes back. At
  -1, `u` brings nothing back. The same holds for a Visual Send.

Repeating a Visual Send ~
A Visual Send removes the selection with Vim's own `"_d`, so `.` after it
repeats that removal: it removes as much text again, at the cursor, and
sends nothing. `u` brings it back.

A block's edge on an invalid byte ~
A byte that is not UTF-8, followed by a combining mark or a zero-width
joiner, is one character to a block's `"_d`. When a block's edge falls on
it, `"_d` removes both, and the Visual Send sends one of them: the byte
when the block ends on it, the mark when the block starts there.

A characterwise start past an invalid byte ~
Under 'virtualedit' set to `all`, a characterwise selection can start one
cell past a byte that is not UTF-8, drawn as `<c3>`, while Vim still places
its start on that byte. `"_d` then removes the byte, and the Visual Send
sends from the character after it, without the byte.

The changes pane ~
- A large diff: a diff shows at most 1 MiB of what git gave, cut at the
  last line break within it, or a first line longer than that cut there,
  under one line saying how much of it is shown. git still gives the whole
  diff first, which takes its time and memory. With the whole file as
  context (`F`) a diff is larger, and the whole diff of a long session is
  cut sooner.
- A large file under a commit: `gf` takes no more than the 1 MiB it shows
  from git and stops it once it has come, so the editor holds about 1 MiB
  of a file of any size; the note under the file gives its whole size,
  which git listed first. git itself may unpack a file stored in a pack
  whole before it prints a byte: it streams one that is not a delta, and
  unpacks a delta whole.
- A large repository: each read runs git over the whole working tree. On a
  repository of 20 001 files whose every file had been rewritten with its
  own content, one read took 1.5 to 3.1 seconds. A git that runs past 10
  seconds is stopped, and the read said to have failed.
- A pull, a merge, or a rebase onto newer upstream commits during the
  session lists those commits, and their files, as the session's: the
  commits window lists every commit reachable from `HEAD` and not from the
  base.
- A restart of Claude Code in another working directory keeps the first
  repository. A session whose base was kept for another repository, or
  whose kept file aineo cannot open, takes `HEAD` as its base here, and
  the files you save then are marked; this editor holds both until it
  quits, a switch back included, and never keeps them: what was kept
  stays as it was. A kept file that holds anything but what aineo
  writes, one cut short say, counts as nothing kept, and is replaced. A
  repository moved or renamed on disk counts as another, so its
  sessions' bases are not read back there. A session whose base could
  not be written is held until a write succeeds: aineo writes it again
  as you follow the session again, and at each save. A kept base git no
  longer has, garbage-collected say, is kept, and the pane says in git's
  words that it cannot be read.
- Two editors following one session in one repository keep the first
  base kept for it, and each other's saves. A save the other editor keeps
  between this editor's read of the kept file and its write is lost from
  the file, though that editor still marks it: it is kept again when
  that editor next saves a file it had not saved before. Between that
  read and that write, the last base written wins too: the other editor
  shows its own base until its next such save, and this editor's from
  then on.
- Where aineo cannot watch the working tree's subdirectories (Linux), the
  files window says so below its first line: a change in a subdirectory
  shows at the next showing of the pane, save or commit, and a branch moved
  by `git update-ref` from another worktree, a tag, a commit on another
  worktree's detached `HEAD`, and a fetch another worktree ran are missed
  too, the commit graph's included (|aineo-changes-graph|); a fetch run in
  your repository's main worktree is seen; what landed in your working
  branch then shows what such a fetch brought at the next showing of the
  pane. No timer reads the repository on a schedule; the only timer is the
  pause before the files window follows the commits window's cursor.
- Choosing another line in the commits window reads the files window again
  for it: another worktree's heading or commit is read in that worktree,
  and a heading's base with it.
- What landed in your working branch is what your repository last fetched:
  aineo never fetches, so work merged on the remote shows once a fetch, by
  you, an agent's worktree or an editor's background fetch, has moved the
  branch your repository holds. It counts from the session's base, not from
  the start of the session: a session begun on a branch forked before the
  working branch's last commits lists everything the working branch gained
  since the fork. A checkout on the working branch itself lists its own
  commits both among the session's and among what landed. A working branch
  that shares no history with the base lists its commits, and the files
  under its heading fail with git's `no merge base`. A name git finds
  ambiguous is read as git reads it: with a local branch called
  `origin/dev`, the setting `origin/dev` names that branch, and
  `refs/remotes/origin/dev` names the remote one. When the default branch
  of the remote was renamed and pruned, `origin/HEAD` names a branch that
  is gone, and the section says it names no commit until
  `git remote set-head origin -a` points `origin/HEAD` at the new default,
  or `changes.working_branch` names it. Each read of the commits
  window runs two or three more git processes for it (the default branch of
  the remote, unless the setting names one; the commit the name names; the
  commits between it and the base), and the files window under the heading
  one.
- The other worktrees have no watch of their own. A file written in a
  worktree outside your top level shows at the next change aineo's watch
  sees in your repository — that worktree's `git add` or commit, a file
  written inside your top level, your save, a fetch, a tag, a branch made
  or deleted — or the pane's next showing.
  On Linux, a file written in a worktree inside your top level, a
  worktree added or removed, and another worktree's commit may show only
  then too (not measured there). Each worktree costs its reads in the
  commits window, at every read: its repository, its base and its commits,
  one git after another, and the files window reads the one worktree it
  lists; a fetch by any program, an editor's background fetch included,
  costs the same read. Your own lines asked for during that read show once
  the worktree being read is done, which a slow git there delays. A
  worktree whose path holds a line break is listed, but its section says
  only that its read failed: git gives that path on lines of its own.
  Once a worktree's branch is merged by rebase, its commits stay listed
  under it until the worktree is removed.
- A worktree's base counts from the working branch, whatever your own
  worktree is on: a worktree forked from your own feature branch lists that
  branch's commits the working branch does not hold yet, besides its own,
  and so do the files of its whole change. Each read of the commits window
  reads the working branch's commit twice, once for the worktrees, however
  many, and once for what landed (a git process each, and one more each to
  find the remote's default branch unless the setting names a branch); the
  files window under a worktree's whole change reads it once. Your upstream
  is read only when a worktree gets no base from the working branch.
- A branch a worktree is rebasing or bisecting: git lists that worktree as
  detached, so |aineo-changes-s| may offer its branch as `[branch]`, though
  git refuses to delete it. Shown alone, it is the branch as it stands, at
  its tip from before the rebase until the rebase ends.
- When the editor quits, aineo stops its watch, but a git it is running
  then runs to its end, outliving the editor.
- A buffer named for a diff that aineo did not make, such as one a restored
  session made under `aineo://diff/{path}`, cannot give up its name while
  Neovim allows no change of text, or in the command-line window: when the
  diff Enter read for that name arrives then, Neovim shows an error with a
  stack trace, the diff is not shown, and aineo does not try again. Enter
  on the line again shows it, the other buffer giving its name up.

Claude's window name ~
- A status-line plugin that sets the status line of every window replaces
  aineo's in Claude's window; lualine does with its default configuration,
  within a second. Such a plugin can show `b:aineo_session_name` and
  `b:aineo_session_folder` of Claude's terminal (|aineo-claude-session|).
- With 'laststatus' set to 3, the one status line shows Claude's name and
  folder only while the cursor is in Claude's window.
- With `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` set to `1` in the environment
  Neovim started in, Claude Code sets no title, and Claude's window reads
  `Claude Code` for the whole session.
- Claude Code 2.1.292 titles a session after its first turn, and the
  name then follows the session: after an in-session `/resume` it is the
  resumed session's title, and after `/branch` `{first prompt} (Branch)`.
  Not measured, and so not known to show: a name `/rename` gives and the
  title of a start with `--resume`. The glyph while Claude Code is busy is
  read from the program, not seen (|aineo-limits|, The activity indicator).
  A glyph is left out
  when the title's first character is neither a letter nor a digit and a
  space or nothing follows it: a title `✳` alone reads `Claude Code`.
  Below U+0100 the letters are the ASCII and Latin-1 ones, `×` and `÷`
  not among them, whatever 'iskeyword' holds.

The activity indicator ~
- It reads the title Claude Code 2.1.301 puts on its terminal, a spinner
  glyph in front of the name while it works, as read from that version's
  program: it has not been seen in a real turn. A later version of Claude
  Code may change that title: the indicator then shows nothing, or the wrong
  thing, until aineo is changed to read it.
- With `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` set to `1`, `true`, `yes` or `on`
  (in any case), Claude Code sets no title; `0`, `false` and any other value
  leave it on. Either way no tab shows activity; `:checkhealth aineo` warns
  (|aineo-health|). Unset the variable before starting Neovim to have it.
- The indicator works inside tmux, screen and zellij. Under them, which
  Neovim hands to Claude Code as `TMUX`, `STY` or `ZELLIJ` with a value,
  Claude Code 2.1.301 keeps its title still, so aineo starts Claude Code
  without `TMUX`, `TMUX_PANE`, `STY` and `ZELLIJ` (`claude.hide_multiplexer`,
  on by default: |aineo-config-claude.hide_multiplexer|). Claude Code inside
  aineo then does not know about the multiplexer, and its features that
  depend on knowing — agent teams opening panes in tmux, say — are off
  there. The shell terminal and every other job keep the editor's
  environment. With `claude.hide_multiplexer` set to `false` Claude Code
  knows, and no tab shows activity; `:checkhealth aineo` warns. Under tmux
  Claude Code then copies a mouse selection with a clipboard sequence
  wrapped for tmux, which Neovim's terminal prints in Claude's window as
  `52;c;<base64>`; the plain one it sends otherwise reaches the clipboard.
- A shell command Claude Code runs in the background is not activity; a
  subagent running in the background is, and keeps the tab busy after the
  reply.
- A question or a permission dialog ends a busy spell: a tab whose Claude
  Code waits for you while you are in another tab shows ●, not ◒ or ◓; in
  the tab you are in, it shows nothing.

The first follow's move ~
- Where the file system refuses hard links — exFAT, FAT, some network and
  FUSE mounts — or the working directory's draft or reports file is a
  symbolic link, the first session aineo follows takes that draft and
  those reports by looking for the session's file and then renaming the
  directory's to it; a symbolic link stays one. Another Neovim that makes
  that session's file between the look and the rename has it replaced.
- An aineo older than sessions, in the same working directory, that
  saves its draft in the instant between this editor's link of the
  directory's draft to the session and its removal of the directory's
  name has that save removed.
- Two editors whose first follows take the same directory's draft or
  reports at the same moment can, on APFS, both remove the directory's
  name: their two sessions then share one file, and each session's
  reports appear in the other's Report. A Neovim that stops between the
  link and the removal leaves the directory's name and the session's on
  one file in the same way.

A session's draft ~
- What you type while Input shows a session whose draft cannot be read is
  saved nowhere: aineo never replaces that draft, and a quit loses the
  text. Making the file readable again does not save it either, until
  Input is emptied and another session is followed.
- An Input emptied — by Send, or by you — while its saves fail refuses
  the next switch: it stays the session it followed, empty, and you are
  told that Input keeps its text. Once the saves work again, what you
  type is kept as that session's draft, not the new one's.

A session in place of one with no conversation ~
- At an editor's first start, what Input holds before the session that
  takes the place of a resume with no conversation is ready — typed then,
  or the working directory's draft put into it — stays the working
  directory's draft when the resumed session had a draft of its own,
  however long that start takes: Input shows the resumed session's draft
  instead. The directory's draft is then shown only once an editor first
  follows a session with no draft of its own. Reports kept unshown with
  the directory's while a claim held, before their session had Reports of
  its own, stay with them the same way, and are then shown in the Report
  of whichever session takes the directory's.
- Another Neovim that shows the resumed session, by `:Aineo claim` or as
  the session of its own exited Claude Code, is not told: it goes on
  showing it, and its next save of Input or new `*` writes that session's
  draft or base again, beside the new session's.
- A session whose Claude Code still runs, in another Neovim say, is not
  handed over: the new session starts with nothing of it. aineo knows of a
  running Claude Code only when aineo's session hooks or its report server
  run in it.
- A new session that already has a Report, a draft or a base of its own
  keeps it, and the resumed session's stays where it was.
