1. INTRODUCTION                                                        *aineo*

aineo turns Neovim into a console for Claude Code. Claude Code's own
interactive CLI runs in a terminal on the left; on the right, the Agent
Report shows what Claude says it is doing, above an Input buffer where you
write your next message. Files you open land in a column between the two.

Every command sits behind one prefix key, `\` by default, in Normal mode:
`\s` sends Input to Claude, `\o` opens or restores the layout, and `\r`, `\i`
and `\c` move to the Report, Input and Claude — `\c` in Terminal mode, so
that what you type next goes to Claude, unless Claude Code has exited.
`\tcn` hides or shows the line numbers of Claude's window. `\pa` and `\pc`
switch the right column between the agent pane, the Report over Input, and
the changes pane (|aineo-panes|). In Visual mode, in Input, `\s` sends the
selection alone and removes it from Input (|aineo-v_\s|).

aineo answers none of Claude Code's questions: its permission prompts, its
trust dialog and every other dialog are yours to answer, in its terminal.
aineo allows one tool of its own without asking, the report tool
(|aineo-report|), and nothing else.

==============================================================================
2. REQUIREMENTS AND INSTALLATION                               *aineo-install*

Requirements:
- Neovim 0.12 or later. aineo is tested on the newest Neovim release,
  0.12.5.
- Claude Code, the `claude` command, installed and signed in. aineo's
  behaviour was measured on Claude Code 2.1.281; the resume of Claude's
  session, and the new session that takes the place of a resume Claude
  Code has no conversation for (|aineo-claude-session|), on 2.1.283.
- git 2.36 or later, the `git` command, for the changes pane
  (|aineo-changes|). aineo is tested with git 2.50.1.

With lazy.nvim, load aineo at startup, so that its autostart can run
(|aineo-autostart|): >lua
    { 'mathiasbrito/aineo', lazy = false }
<
aineo works without a `setup()` call. To configure it, see
|aineo-configuration|; then run `:checkhealth aineo` (|aineo-health|).

3. THE LAYOUT                                                   *aineo-layout*

The layout fills one tab page with three windows; the right column's two
show one pane at a time, here the agent pane:

    +--------------------+--------------------+
    |                    |    Agent Report    |
    |    Claude Code     |                    |
    |    (terminal)      +--------------------+
    |                    |       Input        |
    +--------------------+--------------------+

- Claude Code's terminal takes the left half of the columns.
- The Agent Report, `aineo://report`, takes the top of the right column:
  two thirds of its rows by default (|aineo-config-layout.report_height|).
  It is read-only to you.
- Input, `aineo://input`, takes the rest: a scratch buffer, left out of
  `:ls` and `:bnext`, where you write what Send gives Claude (|aineo-send|),
  kept as a draft until you send it (|aineo-draft|).
- The changes pane shows in the same two windows in their place
  (|aineo-panes|).

The Report and Input wrap long lines between words, a wrapped line keeping
its indent ('wrap', 'linebreak', 'breakindent'), whatever your own settings.
Opening or restoring the layout sets this again: `\o`, or `\r`, `\i` or `\c`
when their window is gone, and so does `\pa`, `\r` or `\i` showing the agent
pane again. A `:setlocal nowrap` in either lasts until then. Claude's
terminal, the changes pane, and a file shown in or split from those two
windows, keep yours.

Opening the layout closes the tab's other windows (floating ones stay); their
buffers stay loaded. The cursor starts in Input's window, which shows the
changes pane's commits instead when the layout is opened anew while the
changes pane shows (|aineo-panes|). The Neovim startup buffer becomes Input;
a file the current window shows stays, as the file column.

Panes ~
                                                                 *aineo-panes*
The right column's two windows show one of two panes, switched in place: the
same two windows, at the same sizes, show the other pane's buffers.

- The agent pane: the Agent Report over Input, as the layout opens.
- The changes pane: `aineo://changes-files` in the Report's place, over
  `aineo://changes-commits` in Input's, listing the session's changed files
  and its commits (|aineo-changes|). Each is a scratch buffer, read-only to
  you; `:edit` there writes its list again. A buffer of yours under either
  name, such as one a restored session made, gives the name up: it is wiped
  out, or kept unnamed when you changed its text.

`\pa` (|:Aineo-pane|) shows the agent pane and `\pc` the changes pane; the
pane already shown stays as it is (the changes pane is read again,
|aineo-changes|), unless one of its windows shows the other pane's buffer
there, as a refused switch or you can leave it (the commits buffer in
Input's window, say): they then show the pane's own buffer there. The
cursor stays in the window it was
in. From another tab page they switch the pane in the layout's tab page,
restoring the layout there first when one of its windows is gone, and
leave you where you are. `\r` and `\i` show the agent pane first, then move
to the Report or Input; `\c` and `\tcn` leave the pane as it is. Send sends
Input while the changes pane hides it (|aineo-send|). When a window will
not take its buffer — 'winfixbuf' is set there, say, or you are in the
command-line window — aineo tells you why, once, and gives each window back
the buffer it showed. A window that will not take that one back either
keeps the other pane's buffer; `\pa` or `\pc` then shows its pane in both
windows.

The Report and Input are kept while hidden, with Input's text and its draft.
A buffer shown again comes back as it was scrolled. When a report arrived
while the agent pane was hidden, the Report's cursor is on its last line,
where an arriving report puts it, once the agent pane shows again with the
Report in its window — by `\pa`, `\r`, `\i` or `\o`.

aineo keeps the pane shown until the editor quits: `\o` restores the layout
with it, and so does the layout opened anew once its windows were closed.

The changes pane ~
                                                               *aineo-changes*
The changes pane lists what changed in your repository since aineo first
started Claude Code in this editor: the session, which lasts the editor's
life. Its repository is the one Claude Code's working directory was in at
that start, and its base is the commit `HEAD` named then. A restart of
Claude Code keeps both. A start aineo could not make — `claude.cmd` not
executable, say — takes neither; a Claude Code that starts and then fails
takes both.

The files window, `aineo://changes-files`, lists every file that differs
from the base, committed since or not, staged or not, and every new file
your ignore rules leave in, one per line, in git's order: >
    * M lua/aineo/init.lua
      ? notes.txt
      R old.txt → new.txt
<
The letter is the kind of change: `A` added, `M` modified, `D` deleted, `R`
renamed, after its old path, `T` turned into a link or back, `?` new and
untracked; a copy shows as added. The `*` marks a file you saved from this
editor since the base was taken, or while aineo first looked for the
repository it then found — `:write`, `:update`, `:wall`, a part of a buffer
written to a file or appended to one, the file written whatever its buffer
is named, a file opened through a symbolic link included. A file you and
Claude both changed is marked too: aineo cannot tell who changed what. A
path holding a line break, a control character, a double quote or a
backslash is shown between double quotes, each of those escaped as git
escapes it; characters outside ASCII are kept as they are, where git writes
them in octal. With nothing changed, the window says "No files changed on
this session".

The commits window, `aineo://changes-commits`, lists the session's commits,
newest first, by abbreviated id and subject, or says "No commits on this
session".

Enter on a file's line shows its unified diff from the base, and on a
commit's line that commit's diff, in the middle column (the file column,
below). The diff is read-only: a buffer named `aineo://diff/{path}` or
`aineo://commit/{id}`, with 'filetype' `diff`, wiped once hidden. The cursor
stays in the pane, so `j` and Enter step through the list: when you press
Enter again before a diff was read, only the last Enter's diff is shown.
Enter on any other line does nothing. When the middle column has no room
for the diff, aineo says so and shows nothing.

The pane is read again whenever it is shown — `\pc`, `:Aineo pane changes`,
`\o`, or the layout built anew showing it — and, from its first showing
until the editor quits, when a file is saved, when a file of the working
tree changes, and when the branch moves: a commit, even one that changes no
file, an amend, a reset, a checkout. One read of each window runs at a time,
and the cursor stays on the line it was on while that line is listed. A
diff already shown stays as it was until you press Enter on its line again.
A list or a diff read while Neovim allows no change of text — an
expression mapping waiting for a key or in |input()|, or a completion
function still running — is shown once Neovim allows it again, with nothing
told, and so is a diff read while the command-line window is open, once it
closes (but see |aineo-limits|).

Until git has answered, each window says aineo is reading the repository.
When Claude Code's working directory is in no repository, both windows say
so, naming the directory, and give git's words below, which tell a
repository git refuses — one of another owner, or a bare one — from none;
when `git` is not found, both say that. aineo then looks again whenever the
pane is shown or a file is saved, and a repository made since — by
`git init`, say — becomes the session's, its `HEAD` then the base. When the
base is no longer behind `HEAD` — after a reset to before it, or a checkout
of another branch — the commits window says so above what git lists, and
the base stays. A read that fails keeps the list shown, under one line
giving git's words. When aineo's watch of the repository fails, both
windows say so until the pane is shown again, which starts it again.

The file column ~
A file you open from one of the three windows — `:edit`, a picker, a jump —
moves to a column between Claude's and the right column, created on first
use and reused afterwards; the aineo window keeps its own buffer. While the
file column is open, the three columns take a third of the screen each.
Only file buffers move: help, terminals and scratch buffers stay where they
were opened until `\o` restores the layout.

A diff Enter shows from the changes pane (|aineo-changes|) takes the file
column's window as a file does, and the next file or diff takes its place:
the column keeps one window for both. A changed file that cannot leave that
window keeps it, and the diff opens above it.

Claude's session ~
                                                        *aineo-claude-session*
Each Claude Code session aineo starts gets an id of its own, which aineo
keeps for the directory Claude Code starts in: the working directory of that
start, which `:cd` changes. The next start there — in a new Neovim, or `\o`
once Claude Code has exited — resumes that session (`--resume`), and the
conversation goes on where it stopped. A directory where aineo has started
no session gets a new one (`--session-id`). The ids are kept under
`stdpath('state')` in `aineo/claude-sessions/`, one file per directory that
only you can read and write, and are never removed.

A session in which nothing was sent leaves no conversation, and Claude Code
cannot resume it: it prints "No conversation found with session ID: …" and
exits. aineo then starts a new session in its place, in the windows that
showed it, and keeps its id instead. At each start that follows a session
in which nothing was sent, Claude Code 2.1.283 shows nothing for about a
second, then the message for about half a second before the new session
takes its place. If you were typing in Claude's window you are left in
Normal mode there: `\c` puts you in the new prompt. A resumed Claude Code
that exits any other way shows its exit as usual, and its id stays kept. A
resume that fails some other way — a Claude Code that words the message
otherwise, or exits with another code — then fails the same way at each
start there: removing `aineo/claude-sessions/` under `stdpath('state')`
makes every directory start a new session.

aineo resumes the session it started, not one you switch to inside Claude
Code (`/clear`, `/resume`), and ignores a conversation you ran in a plain
terminal in the same directory. Two Neovims in one directory resume the
same session.

Input's draft ~
                                                                 *aineo-draft*
What you write in Input is kept as a draft, one per working directory,
beside the Reports: under `stdpath('state')` in `aineo/drafts/`, in a file
only you can read and write. It is saved a second after each change, at
once when Input becomes empty, as Send leaves it, and, for a change not
saved yet, when Neovim quits. Nothing asks you anything at quit, and a crash
loses at most the last second's typing. The working directory is the one of
the first time the layout opened, for the editor's life.

The draft comes back into an empty Input: the first time the layout opens
in this editor, and again once Input's text was dropped — `:bwipeout`,
`:bdelete`, `:edit!` — as soon as Input is shown again. Its coming back is
not a change of yours: `u` does not take it out. It never replaces text you
have written, and an Input that Send emptied stays empty.

Two Neovims in one working directory share one draft, and the last change
in either wins: a Neovim that quits with no change unsaved leaves the draft
as the other left it.

A change not saved yet is saved as you quit with `:quit`, `:qall`,
`:wqall`, `:xall` or `ZZ`, and again, when that save failed or did not
run, as Neovim unloads Input on its way out. `:cquit` has only that second
save, which a |BufWinLeave| or |BufUnload| handler that fails before
aineo's can skip. A |QuitPre| handler that fails before aineo's — a
Vimscript `:throw`, or any error when the quit runs from Lua — skips both
saves, for every quit that fires |QuitPre|. Either way, the draft then
holds what was saved a second after each change. A Neovim ended by a
signal — its terminal window closed, `kill` — saves nothing as it ends:
like a crash, it loses at most the last second's typing.

A draft that cannot be read, put into Input or written is told once as a
warning. While you type in Insert, Replace or Terminal mode — in Input or
in Claude's terminal — the warning waits until you leave that mode, with
`<Esc>`, `CTRL-C` or `CTRL-\ CTRL-N`, so that its prompt never takes a key
you type there.

Restoring ~
The three windows keep their sizes: the layout puts its proportions back
when a window closes, when the editor is resized and when you enter its tab.
`\o` (|:Aineo-open|) restores the layout while any of its windows is left:
it recreates the windows that were closed, in their places, and keeps the
pane the right column shows (|aineo-panes|). The layout lives in one tab;
from another tab, `\o` moves you to it.

4. COMMANDS                                                   *aineo-commands*

                                                                      *:Aineo*
:Aineo {subcommand}	Runs one of aineo's actions. Completion offers the
			subcommands, and the panes after `pane`. Without one
			of them, or with anything else, it tells you, with
			one error, which ones it takes.

                                                                 *:Aineo-send*
:Aineo send		Sends Input to Claude (|aineo-send|). It takes no
			range: Neovim refuses `:'<,'>Aineo send` with E481.
			A selection is sent by `\s` in Visual mode
			(|aineo-v_\s|).

                                                                 *:Aineo-open*
:Aineo open		Opens the layout around Claude's terminal, starting
			Claude Code when it is not running — again after it
			has exited — or restores the layout while it is open.

                                                               *:Aineo-report*
:Aineo report		Shows the agent pane, then moves the cursor to the
			Agent Report.

                                                                *:Aineo-input*
:Aineo input		Shows the agent pane, then moves the cursor to Input.

                                                               *:Aineo-claude*
:Aineo claude		Moves the cursor to Claude's terminal and enters
			Terminal mode there, so that the keys you type next
			reach Claude Code: its prompt, or the dialog it shows.
			Once Claude Code has exited it stays in Normal mode,
			since a key typed in Terminal mode would close the
			terminal and its exit with it.

When Claude Code exits while you are in its terminal in Terminal mode — after
`/exit`, say, or as it fails at its start — aineo puts you back in Normal mode
there, so that its exit stays on screen and the next key you type is a
Normal-mode command. `i`, `a` and |:startinsert| leave that terminal in Normal
mode too. Any other terminal of yours keeps Neovim's own behaviour.

`report`, `input`, `claude` and `pane` open the layout first when their window
is gone (for `pane`, either window of the right column, or a buffer of the
pane wiped or deleted; for `report` and `input` while the changes pane shows,
the Report or Input wiped or deleted too), around Claude's terminal as it is —
its exit on screen when Claude Code has exited. They start Claude Code only
when there is no terminal to show: before the first start, or again, in a new
terminal, once the terminal was wiped (|:bwipeout|). Wiping it from Claude's
window closes that window; a window Neovim cannot close, such as its last one,
stays on an empty buffer until `claude` opens the layout there again —
`report` and `input` do so only when their own window is gone too. A file
opened in Claude's window as the terminal is wiped stays in view, and moves to
the file column when the layout opens again. Of the actions, only `open`
restarts an exited Claude Code; aineo restarts one by itself only in place of
a resume Claude Code has no conversation for (|aineo-claude-session|).

                                                       *:Aineo-claude-numbers*
:Aineo claude-numbers	Hides the line numbers of Claude's window, 'number'
			and 'relativenumber', when it shows either, and shows
			them again as they were when aineo last hid them,
			whichever buffer Claude's window showed then, when it
			shows none: 'number' alone when aineo has hidden none
			before. It acts on the buffer Claude's window shows,
			whichever it is, changes no other window, and leaves
			the cursor and the mode where they are; from another
			tab it acts on Claude's window in the layout's tab.
			Without a Claude window — the layout or Claude's
			window closed, or Claude's window left without its
			terminal once the terminal was wiped, on an empty
			buffer or on a file Neovim showed there — it changes
			nothing and warns you once.

			aineo keeps your choice until the editor quits, and
			gives it to every Claude terminal new to Claude's
			window — Claude Code restarted by `open`, the new
			session that takes the place of a resume with no
			conversation, a wiped terminal started again, a
			terminal you bring back there yourself — and to
			Claude's window when it is opened anew. Numbers you
			set yourself in Claude's window afterwards stay as
			you set them, until another terminal or a new window
			comes. Pressed while Claude's window shows another
			buffer, it hides or shows that buffer's numbers, and
			Claude's terminal gets the same when it next comes
			back there; numbers it hides there are also those the
			next toggle shows Claude's terminal again, in place of
			the terminal's own. A file opened from Claude's window
			keeps your own numbers.

                                                                 *:Aineo-pane*
:Aineo pane {pane}	Shows {pane} in the right column, `agent` or
			`changes` (|aineo-panes|). When it shows already, the
			layout stays as it is (the changes pane is read
			again, |aineo-changes|), unless one of its windows
			shows the other pane's buffer there: it then shows
			{pane}'s buffer there. Without a pane, or with
			anything else, it tells you, with one error, which
			ones it takes.

When an action fails — `claude.cmd` is not executable, say — aineo tells you
once, with one error message starting with `aineo:`, and opens nothing.

5. MAPPINGS                                                   *aineo-mappings*

aineo defines one Normal-mode `<Plug>` mapping per action, and
`<Plug>(aineo-send)` in Visual mode too. Map them to keys of your own when
you turn the prefix off, or when a prefix key is yours: >lua
    vim.keymap.set({ 'n', 'x' }, '<Leader>as', '<Plug>(aineo-send)')
<
                                                        *<Plug>(aineo-send)*
<Plug>(aineo-send)	Does what |:Aineo-send| does. In Visual mode, sends
			the selection alone (|aineo-v_\s|).

                                                        *<Plug>(aineo-open)*
<Plug>(aineo-open)	Does what |:Aineo-open| does.

                                                      *<Plug>(aineo-report)*
<Plug>(aineo-report)	Does what |:Aineo-report| does.

                                                       *<Plug>(aineo-input)*
<Plug>(aineo-input)	Does what |:Aineo-input| does.

                                                      *<Plug>(aineo-claude)*
<Plug>(aineo-claude)	Does what |:Aineo-claude| does.

                                                *<Plug>(aineo-claude-numbers)*
<Plug>(aineo-claude-numbers)
			Does what |:Aineo-claude-numbers| does.

                                                    *<Plug>(aineo-pane-agent)*
<Plug>(aineo-pane-agent)
			Does what `:Aineo pane agent` does (|:Aineo-pane|).

                                                  *<Plug>(aineo-pane-changes)*
<Plug>(aineo-pane-changes)
			Does what `:Aineo pane changes` does (|:Aineo-pane|).

Prefix keys ~
                                                                  *aineo-keys*
Once the editor has started, aineo maps the prefix (|aineo-config-prefix|)
followed by these keys to each `<Plug>` mapping, globally, in Normal mode,
and `\s` in Visual mode too:

                                                                    *aineo-\s*
\s		|<Plug>(aineo-send)|
                                                                    *aineo-\o*
\o		|<Plug>(aineo-open)|
                                                                    *aineo-\r*
\r		|<Plug>(aineo-report)|
                                                                    *aineo-\i*
\i		|<Plug>(aineo-input)|
                                                                    *aineo-\c*
\c		|<Plug>(aineo-claude)|
                                                                  *aineo-\tcn*
\tcn		|<Plug>(aineo-claude-numbers)|
                                                                   *aineo-\pa*
\pa		|<Plug>(aineo-pane-agent)|
                                                                   *aineo-\pc*
\pc		|<Plug>(aineo-pane-changes)|
                                                                  *aineo-v_\s*
\s		|<Plug>(aineo-send)| in Visual mode (|aineo-send|)

Visual mode here is Visual mode alone: in Select mode, `\s` is text you
type.

A key sequence you mapped yourself — a global mapping in the same mode,
when the editor has started — stays yours, and aineo maps the others: with
your own `\s` in Normal mode, aineo still maps `\s` in Visual mode, and the
other way round. A mapping local to a buffer is not counted: it wins in its
own buffer only. A mapping you make later replaces aineo's. A mapping that
only overlaps aineo's key is not yours in this sense: with your own `\sa`,
aineo still maps `\s`, and `\sa` then waits for 'timeoutlen' after `\s`;
with your own `\t` or `\tc`, aineo still maps `\tcn`, and with your own `\p`
— or `<Leader>p` while the leader is `\` — it still maps `\pa` and `\pc`:
yours then waits for 'timeoutlen'.

The prefix is read once, when the editor has started (|VimEnter|): a
`setup()` or `vim.g.aineo` that changes it later maps nothing until the next
start. When a plugin manager loads aineo after startup, the keys are mapped
in the next event-loop tick.

`\` is also the leader when |mapleader| is unset or empty, and the local
leader when |maplocalleader| is: a filetype plugin's `<Leader>` or
`<LocalLeader>` mapping local to a buffer then shadows aineo's key there —
Neovim's own ChangeLog plugin maps `<Leader>o`. `:checkhealth aineo` warns
of both (|aineo-health|).

6. CONFIGURATION                                         *aineo-configuration*

aineo reads its settings from two places, and works with neither:

                                                                     *g:aineo*
vim.g.aineo		A table, set before aineo loads: >lua
			    vim.g.aineo = { prefix = ',' }
<
                                                               *aineo.setup()*
require('aineo').setup({opts})
			Records {opts}, a table shaped as `vim.g.aineo`, and
			does nothing else. Each call replaces the options
			the last recorded. A setting `setup()` gives wins
			over the same setting in `vim.g.aineo`.

The settings are checked when aineo uses them — when the editor has started,
and at each action but Send, which uses no setting. A wrong value is one
error naming the setting, such as
`aineo: layout.report_height: expected a number strictly between 0 and 1,
got 2`; at startup it also means no prefix keys and no autostart. A key
aineo does not know is ignored, and `:checkhealth aineo` names it.

                                                         *aineo-config-prefix*
prefix			A non-empty string, or `false`. Default: `'\'`
			The key sequence before each of aineo's keys
			(|aineo-keys|). `false` maps no key; |:Aineo| and the
			`<Plug>` mappings remain. The empty string is
			refused.

                                                      *aineo-config-autostart*
autostart		A boolean. Default: `true`
			Whether a bare `nvim` opens the layout by itself
			(|aineo-autostart|).

                                                     *aineo-config-claude.cmd*
claude.cmd		A list of at least one string. Default: `{ 'claude' }`
			The command run in the left terminal, as a list of
			words, never through a shell. aineo appends its own
			arguments (|aineo-report|). It must not hold
			`--continue`, `--resume` or `--session-id`, since
			aineo picks the session (|aineo-claude-session|):
			Claude Code 2.1.283 refuses `--session-id` beside
			`--continue` or `--resume`, printing "Error:
			--session-id can only be used with --continue or
			--resume if --fork-session is also specified.", and
			exits 1. A wrapper works: >lua
			    vim.g.aineo = {
			      claude = { cmd = { 'npx', '-y',
			        '@anthropic-ai/claude-code' } },
			    }
<
                                           *aineo-config-layout.report_height*
layout.report_height	A number strictly between 0 and 1.
			Default: `2/3`
			The Agent Report's share of the right column's
			rows; Input takes the rest.

==============================================================================
7. SEND                                                           *aineo-send*

Send (`\s`, |:Aineo-send|) gives Claude what you wrote in Input, as one
message: Input's lines, joined by line feeds, go to Claude's terminal as one
bracketed paste followed by Enter, and Input is emptied. Control characters
but tab, line feed and carriage return are removed first, so nothing in the
text reaches Claude Code as a key.

Send also works while Claude is in a turn: Claude Code queues the message and
runs it after the turn. A draft already in Claude's prompt stays, and the
paste joins it. It sends Input while the changes pane hides it, too.

Visual Send ~
In Visual mode, in Input, `\s` (|aineo-v_\s|, |<Plug>(aineo-send)|) sends
the selection alone — characterwise, linewise or blockwise — as one message,
the same paste and Enter, and removes it from Input; the rest of Input
stays. What leaves Input is what Vim's own `"_d` removes, and the message is
exactly that text: each line's part of the selection, joined by line feeds.
A line of a block too short to reach the block gives an empty line, with no
spaces for padding; a block with `$` takes each line to its own end; a tab,
a double-width character, or an emoji drawn as one with its modifiers, that
a block cuts is removed and sent whole, and spaces take the place of its
part outside the block. A characterwise selection that takes in the end of
a line (`v$`) takes its line break too, which joins the lines, and sends it
— but not on Input's last line, which has none, nor under 'virtualedit',
where a selection past the end of a line takes no line break and sends no
spaces. A linewise selection is sent as its lines, joined by line feeds,
with none after the last, as a Send of Input is. With 'selection' set to
`old`, a characterwise selection that ends on an empty line ends, as Vim's
`d` ends it, on the line above, or takes whole lines, line breaks and all,
when it starts in a line's indent; when it starts past the end of the line
above, `d` removes nothing and nothing is sent. With 'virtualedit' set to
`all` alone, it keeps its end. No register is written, and the cursor stays
where `"_d` leaves it, in Normal mode.

Outside Input, `\s` in Visual mode sends and removes nothing, and tells you
once that Visual Send works in Input.

Send sends nothing, and tells you why with one warning starting with
`aineo: nothing sent —`, when there is no Input yet (open the layout), when
Input — or the selection — holds only white space, and when Claude Code is
not ready: not started, still starting, behind a dialog that awaits your
answer, or exited. A Visual Send that sends nothing removes nothing and ends
Visual mode; `gv` selects the text again.

Undo ~
`u` in Input brings back what a Send removed, one `u` per Send: Input's text
after a Send of Input, the selection, where it was, after a Visual Send —
wherever `\s` was typed, and while the changes pane hid Input. `u` restores
Input only: the message has reached Claude. The draft the layout restores
into Input (|aineo-draft|) is not undone: after a Send, `u` brings the text
back and stops there. How many Sends `u` can reach is your 'undolevels'
(|aineo-limits|).

Claude Code counts as ready once its input box has shown, unbroken, for 1.5
seconds. A permission dialog drawn in the few tens of milliseconds before
aineo notices it could receive the paste and the Enter (|aineo-limits|).

==============================================================================
8. THE AGENT REPORT                                             *aineo-report*

aineo starts Claude Code with four additions of its own:
- the session it resumes, or the id of a new one: `--resume` or
  `--session-id` (|aineo-claude-session|);
- instructions appended to its system prompt, telling Claude when to call
  the report tool and how to write a report (below);
- aineo's MCP server, which Claude Code runs as a headless `nvim`, given
  through `--mcp-config`;
- the report tool allowed without asking: `--allowedTools
  mcp__aineo__report`.
The server is given this editor's address, |v:servername|, and relays each
report to the editor there. Claude Code also gets `AINEO_CHILD=1` in its
environment, so a Neovim started inside it never autostarts.

A report holds a `task`, a `status` — `started`, `progress`, `blocked`,
`done` or `failed` — a one-line `summary` and, optionally, `details`. The
Agent Report shows each as: >
    HH:MM [status] task — summary
          details, indented under the status
<
A line break in the task or the summary becomes a space. The Report follows
the newest report.

The instructions ask Claude to write each report for a person, in plain
language: what was done or planned, and how, never the reasons for its
decisions. A `blocked` or `failed` report states, as a fact, what blocks the
task or what stopped it. A `started` report of a plan lists the features
planned in its details, one per line; a `done` report lists what was done,
the features, one per line. References go only at the very end of a report,
in parentheses, by number or ID only, such as `(D18, C12, #31)`: on a line of
their own, the last of its details, or at the end of its summary when it has
no details. These rules are for reports only, not for Claude's other replies.
A running Claude Code keeps the instructions it started with.

Links ~
Every web link in a task, a summary or details is underlined, in
|hl-AineoReportLink|, and carries its address: ⌘-click opens it in a
terminal that opens OSC 8 hyperlinks, as iTerm2 does, and |gx| opens it
from the keyboard. A link starts with `http://` or `https://`, in any case,
at the start of the text or after a character that is not an ASCII letter
or digit. It runs up to an ASCII space, a control character, `<`, `>`, `"`,
`|`, a backtick or a byte that is not part of well-formed UTF-8, so a link's
address never holds a control character or a byte that is not well-formed
UTF-8. Any other character, such as `é`, `—` or a non-ASCII space, is part of
the link. It leaves out the `.` `,` `;` `:` `!` `?` `'` `*` `~` it ends in,
and a `)`, `]` or `}` with no opening partner inside it, one after another
until it ends in none of them: `(see https://example.com/a).` links to
`https://example.com/a`. What is left holds at least one character after the
`://`, or is no link.

Paths ~
A path in a task, a summary or details that names a regular file that
exists — not a directory, a FIFO or a device — is underlined, in
|hl-AineoReportPath|. Double-click it to open the file in the middle column,
at its line when it names one:
`render.lua:112` opens `render.lua` at line 112, a line past the file's end
at its last line, and `:0` at its first. A double-click works from Normal
mode, from Insert mode, as when you click from Input, and from Claude's
terminal; it needs 'mouse' on in Normal and Insert mode, as Neovim's
default, `nvi`, has it. Anywhere else in the Report, a double-click selects
the word, as Neovim's own does; in the Report, it takes the place of a
`<2-LeftMouse>` mapping of your own. A path carries no address: ⌘-click
opens only web links. |gf| and |gF| open a path too, in the middle column,
but find its file as Neovim does, in the current directory and 'path'.

A path runs up to an ASCII space, an ASCII control character, `<`, `>`,
`"`, `'`, `|`, a backtick, `(`, `)`, `[`, `]`, `{`, `}`, `,` or `*`, so a path
in quotes, brackets or Markdown emphasis, `**lua/x.lua**`, is found; it
leaves out the `.` `:` `;` `!` `?` it ends in, one after another, and keeps
a `~`. It holds a `/`, or a `.` that is neither its first nor its last
character: `lua/x.lua`, `./Makefile`, `/etc/hosts`, `README.md` and
`.luarc.json` are paths, `Makefile` and `.gitignore` are not. A `:<line>` or
`:<line>:<column>` at its end is part of it and names the line; a range,
`x.lua:12-20`, or `x.lua#L12` names no file. A relative path is looked up in
the working directory (below), an absolute one as it is; `~` is not
expanded. After a `:cd`, the relative paths a new Claude Code writes may not
be found. A file name holding a space is never found whole, and text inside
a web link is never a path. A path is looked up when the Report shows its
report: a file made later is underlined the next time the Report shows it,
after `:edit` in the Report, and one removed stays underlined until then. A
double-click looks the path up again: when it names no regular file any
more, or cannot be looked up, the double-click opens nothing and tells you
why.

Colours ~
The Report shows the time in |hl-AineoReportTime|, and the `[status]`,
brackets included, bold, in the group of its status, only where it placed
them, never text like them in a task, a summary or details; web links in
|hl-AineoReportLink|; and paths to files in |hl-AineoReportPath|. The bold
is |hl-AineoReportStatusBold|, beneath the group of the status, linked to
Markdown bold, `@markup.strong`: the bold, and whatever else a colour scheme
gives Markdown bold — a background, italic, underline, or no bold at all —
shows on the `[status]`. Its colour does not,
unless the status's own group has no text colour, such as
`AineoReportDone` given only a background (`guibg=`). To turn the bold off
and keep the colour, put this in your config, before or after your colour
scheme, or run it at any time. In Lua: >lua
    local function aineo_bold_off()
      vim.cmd('highlight clear AineoReportStatusBold')
      vim.cmd('highlight link AineoReportStatusBold NONE')
    end
    aineo_bold_off()
    vim.api.nvim_create_autocmd('ColorScheme', {
      group = vim.api.nvim_create_augroup('aineo_bold_off', {}),
      callback = aineo_bold_off,
    })
<
In Vimscript: >vim
    highlight clear AineoReportStatusBold
    highlight link AineoReportStatusBold NONE
    augroup aineo_bold_off
      autocmd!
      autocmd ColorScheme * highlight clear AineoReportStatusBold
      autocmd ColorScheme * highlight link AineoReportStatusBold NONE
    augroup END
<
The bold stays off through every report, `:edit` in the Report, and every
later `:colorscheme`, even one that makes `AineoReportStatusBold` bold: the
`ColorScheme` autocommand turns it off again. A bare `:highlight clear`
fires no `ColorScheme` event, so the bold comes back until the next
`:colorscheme`, or until you run the recipe again.
Each group links to one of Neovim's own, unless a colour scheme or a
`:highlight` of your own colours it.
After `:colorscheme` or `:highlight clear`, a group nothing colours any more
links to its default again, with one exception: a group given a default link
of its own (`:highlight default link`, as some colour schemes do) before aineo
first defined it goes back to that link, until the Report shows reports
again — a new report, or `:edit` in the Report. aineo defines the groups when
the Report first shows a report.

                                                          *hl-AineoReportTime*
AineoReportTime      the time, `HH:MM`, linked to `Comment`
                                                       *hl-AineoReportStarted*
AineoReportStarted   `[started]`, linked to `DiagnosticInfo`
                                                      *hl-AineoReportProgress*
AineoReportProgress  `[progress]`, linked to `DiagnosticHint`
                                                       *hl-AineoReportBlocked*
AineoReportBlocked   `[blocked]`, linked to `DiagnosticWarn`
                                                          *hl-AineoReportDone*
AineoReportDone      `[done]`, linked to `DiagnosticOk`
                                                        *hl-AineoReportFailed*
AineoReportFailed    `[failed]`, linked to `DiagnosticError`
                                                    *hl-AineoReportStatusBold*
AineoReportStatusBold  the bold of a `[status]`, linked to `@markup.strong`
                                                          *hl-AineoReportLink*
AineoReportLink      a web link, linked to `Underlined`
                                                          *hl-AineoReportPath*
AineoReportPath      a path to a file, linked to `Underlined`

Reports are kept per working directory, under `stdpath('state')` in
`aineo/reports/`, and shown again when aineo opens in that directory. The
Report shows the newest 2 MiB of them; the file is cut back to its newest
2 MiB once it passes 4 MiB. The working directory is the one of the first
time the layout opened, for the editor's life; each new Claude Code starts in
the working directory of its own moment.

==============================================================================
9. THE AUTOSTART                                             *aineo-autostart*

A bare, interactive `nvim` opens the layout and starts Claude Code by itself,
in the directory Neovim started in. Two scheduled callbacks after |VimEnter|,
so a startup dashboard drawn at `VimEnter` or `UIEnter` — snacks.nvim's,
alpha-nvim, dashboard-nvim, mini.starter — has shown, and the layout
replaces it.

The autostart does not run, and the editor starts as usual, when, in the
order aineo looks for them:
- a setting is wrong (|aineo-configuration|);
- `autostart` is `false` (|aineo-config-autostart|);
- no user interface is attached: `nvim --headless`, `nvim -es`;
- Neovim was given a file to edit: `nvim file`, `git commit`;
- Neovim read its standard input: `echo text | nvim -`;
- Neovim was given something to do besides edit: `-c`, `-S`, `-e`, `-s`,
  `-E`, alone or among other short options (`-Rc`), or a `+` command;
- it runs inside aineo's own Claude terminal (`$AINEO_CHILD` set and not
  empty);
- a session was restored at startup, by a plugin such as auto-session
  from its own `VimEnter` (|v:this_session| set) — `-S` is a startup task
  above;
and, apart from the others, when aineo was loaded after startup, as a
plugin manager loading it lazily does: the keys are mapped then, but
nothing opens. `--cmd`, `-t` and `-q` alone still autostart.

`:checkhealth aineo` tells which of these held, the first in this order
(|aineo-health|).

==============================================================================
10. HEALTH CHECK                                                *aineo-health*

`:checkhealth aineo` reads the configuration and the editor's state and
reports on them. It starts no Claude session, opens no layout and maps no
key; the one command it runs is `claude.cmd` with `--version` appended.

Neovim ~
  The version of the Neovim that runs aineo; an error when it is older
  than 0.12, the oldest version aineo supports (|aineo-install|).

Configuration ~
  An error naming a wrong setting; a warning naming each unknown key.

Claude Code ~
  An error when the first word of `claude.cmd` is not executable. Else
  `claude.cmd --version`, run whole — a wrapper reports Claude Code's
  version, not its own — and killed after 3 seconds, or when Ctrl-C ends
  the check early, with every process in its process group: the first line
  it prints, or a warning when it cannot start, runs longer, fails or
  prints nothing. A command that prints its version and exits but leaves a
  process of its own holding its output open counts as running longer. A
  process it starts that leaves the group, by starting a session or a
  group of its own, is not killed and can outlive the check.

Server socket ~
  The address the editor listens at (|v:servername|); an error when it
  listens nowhere, since Claude's reports could not reach it.

Prefix mappings ~
  For each prefix key, whether it runs aineo's `<Plug>` mapping; a warning
  when it runs something of yours, or nothing. The Visual-mode `\s` comes
  last, its line saying `in Visual mode`. While aineo's |VimEnter|
  handler, which maps the keys, has not run — the editor is still
  starting, as when `nvim +checkhealth` runs the check before `VimEnter`,
  or a `VimEnter` autocommand before aineo's threw an exception — one line
  says so in place of the keys; so does one in the tick a plugin manager
  loads aineo after startup, since the keys are mapped in the next. A
  warning when the leader or the local leader is the prefix: with the
  default prefix and |mapleader| or |maplocalleader| unset or `\`, these
  warnings show. Neovim reads a leader that is a List, a Dictionary or
  longer than 48 bytes as a backslash, and so does the check.

Autostart ~
  Whether the autostart opened the layout at startup, or which reason kept
  it from running (|aineo-autostart|); while aineo's `VimEnter` handler has
  not run, that it has not decided; once it has decided to open the layout,
  that it will. A warning when a setting was wrong at startup, and when the
  autostart tried to open the layout and failed, with the error it met.

                                                             *g:aineo_startup*
  aineo records its decision in `vim.g.aineo_startup`, a table whose
  `reason` is one of, in the order aineo reaches them: `starting` (sourced,
  the editor not started yet), `wrong-setting`, `autostart-off`, `no-ui`,
  `file-argument`, `stdin`, `startup-task`, `inside-claude`, `opening`
  (the open decided, not tried yet), `session-restored`, `opened`,
  `open-failed` — with the error in `failure`. When aineo is loaded after
  startup: `mapping-late` (its keys not mapped yet), then `sourced-late`.
  The health check reads it; aineo never does.

Limits ~
  The stop on quit of |aineo-limits|, which a check cannot detect.

The check passes when it shows no error; warnings are advice.

==============================================================================
11. LIMITS                                                      *aineo-limits*

Stopping Claude Code on quit ~
When Neovim quits, aineo stops a running Claude Code from its own
|VimLeavePre| handler, by its keys: one Ctrl-C, then a double Ctrl-C, then
`jobstop()` — up to about 12 seconds. A `VimLeavePre` handler registered
before aineo's that raises an error makes Neovim skip aineo's: Claude Code
then only gets Neovim's hangup, and a Claude Code that hangs outlives the
editor. aineo cannot detect this.

The 80-column start ~
At startup, a message longer than |v:echospace| — 68 columns on an 80-column
screen — holds Neovim at a hit-enter prompt. aineo's line for a
`claude.cmd` that is not executable fits for a command name of up to 29
characters; a longer one, such as an absolute path, still prompts.

Send and a dialog ~
A permission dialog drawn in the few tens of milliseconds before aineo
notices it receives Send's paste and Enter. What the dialog does with them
was not measured.

Undo after a Send ~
- A Send can reach a Claude Code that has just ended before aineo notices:
  the write to its terminal then fails, and Send puts Input back as it was
  and shows the error. Emptying Input and putting it back are then one
  undo step: the first `u` changes nothing you can see, and the second
  undoes your own last change. A Visual Send does the same, and `gv` then
  selects the text again.
- 'undolevels' decides how many Sends `u` can reach. At 0, `u` toggles the
  last Send alone: after two Sends, `u` brings back the second's text, a
  second `u` empties Input again, and the first's text never comes back. At
  -1, `u` brings nothing back. The same holds for a Visual Send.

Repeating a Visual Send ~
A Visual Send removes the selection with Vim's own `"_d`, so `.` after it
repeats that removal: it removes as much text again, at the cursor, and
sends nothing. `u` brings it back.

A block's edge on an invalid byte ~
A byte that is not UTF-8, followed by a combining mark or a zero-width
joiner, is one character to a block's `"_d`. When a block's edge falls on
it, `"_d` removes both, and the Visual Send sends one of them: the byte
when the block ends on it, the mark when the block starts there.

The changes pane ~
- A large diff: a diff shows at most 1 MiB of what git gave, cut at the
  last line break within it, or a first line longer than that cut there,
  under one line saying how much of it is shown. git still gives the whole
  diff first, which takes its time and memory.
- A large repository: each read runs git over the whole working tree. On a
  repository of 20 001 files whose every file had been rewritten with its
  own content, one read took 1.5 to 3.1 seconds. A git that runs past 10
  seconds is stopped, and the read said to have failed.
- A pull, a merge, or a rebase onto newer upstream commits during the
  session lists those commits, and their files, as the session's: the
  commits window lists every commit reachable from `HEAD` and not from the
  base.
- A restart of Claude Code in another working directory keeps the first
  repository and its base.
- Where aineo cannot watch the working tree's subdirectories (Linux), the
  files window says so first: a change in a subdirectory shows at the next
  showing of the pane, save or commit, and a branch moved by
  `git update-ref` from another worktree is missed too. No timer reads the
  repository.
- When the editor quits, aineo stops its watch, but a git it is running
  then runs to its end, outliving the editor.
- A buffer named for a diff that aineo did not make, such as one a restored
  session made under `aineo://diff/{path}`, cannot give up its name while
  Neovim allows no change of text, or in the command-line window: when the
  diff Enter read for that name arrives then, Neovim shows an error with a
  stack trace, the diff is not shown, and aineo does not try again. Enter
  on the line again shows it, the other buffer giving its name up.
