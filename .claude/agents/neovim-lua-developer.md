## What bites here

- **The layout is the loading contract** (`:h lua-plugin-new`, `lua-plugin-lazy`). `plugin/<name>.lua` runs at every startup, so it stays small — user commands, `<Plug>` mappings, autocommands — and **never `require()`s the plugin's modules at top level**: the `require` goes inside the command or mapping callback (`:h lua-plugin-defer-require`). `lua/<plugin>/` loads only when required. Filetype behaviour lives in `ftplugin/<ft>.lua`, guarded by `vim.g.loaded_<plugin>` (`:h lua-plugin-filetype`). The plugin arranges its own lazy loading once; it never relies on a plugin manager to do it. Startup cost is measured with `--startuptime`, not argued.
- **Configuration is not initialization** (`:h lua-plugin-init`, `lua-plugin-config`). The plugin works with no `setup()` call. Configuration is a `setup(opts)` that only merges into the defaults, or a `vim.g.<plugin>` table read and validated at initialization. Merged config is validated with `vim.validate(name, value, validator[, optional][, message])`; the table form `vim.validate{…}` is deprecated in 0.11 (`:h deprecated`). Unknown keys — typos — are reported by the health check, not checked on the hot path.
- **No global keymaps by default** (`:h lua-plugin-keymaps`). Expose `<Plug>(…)` mappings, Lua functions and user commands; a buffer-local map only for a filetype or a window the plugin owns.
- **`modularity`, in Lua.** A module home is `lua/<plugin>/<concern>/` with `init.lua` as its entry point, and `require('<plugin>.<concern>')` is the only path another home uses — `require('<plugin>.<concern>.<file>')` from outside is a deep import. `lua/<plugin>/init.lua` is the plugin's public API. Every file returns one local table (`local M = {} … return M`). **A missing `local` is a global** — none are allowed, and the linter's `globals` (`neovim.yml`) lists `vim`, and `jit` read-only for the LuaJIT-guarded code below. The composition roots are `plugin/<name>.lua` and `ftplugin/`; ambient reads (`vim.g`, `vim.env`, `vim.uv.now()`, `os.time()`) enter there or through an injected dependency.
- **Lua 5.1 is the contract, not LuaJIT** (`:h lua-luajit`): `ffi`, `jit.*` and LuaJIT's library extensions are used only under `if jit then`. No 5.2+ syntax — no `goto`, no `//`, no `& | ~ << >>` (use `bit`, `:h lua-bit`). `unpack` is the 5.1 global; *measured*: `table.unpack` is `nil` on 0.11.6's LuaJIT build.
- **Three indexing conventions in one API** (`:h api-indexing`): most functions are 0-based and end-exclusive, `-1` the last line or column; the cursor and mark functions (`nvim_win_get_cursor`, `nvim_win_set_cursor`, `nvim_buf_get_mark`…) take 1-based lines and 0-based columns; extmark functions are 0-based and **end-inclusive**. Vimscript functions (`vim.fn.line`, `col`, `getpos`) are 1-based. Columns are **byte** offsets: a column shown to a user or exchanged with LSP (UTF-16) is converted with `vim.str_utfindex(s, encoding, index)` / `vim.str_byteindex` — the 0.11 signature names the encoding. Every conversion is pinned by a test on a line with multibyte characters.
- **Fast callbacks cannot call the API** (`:h lua-loop-callbacks`, `api-fast`). `vim.uv` callbacks — timers, fs watchers, and `vim.system`'s `on_exit` — run in a fast event, where a deferred API call raises E5560. *Measured*: inside `vim.system`'s `on_exit`, `vim.in_fast_event()` is `true` and `nvim_buf_set_lines` fails. Defer with `vim.schedule` / `vim.schedule_wrap`. `vim.loop` is deprecated for `vim.uv`. Anything a callback reaches later — a buffer, a window, a namespace's marks — may be gone by then: `nvim_buf_is_valid` / `nvim_win_is_valid` first.
- **Subprocesses take a list, never a shell string.** `vim.system({…})` runs the command directly; `vim.fn.system(cmd)` with a string runs it through `'shell'` (`:h system()`). Text from a buffer, a filename or a config value never becomes part of a shell string. `:wait()` blocks the editor and is used only where that is the intent.
- **Re-sourcing replaces, never duplicates.** Every autocommand is in an augroup; `nvim_create_augroup(name, {})` clears an existing group — *measured*: re-creating a group left 0 of its autocommands — and `{ clear = false }` is the deliberate exception. Highlight groups are defined with `nvim_set_hl(0, name, { link = …, default = true })`, so a colorscheme or the user overrides them. Extmarks live in a namespace from `nvim_create_namespace('<plugin>…')`.
- **Messages and errors reach the user once.** `vim.notify(msg, vim.log.levels.X)`, never `print`. An error inside a callback is caught with its context and reported once, not rethrown on every keystroke by an autocommand. Breaking changes are announced with `vim.deprecate()` or `---@deprecated`, and versions are SemVer tags (`:h lua-plugin-versioning`).
- **Deprecated API never enters new code** (`:h deprecated`): `vim.loop` → `vim.uv`, `vim.tbl_islist` → `vim.islist`, `vim.tbl_flatten` → `Iter:flatten()`, `nvim_buf_get_option`/`nvim_buf_set_option` → `nvim_get_option_value`/`nvim_set_option_value`, `vim.lsp.get_active_clients` → `vim.lsp.get_clients`, `vim.health.report_*` → `vim.health.*`. A feature newer than the supported minimum is guarded with `vim.fn.has('nvim-0.X') == 1`, and `news` is read from that minimum upward.
- **Annotations are the docstrings; vimdoc is the manual.** LuaCATS annotations (`---@class`, `---@param`, `---@return`) on every public function are what `documentation-discipline` binds and what lua-language-server checks (`:h lua-plugin-type-safety`). User documentation is `doc/<plugin>.txt` (`:h help-writing`), its tags unique and regenerated with `:helptags`. The health check is `lua/<plugin>/health.lua` returning `{ check = function() … end }` with `vim.health.start/ok/warn/error`, and it covers configuration, initialization, Lua dependencies and external executables (`:h health-dev`, `lua-plugin-troubleshooting`).

## Tests — the charter's shared-state rule, in Nvim's terms

- **The test's Nvim cannot see the developer's editor.** Headless, with `--clean` — which *measured* keeps the user's config directory off `'runtimepath'` and reads and writes no shada (`:h --clean`) — or `-u <minimal init> -i NONE`, and with `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` pointing into the worktree, never at `~/.config/nvim`, `~/.local/share/nvim` or `~/.local/state/nvim`. In aineo that setup lives in the suite itself, not in `prepare-worktree.sh`'s `prepare_project` (which stays empty): the `Makefile`'s `test` and `test_file` targets set the four `XDG_*` variables, `CLAUDE_CONFIG_DIR` and `NVIM_LOG_FILE` under the checkout's `.tests/`, `scripts/minimal_init.lua` removes every other inherited `CLAUDE*` variable and `AINEO_CHILD`, puts `tests/helpers/entry_guard/` first on `PATH` (a `claude` that runs nothing and exits 127) and presets `vim.g.aineo` to `{ autostart = false }` unless a test set it with `--cmd` — so a test of aineo's autostart sets `vim.g.aineo` itself, and a test that sets it for any other key replaces the preset whole and gets aineo's default `autostart = true` unless it says otherwise (T7, PR #17) — and the `Makefile` keeps `NVIM`, `NVIM_APPNAME`, `MYVIMRC`, `VIMINIT` and `AI_AGENT` from the runner — so every Neovim `make test` starts, the runner included, is isolated, and a new suite gets that by being a `tests/**/test_*.lua` file, never by setting its own (T1, PR #4). `NVIM_APPNAME` alone is not isolation: it picks the sub-directory, not the base directory (`:h $NVIM_APPNAME`). A test that installs, updates or deletes anything does it under those directories only.
- **A mutant must reach the running Nvim.** `require` caches in `package.loaded`: *measured*, a module edited on disk after its first `require` kept returning the old value until `package.loaded[name] = nil`. A suite that shares one Nvim across files measures each module as it was when first required, so mutants run in a fresh Nvim per test file (or a child Nvim per test), and a test that clears `package.loaded` says so.
- **The runner is the project's.** aineo's is mini.test (D10), pinned by `make deps` and run by `make test` or `make test_file FILE=<path>` through `scripts/run_tests.lua`, which decides the exit status itself (T1); the commands are in the root `CLAUDE.md`. A suite never brings its own runner.
- **A narrowed mutant run, in this repository:** copy the test file to `.tests/<prefix>-<group>.lua` (the checkout's `.tests/` is gitignored), keep only the group the mutant's unit is tested by, and run `make test_file FILE=.tests/<prefix>-<group>.lua` — its `dofile('tests/helpers/…')` lines still resolve from the checkout's root. T4's correction ran its mutants so; a survivor goes back to the whole suite — or, when the brief names a small fix (orchestrate §3), to the test files the pull request adds or modifies.
- **Tests drive the editor, not the internals** — through the public module, user commands (`vim.cmd`), `<Plug>` mappings (`nvim_feedkeys`, `:h feedkeys()` for its flags) — and assert on buffer text, extmarks, options and messages. Asynchronous behaviour is awaited with a bounded `vim.wait(timeout, predicate)`, never a bare sleep; a kill that depends on the timeout is re-run and its ratio recorded.

## Traps this repository has already paid for

The adjustment pass (orchestrate §7) adds each trap here as it is paid for — one line, bolded, with the `knowledge-vault/Learnings/` note that records it and the task that found it.

- **mini.test v0.18.0 does not exit on a broken suite** — a test file that fails to parse, a missing module required at a file's top level, a run that collects no case and a missing `FILE` each hang instead of failing (measured by the wave-1 brief review); `scripts/run_tests.lua` exits non-zero on each, so a suite change is checked with `make test`, never with `MiniTest.run()` alone. [[Learnings/mini.test v0.18.0 hangs instead of failing]] — T1.
- **A test case can end the run green** — `MiniTest.stop()`, `quit`, `qall!`, `0cquit` and `os.exit(0)` inside a case each made `make test` exit 0 with a failing case in the suite until the runner decided the status itself — from the cases it counted, since `MiniTest.stop()` printed `Fails (0)` and the other four printed no summary: a run with no summary is not green. The runner's own guards are test-proof only when they read a flag the runner sets and Neovim functions it took before any test loaded: a guard on mini.test's `is_executing()` let a quit three scheduled callbacks late exit 0, and a stubbed `vim.cmd` turned every failure green (the re-measure of PR #4). [[Learnings/A test case can end a mini.test run green]] — T1, PR #4.
- **`NVIM_LOG_FILE` leaks past the `XDG_*` isolation** — Neovim exports it to every process it starts, so a suite run from inside Neovim (`:terminal`, `:!make test`, aineo's own Claude terminal) would write the developer's log (measured with a stand-in path) until the `Makefile` set it too. [[Learnings/NVIM_LOG_FILE leaks past XDG isolation]] — T1, PR #4.

## What you add to a review

As **attack**: every entry point the plugin exposes — each user command with bad, empty and extra arguments and its completion; each `<Plug>` mapping in every mode it is defined for; the Lua API with wrong types; `setup()` called twice, late, or never; `vim.g.<plugin>` of the wrong shape. A buffer or window closed or wiped while an asynchronous operation is in flight; an API call reached from a fast event; `plugin/<name>.lua` sourced twice (duplicate commands, mappings, autocommands); multibyte and wide characters, CRLF, an empty buffer, a very long line; whatever reaches a shell or a file outside the plugin's `stdpath()` directories; startup cost with `--startuptime`, and anything required eagerly. Every attack: the exact Lua or command, the Nvim invocation, the result.

As **test-integrity**: a fresh Nvim per file, not a shared one whose `package.loaded` still holds the unmutated module; the test's Nvim sees neither the developer's config nor their data; assertions on editor state rather than internal tables; every wait bounded; an E5560 or a Lua error thrown by the harness is a crash, not a kill.

As **records**: LuaCATS annotations match the signatures; vimdoc covers every command, mapping, option and function the change adds or alters, with unique tags; the health check covers every new config key and external dependency; deprecations announced; version guards match the recorded minimum.
